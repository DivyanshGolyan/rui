# Verification

[ARCHITECTURE.md](ARCHITECTURE.md) owns behavior; this document owns required evidence. Test production interfaces and real SQLite transactions against independent expectations. Crash tests kill a fixture process and reopen in a fresh one; injected returned errors are fault tests. Record revision, machine, dependencies, inputs and measurements. Distinguish production qualification from prototypes, source inspection, compilation and accepted decisions; [research evidence](research/README.md) records those limits.

## Canonical gates

The composed driver rejects older interpreters before launching tests and records the selected interpreter. On macOS, select a current Python installation rather than `/usr/bin/python3`. Diagnose interpreter failures separately from product assertions.

Pushes with an unavailable predecessor use a usable main merge base for both selection and whitespace checks; an unavailable review base remains an error.

Pushes run the affected-owner mapping on Linux and macOS. Draft PRs retain cheap `test-logic` feedback. A push matching an open, ready, mergeable PR head omits duplicate work; unknown mergeability or an unavailable PR lookup retains the affected-check fallback. Review-ready PRs test the actual merge ref. Both platforms start after planning, independently of each other. `check` includes formatting, ReleaseSafe native tests and process integrations, a Debug artifact/recovery smoke, and ReleaseSmall deliverables. Its native and process suites run concurrently except short-deadline Host-startup and Debug smoke cases, which follow the parallel batch. Required functional assertions remain required even when their source fixture changes.

Run `zig build check-full` on the exact candidate for build/dependency changes, release qualification, or claims of isolated process latency. It runs routine native tests, the pinned evaluator string sanitizer, evaluator owner cases and process integrations serially after formatting and production builds. It is not an every-edit gate. Each separately merged platform-sensitive change needs its affected native checks; the daily suite below does not qualify intermediate merges. Rerun affected final-candidate checks after corrections unless tooling establishes the validity of an existing outcome. Build caches alone cannot establish that validity. Serial execution reduces unrelated load but does not establish scheduler order without owner-visible outcomes or handshakes.

For CI feedback, each platform's full gate runs `-Dcheck-part=execution` and `-Dcheck-part=callers` on two isolated native runners at the same merge ref. Both parts must pass. Their disjoint process fixtures cover the unchanged full gate exactly once. The execution part stays serial and owns native tests, sanitizer and evaluator cases. The callers part reuses the ordinary gate's eight parallel-safe caller fixtures, each with private Store/HOME, endpoints and owned-Host census. It waits for every fixture before running Host-process, allocator, launch and Debug smoke cases serially so short startup deadlines remain unloaded. [qualification.py](tests/ci/qualification.py) gives Linux's other selected targets separate jobs. macOS packs native work into at most three workers: execution plus portable logic, callers, and remaining native targets. Remaining timing-sensitive suites still run serially within their worker. This leaves two of the documented five standard Mac slots for other workflows; the account's plan and any raised limit are unavailable through this token. The existing `linux` and `macos` statuses fail if any selected job fails or is cancelled. The default `zig build check-full` still runs every case in its original serial order; use that default for single-machine isolated-latency or release evidence.

The shared driver reports one `fixture passed: exit=0 elapsed=1.234s` record per completed invocation, including nonzero exits as `failed`. Two short-lived Python helpers sample the monotonic clock around the shell's invocation and wait. The elapsed interval includes clock-helper startup/exit overhead, but excludes later inventory-order waits and log printing. Parallel fixtures save one status line beside their existing logs and publish it in inventory order; serial fixtures report immediately on stderr. The shell retains launch/wait ownership through recording, without new signal handlers, process groups or deadlines. Timing failure reports unavailable when possible and preserves the fixture exit status. Status files share the existing temporary-directory lifetime, with at most 22 records for the ordinary native gate. Driver tests use controlled clock values and gated reverse completion to distinguish invocation time from delayed printing, with successful and failed peers. These diagnostics attribute fixture cost, not CPU time, child-only lifetime, isolated latency or a speedup; fixture budgets, fail-fast/drainage policy and failed-log retention remain unchanged.

[build_artifact.py](tests/ci/build_artifact.py) transfers emitted native executables and pinned package sources through an immutable same-run artifact, expiring after one day. Workers use the successful producer's exact artifact ID and verify GitHub's archive digest, source/tree, run/attempt, complete platform selection, native tools, image, compiler, fixture dependencies, inner archive digest and executable hashes/modes before using it. Extraction rejects traversal, special files, hardlinks and symlinks. This receipt says `compiled-not-tested`, never `passed`; gates execute through the existing driver with `-Dci-artifacts=.zig-cache/o/ci-compiled`. The build graph uses those binaries instead of Compile steps, retaining the original test protocol, side-effectful execution, fixture ordering and assertions. Copying compiler caches is not a compile-once guarantee because Zig's metadata keys include filesystem identity. Worker setup identifies tools and installs required fixture dependencies but skips duplicate build-cache restoration and source fetching. The compiler still bootstraps the build runner; Go and sanitizer gates retain the fresh-compilation exceptions above. Test-acceptance reuse remains a separate authority below.

Both compiled-handoff options select Zig's baseline CPU, rather than the producer's physical CPU. With the pinned compiler, this is `x86_64` on Linux and `apple_m1` on macOS ARM64. The build graph rejects incompatible target or optimization overrides and emits the resolved CPU model and feature set in `ci-cpu.json`. Consumers check that manifest before executing any gate, including after a cached build configuration. Artifact inputs bind the CPU floor, and acceptance inputs additionally bind the complete manifest. Ordinary local builds retain native CPU selection. Transport's separate C build uses explicit platform targets without host-specific CPU flags. These constraints prevent unconditional producer-only instructions from reaching another hosted worker. Architecture and runner-image equality alone do not establish CPU compatibility.

Selected checks may reuse acceptance only through [evidence.py](tests/ci/evidence.py). Reuse is limited to the native `test`, `test-full` and `test-logic` gates, whose complete executable sets are retained. Process fixtures, sanitizer and Go checks execute afresh because temporary helper executables are not retained for identity verification; unknown future targets also fail closed. The verifier checks the complete git tree, target and partition, platform, runner image, native-tool and compiler hashes, Python, workflow, event and branch. The origin must be a successful same-repository run. Push source identity must match the run SHA. PR source identity must have the run's base/head parents and the independently reconstructed merge tree. The downloaded artifact must match GitHub's SHA-256 digest, and every recorded cached executable must still match its hash. Missing, expired, unavailable or mismatched evidence executes the checks. Commit messages and manual claims never supply acceptance. Reused evidence links its origin and explicitly reports no new execution. Qualification and daily runs always execute afresh.

Cleanup resolves the complete inventory and PR states before deleting recognized Rui caches. In that inventory, closed PR merge refs lose their caches, open PRs retain the newest build snapshot per platform and partition, and main retains two. Other namespaces and branch refs remain untouched. These are post-publication cleanup targets, not an atomic count or byte quota: concurrent saves can exceed them until a later successful cleanup observes those saves. Cleanup failure leaves excess snapshots for diagnosis and subsequent maintenance; it does not retry tests or make a failed producer successful. Existing required checks and the changed-main macOS test cadence remain unchanged.

### Product tenets at stage completion

Each implementation stage must demonstrate the following through its completed caller flow, alongside its correctness and recovery checks:

- **Simplicity:** explain the required behavior or demonstrated cost that justifies each added module, durable fact, cache or queue. Check for duplicate authority and caller-owned coordination that belongs inside an existing owner; compare a simpler approach where one could preserve the required behavior. Identify dependencies introduced or removed on another owner's representation, call order or lifetime; justify each retained dependency by required behavior. Passing tests establishes tested behavior, not design simplicity.
- **Explainability:** walk ordinary work, failure and recovery in plain language using the stage's normal results and inspection. A reader should be able to tell what happened, what remains uncertain and what can happen next. Explanations must follow owning facts without treating optional diagnostics as recovery authority. Check this as each caller path appears, before final presentation work.
- **Memory footprint:** rerun comparable fixtures as resource owners are added, recording aggregate peak and retained-idle footprint, including native libraries and Rui helpers. At fixed capacity, vary payload and durable-history populations independently and exercise fill/drain with delayed cleanup or failure. Explain changes from the preceding measurement and resolve unexplained growth before dependent work builds on it. Use the existing [resource measurements and targets](#resources-and-accepted-host-qualification-targets); stage checks do not replace qualification of the complete simultaneous workload or introduce per-module quotas.

Record these checks with the stage's existing evidence; no separate scorecard or reporting system is required.
