# Request-failure ownership before model dispatch

Research for [issue #206](https://github.com/DivyanshGolyan/rui/issues/206), inspected 2026-09-16. This is decision evidence, not an accepted-contract amendment or qualification result. **Contract** below means the pre-decision `ARCHITECTURE.md`/`VERIFICATION.md` inspected on that date; **observed** means Rui or pinned prior-art source at that point; **recommendation** is this note's conclusion. Prior art is evidence, not authority. The subsequent Wayfinder decision removed issue #201's pre-Operation rejection premise from the accepted contract.

## Conclusion

The evidence establishes **no genuine provider-independent pre-Operation failure presently satisfying #201**.

The only contract-shaped candidate is failure while Core forms the selected historical request boundary: after it has selected a pending prefix and configuration revision, but before it can atomically validate/projection-bind that prefix and create the Operation/manifest. Such a failure would have to be a deterministic, locally decidable incompatibility of canonical Core facts. The accepted contract names this boundary, but neither current production code nor the inspected prior art supplies such a concrete condition:

- current Rui creates the Turn, binds and projects selected messages, and creates the model Operation in one transaction before any adapter work;
- required canonical corruption/read/save failure fences the Host rather than becoming a Turn failure;
- adapter compatibility, request encoding/materialization, credentials, transport, remote rejection, context overflow, and output interpretation are knowable only after a valid Operation exists;
- changing only an adapter may change rendering or reveal compatibility, but may not change Conversation membership. Treating such a condition as pre-Operation would make canonical message application depend on provider-specific behavior and reverse the directionality accepted for #198.

Therefore #201 needs either (a) a newly accepted, provider-independent Core invariant that can deterministically reject the selected canonical recipe before Operation admission, with a concrete production trigger, or (b) scope/acceptance clarification. It should not recategorize an existing post-admission failure merely to obtain a fixture.

## Current Rui implementation

Current production implements the post-Operation categories, but not #201's no-Operation selected-input rejection:

1. `src/store.zig:1687-1744` selects runnable pending input and allocates both Turn and Operation identities inside `admitNextModelAttempt`.
2. `src/store.zig:1745-1798` inserts/updates the Turn, binds selected Message admissions, and projects them into `conversation_entry` before later manifest/attempt work. There is no branch that commits a selected failed Turn without projection or Operation.
3. `src/server.zig:453-557` reserves custody, admits the Attempt, opens the historical view, then materializes the request. Thus every materialization failure is necessarily post-Operation and post-Attempt today.
4. `src/provider.zig:183-290` performs streaming adapter lowering into sealed scratch. `src/server.zig:640-715,748-814` separately classifies transport evidence, validates provider output, and asks Store/Core to settle it. This mostly matches the accepted owner split, but current output path supports assistant-message settlement rather than #198 call classification (`src/provider_output.zig:499-555,645-829`).

This is observed implementation status, not evidence that the current ordering supersedes the accepted #201 contract. It does establish that no existing production failure can simply be relabeled as pre-Operation.

## Recommendation and unresolved evidence

1. Keep Message admission rejection, canonical storage fault, adapter lowering, credentials, transport, remote status/overflow and output rejection in their existing owners and phases.
2. Preserve the #198 direction: adapters establish provider-structural facts; Core alone applies canonical catalog/Conversation semantics. The request side should likewise let adapters reject wire compatibility only after Core has admitted an Operation against canonical history.
3. Do not implement #201 using an injected allocation/scratch/read fault, unsupported provider schema, continuation wire incompatibility, HTTP invalid request or provider overflow. Each either lacks a valid durable work outcome, requires Host fencing, or occurs after a valid Operation.
4. Before implementing #201, name and accept one concrete Core-only invariant whose violation is deterministic at selected-prefix formation. Verify that adapter-only replacement cannot change the decision and that repaired facts can permit later work without replaying the settled prefix. If no such invariant is required, revise #201 rather than add a synthetic state solely for its acceptance test.

Uncertainties: current implementation does not yet exercise #198 call envelopes/actions; live-provider behavior is unqualified; prior-art source layouts and product contracts differ from Rui; and the accepted phrase “local preparation rejects” does not itself identify a real provider-independent production condition.
