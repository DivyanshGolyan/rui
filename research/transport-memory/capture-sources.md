# Slow capture and repeated TLS reuse: additional primary evidence

Checked 2026-09-11 against current official manuals and curl tag `curl-8_22_0`. curl 8.22.0, OpenSSL 3.6.3 and nghttp2 1.70.0 remain experimental pins. [sources.md](sources.md) owns the previously established buffer sizes, pause ceilings, cache cap and shutdown-list evidence; this note adds servicing and reuse interpretation, not a runtime specification. API/source evidence here is distinct from the [companion measurements](capture-README.md).

## Callback servicing and capture ownership

[curl_multi_perform](https://curl.se/libcurl/c/curl_multi_perform.html) processes ready transfers until current reads/writes finish. It exposes no callback-count or elapsed-time budget. [Pinned multi.c 2909 onward](https://github.com/curl/curl/blob/curl-8_22_0/lib/multi.c#L2909) services transfers within one call, and [cw-out.c 186–191](https://github.com/curl/curl/blob/curl-8_22_0/lib/cw-out.c#L186) calls the application write function synchronously. Therefore a blocking capture callback occupies the driving thread. A small callback chunk does not bound the total time before `curl_multi_perform` returns: many callbacks can run in that call. Measure callback duration, whole perform/unpause-call duration and control delay separately.

[CURLOPT_WRITEFUNCTION](https://curl.se/libcurl/c/CURLOPT_WRITEFUNCTION.html) requires returning the complete accepted byte count or an explicit error/pause. Its body callback maximum is normally 16,384 bytes, but callback sizes vary, and routing headers through this callback allows larger chunks. Off-callback consumption consequently needs application-owned bytes before returning acceptance; the callback pointer is not an ownership transfer. The pinned output code passes a borrowed pointer directly and continues after return. A bounded copy can transfer custody to a capture owner; a full destination requires pausing before accepting that chunk. Neither short writes nor pause may silently drop or duplicate data.

[curl's threading contract](https://curl.se/libcurl/c/threadsafe.html) forbids concurrent use of a handle by multiple threads. If capture completes elsewhere, completion must return to the transport owner before handle operations; no worker is required by this evidence. [curl_multi_wakeup](https://curl.se/libcurl/c/curl_multi_wakeup.html) may be called from another thread, but only wakes the current/next `curl_multi_poll`; it does not interrupt an executing callback, wake `curl_multi_wait`, or guarantee one wake per completion. Application completion state remains authoritative. Keep capture bytes, scratch accounting and callback state owned until pending I/O and transport teardown can no longer use them. Successful network completion alone cannot certify a delayed sink write succeeded.

## Pause credit and controls

[http2.c 308–344](https://github.com/curl/curl/blob/curl-8_22_0/lib/http2.c#L308) sets desired stream credit to zero when paused; its decrease branch updates nghttp2's local window without issuing a negative WINDOW_UPDATE. Already advertised credit is not recalled. Thus a bounded application queue is not an equal bound on transport buffering, especially after an unpaused stream has received expanded credit. This complements the initial/expanded window evidence in sources.md. Measure first-callback pauses separately from pauses after flow; keep peer streams progressing and record received, accepted, written and verified bytes independently.

Inference: servicing controls between library calls gives no finer bound than the longest such call. Moving writes outside callbacks may shorten callback occupancy, but if those same slow writes then block the control owner, control latency can still be poor. The experiment must measure that scheduling choice rather than assume a worker or a particular redesign is necessary.

## Connection reuse versus session resumption

[CURLOPT_FRESH_CONNECT](https://curl.se/libcurl/c/CURLOPT_FRESH_CONNECT.html) forces a new connection for a transfer; [CURLOPT_FORBID_REUSE](https://curl.se/libcurl/c/CURLOPT_FORBID_REUSE.html) requests closure after use. Both default to zero. They answer different questions from the idle `MAXCONNECTS` cap already documented. Cache eviction may still leave graceful shutdown in progress; service the multi loop before claiming settled release.

[CURLOPT_SSL_SESSIONID_CACHE](https://curl.se/libcurl/c/CURLOPT_SSL_SESSIONID_CACHE.html) defaults to enabled and controls TLS session reuse, not reuse of an already open socket. [Pinned vtls_scache.c 368–381](https://github.com/curl/curl/blob/curl-8_22_0/lib/vtls/vtls_scache.c#L368) selects the share cache when present, otherwise the multi cache. Keeping the multi can therefore preserve sessions even if easy handles are replaced. [openssl.c 3347–3372](https://github.com/curl/curl/blob/curl-8_22_0/lib/vtls/openssl.c#L3347) offers a cached session through `SSL_set_session`; its reuse diagnostic establishes an offer, not proof the server accepted resumption.

[CURLOPT_MAXAGE_CONN](https://curl.se/libcurl/c/CURLOPT_MAXAGE_CONN.html) defaults to 118 seconds of idle age; [CURLOPT_MAXLIFETIME_CONN](https://curl.se/libcurl/c/CURLOPT_MAXLIFETIME_CONN.html) defaults to 24 hours since curl 8.17.0. These are reuse eligibility checks, not promises of proactive closure at a wall-clock deadline. Record burst spacing and server closure behavior when interpreting reuse.

| Observation | Meaning and limit |
| --- | --- |
| [CURLINFO_NUM_CONNECTS](https://curl.se/libcurl/c/CURLINFO_NUM_CONNECTS.html) | Successful newly created connections for the previous transfer. Sum per burst; failures are not counted. Read before reuse of the easy handle overwrites the transfer result. |
| [CURLINFO_CONN_ID](https://curl.se/libcurl/c/CURLINFO_CONN_ID.html) | Last-used connection identifier, unique within the same connection cache; -1 means none. Pair with new-connect counts to demonstrate same-connection reuse. |
| [CURLINFO_APPCONNECT_TIME_T](https://curl.se/libcurl/c/CURLINFO_APPCONNECT_TIME_T.html) | Microseconds from transfer start to TLS/SSH handshake completion, cumulative across redirects; not isolated cryptographic handshake time. HTTP multiplexing can additionally delay pretransfer. Timing alone proves neither reuse nor resumption. |
| [SSL_session_reused](https://docs.openssl.org/3.6/man3/SSL_session_reused/) | Indicates actual session resumption on an established OpenSSL connection. Prefer observing it in the controlled server's handshake record. |
| [CURLINFO_TLS_SSL_PTR](https://curl.se/libcurl/c/CURLINFO_TLS_SSL_PTR.html) | For OpenSSL, exposes the active SSL pointer; it can be NULL before establishment or after detachment. Read-only resumption inspection must happen while associated and on its owner; do not retain or mutate this pointer. |

For repeated bursts, distinguish same-connection reuse, new connections with resumed sessions and new full handshakes. Keep payload integrity, concurrent population, TLS verification and output capture equivalent while comparing retention and elapsed costs. These API facts alone establish no Linux result or production control-latency qualification.

## Follow-up: accepting a chunk and explicitly pausing

The public [curl_easy_pause contract](https://curl.se/libcurl/c/curl_easy_pause.html) permits calling it from write callbacks (socket callbacks are excluded). Copying the entire chunk into owned storage, calling `curl_easy_pause(easy, CURLPAUSE_RECV)` and returning the accepted count is therefore supported API usage, provided errors are handled and the action preserves any independently required send-pause state. It is **not a source-backed small receive-credit bound**.

The exact 8.22.0 order matters:

1. [easy.c 1182–1198](https://github.com/curl/curl/blob/curl-8_22_0/lib/easy.c#L1182) compares requested pause states and calls `Curl_xfer_pause_recv` for a receive-state change.
2. [transfer.c 880–888](https://github.com/curl/curl/blob/curl-8_22_0/lib/transfer.c#L880) blocks/unblocks the receive rate limiter; on unpause it first flushes a paused client writer, then unconditionally notifies the connection of the requested pause state, then updates progress pause state. [sendf.c 528–532](https://github.com/curl/curl/blob/curl-8_22_0/lib/sendf.c#L528) clears `writer.paused` before flushing cached callbacks.
3. [http2.c 2620–2626](https://github.com/curl/curl/blob/curl-8_22_0/lib/http2.c#L2620) sets the stream's write-paused flag to that notification, recalculates its window and attempts to send pending frames. Without a configured rate limit, unpause targets the previously documented 10 MiB window.

Consequently, when no writer-cache flush is pending, unpause restores credit before any later receive callback can pause again. When cached callbacks are pending, they run first, but a callback's nested pause does not remove the outer function's subsequent connection-unpause notification. Neither path justifies claiming that pausing after each accepted chunk prevents window expansion. This source observation is not a measured allocation bound or a claim that the public pause API is generally broken.

There is an additional bounded-queue trap: directly pausing reception does not set `data->req.writer.paused`, whereas returning `CURL_WRITEFUNC_PAUSE` does ([cw-out.c 196–207](https://github.com/curl/curl/blob/curl-8_22_0/lib/cw-out.c#L196)). The current output-delivery loop tests that writer flag ([253 onward](https://github.com/curl/curl/blob/curl-8_22_0/lib/cw-out.c#L253)). Do not assume one accepted callback plus an explicit pause is the last callback in the current flush. Every callback must still check space and return PAUSE without accepting bytes when full. The supported nested call is not intrinsically forbidden recursion, but unpause is synchronously reentrant into application callbacks; unconditional recursive unpause, stale queue state or assuming no subsequent callback would be unsafe. No new threading design follows from these facts.

## Follow-up: two cached TLS tickets per peer

[8.22.0 multi.c 300](https://github.com/curl/curl/blob/curl-8_22_0/lib/multi.c#L300) creates the multi TLS session cache with `max_sessions_per_peer = 2`. [vtls_scache.c 903–916](https://github.com/curl/curl/blob/curl-8_22_0/lib/vtls/vtls_scache.c#L903) appends TLS 1.3 sessions and removes oldest entries above this count; non-TLS-1.3 sessions instead replace the list. [1010–1044](https://github.com/curl/curl/blob/curl-8_22_0/lib/vtls/vtls_scache.c#L1010) takes a session out of the peer list when a connection requests one. Thus a burst starting many reconnects before replacement tickets arrive can consume its two retained tickets immediately, leaving the other reconnects without cached sessions. This is consistent with two observed resumed handshakes per peer despite many concurrent reconnects. It is not a universal two-resumptions-per-burst ceiling: later handshakes/tickets can replenish the cache during a differently timed burst. Confirm negotiated TLS version and accepted resumption in fixture records; do not attribute the exact measured count solely to OpenSSL's server ticket defaults.
