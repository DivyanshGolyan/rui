# CLI mode, approval and reconnect evidence

Inspected 2026-09-25 as input to Rui's explicit interactive and one-shot CLI modes. This supplements [the clig.dev comparison](cli-guidelines-rui.md), not its help/output/prompt recommendations. [Architecture](../ARCHITECTURE.md#inspection-and-local-protocol) owns Rui's accepted behavior; these mutable product docs describe other tools, not Rui requirements or tested runtime behavior.

| New primary-source product pattern | Transfer to Rui (inference, not a source mandate) |
| --- | --- |
| [Codex's non-interactive guide](https://learn.chatgpt.com/docs/non-interactive-mode) explicitly invokes `codex exec` for scripts rather than opening its TUI. Its [command reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli) names `codex` as interactive and `codex exec` as non-interactive, with separate `codex resume` and `codex exec resume [SESSION_ID]`. The guide sends progress to stderr and the final message to stdout, with opt-in JSONL events. | Make any guided human surface an **explicit invocation**, not a TTY-detected change to the meaning of Rui's one-shot commands. Keep programmatic output/exit semantics stable when redirected; Rui's Markdown/JSON and selected-data rules remain its own contract. A separate interactive loop is precedent, not a need for a TUI or for changing the one-shot model. |
| [Codex's automation safety section](https://learn.chatgpt.com/docs/non-interactive-mode#permissions-and-safety) documents a read-only `exec` default and explicit sandbox escalation. [Claude Code headless](https://code.claude.com/docs/en/headless#turn-off-permission-prompts-in-unattended-runs) documents `--permission-prompts none`: after other permission rules, unanswered requests are denied rather than waiting for a nonexistent human; a separate permission host can answer if enabled. | Surface Rui's ask/bypass policy explicitly in unattended examples; do not silently convert `ask` to bypass merely because there is no TTY. Rui instead durably retains unanswered exact Permission Requests under Host/core authority for another client, so neither tool's non-interactive denial/read-only behavior is a drop-in policy. A human view must show the exact Action ID and arguments; a separate explicit decision must still pass Host validation at decision time, including if the request became stale. |
| [Codex's exec resume](https://learn.chatgpt.com/docs/non-interactive-mode#resume-a-non-interactive-session) can select a previous conversation by ID or `--last` to continue a pipeline; [Claude Code headless](https://code.claude.com/docs/en/headless#continue-conversations) captures `.session_id` in JSON and resumes with an explicit ID. [Claude's session documentation](https://code.claude.com/docs/en/sessions#resume-a-session) distinguishes finished background sessions from still-running ones. | Distinguish *finding a saved Session* from *recovering the original request acknowledgement*, *observing its present result*, and *submitting new work*. An idle Rui Session wait returns idle immediately; `follow` remains bound to the original saved message even if another Turn starts. A fresh client may inspect the same full Session reference and enumerate caller records without starting the Host or sending a message. Prefer exact saved identity over `--last` in recovery instructions. Resuming a competitor's conversation is not evidence of idempotent replay, durable pending approval, or idle observation. |

**Boundary:** These are product patterns, not a normative UX study. The existing [clig.dev note](cli-guidelines-rui.md) already covers general output, prompts, errors, flags and composability, and [permission prior art](permission-prior-art.md) already compares approval ownership/reconnect implementations. No primary source above demonstrates Rui's capture-before-send, Host-restart or uncertain-effect guarantees; evaluate those against Rui's own [wait and result contract](../ARCHITECTURE.md#work-state-and-wait-conditions) and [verification cases](../VERIFICATION.md#inspection-and-waits).
