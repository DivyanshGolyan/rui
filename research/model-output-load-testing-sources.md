# Model-output load qualification: external evidence

Researched 2026-09-15. This is an evidence note with unaccepted recommendations, not a specification or a change to fixture thresholds. No benchmark was run. The owning contracts remain [ARCHITECTURE.md](../ARCHITECTURE.md#resources-storage-and-diagnostics) and [VERIFICATION.md](../VERIFICATION.md#resources-and-accepted-host-qualification-targets).

## Question and local boundary

The reported fixture runs 1,000 concurrent SSE streams at 100 events/second each for 60 seconds: exactly 6,000,000 events, emitted as two events every 20 ms. It rejects a run if any stream has an inter-batch gap above 40 ms or more than two batches in a rolling 20 ms window. A reported 48.65 ms gap can therefore reject otherwise complete work. These fixture details and the example gap are task inputs, not independently reproduced measurements.

The root checkout's resource sections specify the stream population/rate and average CPU target, plus useful capture throughput, achieved delivery rate, framing/batching variation and memory observations. The implementation worktree at `/Users/divyanshgolyan/.codex/worktrees/1e5b/latifa` separately contains the newly committed bounded-delivery-v1 contract, including the 40 ms gap rule. This research questions the justification for that rule; it does not override it. Exact completion alone cannot establish that the intended concurrent load reached the runtime.

## Primary-source findings

| Source | What it establishes | Applicability and limit |
| --- | --- | --- |
| [Grafana k6: constant arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/) | Schedules iteration starts independently of system response, at a configured rate per time unit; starts are fractionally spaced. | Supports preserving an intended offer schedule. HTTP iteration starts are different from events within existing SSE responses; this is a measurement principle, not a drop-in server fixture. |
| [Grafana k6: dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/) | Unstarted work can reflect insufficient generator configuration or degrading system performance. Acceptable dropped-work budgets are test decisions. | A missed schedule does not identify its cause. For this exact-work fixture, permitting dropped events would change the workload; tracking delay does not require dropping work. |
| [Grafana k6: running large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/#hardware-considerations) | Generator CPU, memory and network constraints can distort results; monitor these resources and retain headroom. | Supports observing the fixture separately, including contention when it shares the runtime's machine. k6's suggested headroom percentages are guidance for k6, not evidence for a Latifa threshold. |
| [wrk2 README](https://github.com/giltene/wrk2#readme) | Measures latency from intended transmission time, preserving delay that response-dependent sending can hide; documents roughly millisecond timing granularity from OS sleeps. | Supports recording intended versus actual progress rather than silently resetting the schedule after a stall. Its HTTP request/response latency model does not directly define SSE event delivery latency. Its timing observation neither excuses a 48.65 ms stall nor prescribes a maximum gap. |
| [OpenMessaging Benchmark: interpreting results](https://openmessaging.cloud/docs/benchmarks/#interpreting-the-results) | Reports publish/consume rates and backlog in 10-second windows, latency distributions, and production delay relative to ideal throughput. Large or increasing production delay indicates inability to achieve configured throughput. | Direct precedent for assessing sustained messaging load using achieved rates, delay and backlog together. Ten seconds is this tool's reporting interval, not a justified Latifa acceptance window. Historical documentation notes latency/delay values above 60 seconds are not captured. |
| [Google Benchmark: CPU timers](https://google.github.io/benchmark/user_guide.html#cpu-timers) | Distinguishes wall-clock time from total process CPU time across threads and supports reporting both. | Supports keeping elapsed time and CPU work distinct. It is a microbenchmark library, not authority for Latifa's workload or multi-process accounting boundary. |

None of these sources establishes a universal maximum inter-batch gap of 40 ms, or any substitute numerical cutoff. This limited survey does not prove that such a bound can never be useful: a bound needs a consumer requirement or evidence that larger gaps materially alter the resource workload.

## Interpretation for this fixture

The strongest source-supported direction is to judge delivered load using predeclared, workload-relevant windows, while retaining scheduling-delay/backlog and per-stream coverage evidence. An aggregate average across the whole run can hide an idle interval followed by a catch-up burst, or starving some streams while others compensate. The window length, allowed deficit and burst envelope need an explicit rationale; importing OpenMessaging's 10-second interval would just replace one unsupported choice with another.

Keep the intended schedule independent of runtime progress. Distinguish a delayed generator wakeup from a blocked send and from runtime capture lag wherever existing evidence allows. Socket acceptance alone does not prove application consumption. A runtime-induced slowdown is evidence about runtime capacity; calling every delayed send an invalid generator would discard that evidence. Conversely, generator saturation can make runtime capacity inconclusive. The sources justify this attribution distinction, not a claim that the reported gap was harmless.

Preserve the evidence a run actually earned. Correctly processing six million events can support fixed-work CPU cost and measured memory footprint for that execution even when its load shape misses qualification. Let `C` be aggregate runtime CPU seconds and `T` the matching elapsed interval: `C / 6,000,000` is observed CPU seconds/event, and `C / T` is observed average cores. Multiplying the former by 100,000 events/second is only a rate-normalized estimate; changed batching, waits, contention and concurrency can change cost. It cannot establish the accepted average-core target at a load that was not delivered. Likewise, a measured lifetime memory peak does not establish memory qualification under a different arrival shape or required churn.

Accordingly, research supports reviewing the 40 ms rule's purpose before retaining or replacing it. It does not support simply raising the cutoff, deleting cadence evidence, accepting completion totals as sustained-rate proof, or rerunning until an unexplained maximum happens to pass. Any accepted change belongs in the owning verification contract with its proof; this note changes neither.
