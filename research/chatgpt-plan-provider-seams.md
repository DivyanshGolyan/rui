# ChatGPT plan sign-in: Rui provider and replay seams

Research only; base `1cf38900a71d771f37c596d1f24e08b40b682f86`. References below are repository paths and line numbers at that commit, not evidence of current external service guarantees. No live sign-in, credential inspection, inference, or runtime qualification was performed. Official registration, access and concurrency guarantees belong to **Verify the official ChatGPT plan contract and concurrent VM credential limits** (#1031).

## Existing repository facts

### Identity, routing and UX

- Rui owns its Codex credential file, configurable via `RUI_CODEX_CREDENTIAL_FILE` (`src/cli.zig:319-327`); it does not fall back to the Codex CLI file (`ARCHITECTURE.md:1030-1036`). Nevertheless its device flow uses the pinned Codex OAuth client and endpoints (`src/codex_token_wire.zig:11-18,63-81`; `src/codex_auth.zig:352-393`), not a demonstrated Rui registration.
- `codex` routes to the ChatGPT Codex backend, `openai` to the API-key Responses endpoint (`src/providers.zig:17-19,57-95`). Sign-in headers are restricted to the managed endpoint except fixtures, while key authentication has separate headers (`src/providers.zig:221-262`). `RUI_OPENAI_BASE_URL` is for the key route, not an authorization to send sign-in tokens elsewhere.
- CLI login for Codex is a device flow; OpenAI takes a key. Publication precedes the success receipt; guided versus explicit login differ in default selection (`src/cli.zig:868-875,908-949`). Local readiness is not remote entitlement (`src/cli.zig:406-435`). Selection is explicit, then saved, then sole locally usable provider; unavailable choices do not silently fall back (`src/provider_selection.zig:35-78`). Host auto-start and serving are separate from selection (`src/cli.zig:734-774`; `docs/host.md:63-74`). Fresh peer Sessions default to Codex and Bash plus web search (`src/product_defaults.zig:21-33`).
- Saved Sessions reject changes to **both provider and model** (`src/store/domain/configuration.zig:245-252`); the selected provider supplies the codec and the version is pinned (`src/provider_name.zig:12-15,91-95`). Defaults do not rebind history. A new login acquisition method is not necessarily a new persisted route, but a distinct replay domain cannot be assumed equivalent merely because it is called ChatGPT.

### Credential lifetime and concurrency

- Credential leases hold immutable records under shared locks and wipe on release; installs take an exclusive lock and check generations (`src/codex_credentials.zig:24-48,76-103`). Refresh holds a stable exclusive lock from durable `refresh_pending` through exchange and publication. Only a positively not-sent exchange returns to ready; an uncertain/sent exchange or claimant crash leaves pending and needs explicit login (`src/codex_credentials.zig:105-130`; `ARCHITECTURE.md:1048-1076`). Refresh checks account and routing continuity; explicit login can replace ownership (`src/codex_token_wire.zig:302-390`).
- Dispatch checks expiry, releases a lease to refresh and reacquires before launch (`src/codex_auth.zig:45-79`; `src/codex_credential_policy.zig:18-24`). Only an answered model 401 can request a forced refresh (`src/execution.zig:95-109`), and the Operation durably claims its one forced refresh before exchange (`src/store/Store.zig:1358-1372`).
- This locking coordinates users of the **same** lock and credential file; independent copied files on remote VMs do not share that lock or generation. Portability alone cannot establish safe concurrent refresh, replacement, revocation or recovery. The requested workflow is one human authorization, a protected cloud-project bundle and scripted bootstrap of many concurrent ephemeral thread VMs without per-VM approval; it remains a requirement, not a proven property.
- Multiplicity is constrained: `onlyWith(.sign_in)` requires uniqueness (`src/provider_name.zig:49-68,104-107`); `leasedSignIn` returns the first such source (`src/providers.zig:314-321`); execution creates one Host auth worker (`src/server_execution.zig:429-435`). Adding a second refreshable credential owner requires reviewing all three and job identity, shutdown and resource ownership.

### Wire, tools, discovery and recovery

- Both current providers select `openai-responses/2` (`src/provider_name.zig:34-46`). The request asks for streaming, parallel tools, no storage and encrypted reasoning (`src/codecs/responses.zig:451`); /2 additionally emits `configuration_update`, historical `additional_tools`, and `compaction_trigger` (`src/codecs/responses.zig:163-193`). Replay preserves provider bags and encrypted continuation, omitting private reasoning text (`src/codecs/responses.zig:91-153`; `ARCHITECTURE.md:980-1014`). Same codec name is not evidence another route accepts or can decrypt this history.
- Hosted web search is advertised for both routes and enabled by default; its wire declaration requests live external access (`src/provider_name.zig:34-45`; `src/product_defaults.zig:21-22`; `src/codecs/responses.zig:203-208`). Hosted search calls are replayed without local Actions; unfamiliar hosted effects are rejected (`ARCHITECTURE.md:998-1003`; `src/output_decode.zig:1104-1120`). Completion checks streamed items against nonempty terminal output (`src/output_decode.zig:775-806`); streaming is not itself proof of a compatible end-to-end route.
- ChatGPT models use the shipped catalog, while the key route can fetch a startup live list (`src/provider_name.zig:44`; `src/model_catalog.zig:1-45`; `src/providers.zig:331-336`). Catalog membership proves neither entitlement nor replay compatibility. The Codex-specific compaction trigger is a local default, not a public-route guarantee (`src/product_defaults.zig:41-45`). Structured output is currently rejected for ChatGPT (`src/providers.zig:51-55`).
- Raw usage and optional token counts are response evidence (`src/output_decode.zig:807-816`); the codec maps input minus cached to uncached, cached to cache read, zero cache write, and output to output (`src/codecs/responses.zig:1560-1580`). These counts are not plan balance or billing evidence. Retry and refusal handling distinguish transient failures from quota/plan/policy/model failures (`src/retry_policy.zig:4-7,28-53`; `src/model_adapter.zig:51-115`; `src/transport_policy.zig:59-106`); advice mentioning credit needs a plan-specific audit (`src/session_view.zig:1412,1511`). No silent paid-key fallback.
- Recovery authority is canonical Store state and pinned replay/binding, not diagnostic capture (`ARCHITECTURE.md:1572-1582`; `src/failed_responses.zig:1-20`). Existing fixture coverage is synthetic and explicitly does not qualify live refresh, cross-Host process crashes, or real backend routing (`VERIFICATION.md:495-499`); the README names the narrower live journey (`tests/qualification/README.md:7`).

## Independent design opinion — proposals, not decisions

1. Model headed and headless authorization as explicit acquisition methods. If official authority and replay identity are truly the same, they can share one owner; if route or continuation authority differs, give it a distinct persisted route/codec identity. Do not infer equivalence from UI or token shape.
2. Use explicit typed credential ownership and route authority, restricted to documented issuer, audience, scopes and target hosts. Keep authentication failures distinct from model failures and never route sign-in credentials to arbitrary endpoints. Multiplex typed owners in one worker or use bounded owner-specific workers only after evaluating lifecycle; methods sharing one owner do not inherently require multiple workers.
3. Evaluate a coordinated shared refresh/publication owner versus officially supported independent grants as alternatives, including partition, uncertain exchange, owner death and secret replacement. This is not a choice of cloud ownership model. No existing local lock proves cross-VM coordination.
4. Preserve immutable bindings and surface explicit failures. Retention, migration, old-route availability, default selection and capability tradeoffs are human decisions; no silent history rewrite, dropped encrypted reasoning, or billing switch.

## Proposed compatibility acceptance gates

- **Official authority:** #1031 must establish whether a Rui-owned registration, headed/headless methods, plan eligibility, scopes, refresh/revocation, concurrency and charging are actually supported. Neither Codex client reuse nor a copied token is a substitute.
- **Wire and replay:** demonstrate the full /2 grammar, local parallel tool calls/results, IDs, provider bags, encrypted continuation, effort changes, long-session compaction, restart and explicit rejection of incompatible saved history. Test public-route compatibility separately from fixture serialization.
- **Capabilities:** verify hosted live web search and citation replay, model and effort availability, context limits, compaction and usage semantics under the actual plan; explicitly disclose unsupported defaults rather than silently degrading. Do not call current absence of ChatGPT structured output a new regression.
- **Lifecycle and operations:** exercise both authorization modes; protect secrets and suppress login payloads in diagnostics; cover multiple credential owners, lease lifetime, generations, uncertain refresh, logout/replacement, 401, rate/entitlement errors, Host restart and concurrent VM bootstrap without per-VM approval. Establish what happens under network partitions and crash cuts; prove no automatic billable fallback.
- **Transport and recovery:** test SSE ordering, terminal agreement, HTTP/2, cancellation, endpoint/header restrictions, bounded diagnostics and Store recovery; preserve unknown tool outcomes instead of repeating side effects. The existing fixtures (`tests/integration/codex_credential_integration.py:18-117`, `tests/integration/codex_h2_integration.py:45,201,327,375`, `tests/integration/codex_integration.py:109,496,586,711`) provide starting seams, not live proof.

## Unknowns and limits

Official app registration and entitlement, supported authorization methods, concurrent refresh/VM policy, public-route grammar and replay interoperability, capability parity, and plan allowance/billing semantics are unresolved. This repository investigation cannot decide them. No migration/default/retention or cloud ownership policy was selected. No production code, credentials, live login or inference was touched.
