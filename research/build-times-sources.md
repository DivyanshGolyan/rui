# Zig 0.16 development build latency: source-backed options

Research note, initially 2026-09-23. Scope: Zig **0.16.0**, `build.zig`, `src/build_transport.sh`, and the [canonical gates](../VERIFICATION.md#canonical-gates). The original source-backed options and timings below remain historical evidence, not measured compiler/cache improvements. The [first gate comparison](#routine-versus-long-qualification-2026-09-29) measures separation of long witnesses; the [verification-design follow-up](#owner-boundaries-instead-of-elapsed-holds-2026-09-29) measures explicit synchronization and narrower duplicate artifact coverage.

## Graph at the original measurement

- `zig build` installs a Rui CLI built with the standard `-Doptimize` option (Debug by default) and notices. `zig build test` compiles/runs `src/tests.zig` in **ReleaseSafe**, including SQLite, Bash platform C and transport; `test-logic` compiles/runs `src/logic_tests.zig` in ReleaseSafe without those native attachments. `-Dtest-filter=...` filters tests but is not a way to compile only the selected source declarations. The [Zig build guide's test section](https://ziglang.org/learn/build-system/#testing) distinguishes compiling from running a test artifact; [build modes](https://ziglang.org/documentation/0.16.0/#Build-Mode) explain the optimization/safety tradeoff.
- `check` builds the ReleaseSafe and Debug CLIs, ReleaseSafe tests, a ReleaseSmall CLI, formatting, then process integrations; it is not a cheap compilation-only check. The named admission/dispatch/Bash/control steps use a ReleaseSafe CLI. `cross-check-linux` and `cross-check-macos` build ReleaseSmall CLIs for two architectures each; the macOS transport script requires Apple's SDK. These steps are different evidence, not redundant runs of the default Debug artifact. [Local graph](../build.zig), [gate contract](../VERIFICATION.md#canonical-gates).
- Each CLI and the main `test` compilation attaches `sqlite3.c` with the same C flags and macros and `bash_platform.c`; `test-logic` does not. The qualification SQLite shell adds `shell.c`. The CLI names, targets and optimization modes differ. The pinned transport command builds static OpenSSL/curl once per selected target *step* and supplies its generated include/lib directory to the compile steps; it invokes `make -j4` twice. Cross targets have separate transport outputs. [Build configuration](../build.zig), [shell recipe](../src/build_transport.sh).

## Supported controls and important limits

| Control / mechanism | Source-backed behavior | Applicability and caveat for Rui |
| --- | --- | --- |
| Reuse local `.zig-cache` and dependency caches | The [official build guide](https://ziglang.org/learn/build-system/#installing-artifacts) describes `.zig-cache` as rebuild acceleration. Zig 0.16 [release notes](https://ziglang.org/download/0.16.0/release-notes.html#Fetch-Packages-Into-Project-Local-Directory) specify that fetched packages live in `zig-pkg`, with canonical compressed copies in the global cache. `zig build --help` offers `--cache-dir`, `--global-cache-dir`, and `--fetch=needed\|all`. | Keep caches between ordinary iterations. Do **not** equate a warm local build with the required clean export/empty-cache build; the [verification recipe](../VERIFICATION.md#canonical-gates) explicitly excludes `zig-pkg`, uses fresh local/global caches, prefetches pinned OpenSSL and then fetches the full graph. `--fetch=all` fetches rather than benchmarking compilation. |
| Run a narrow existing step | The [official build guide](https://ziglang.org/learn/build-system/#installing-artifacts) models a DAG of independently runnable/concurrent steps, and its [test section](https://ziglang.org/learn/build-system/#testing) separates compilation from execution. | During edits use `test-logic` for portable owner/turn logic or a named filtered/native/integration gate as appropriate; retain `check` and cross gates for the evidence their contract requires. A narrower step does not prove the larger gate. Selecting a step does not imply the entire `build.zig` graph is never constructed. |
| `--summary all`, `--verbose`, `--time-report` | The [0.16 build guide's CLI help](https://ziglang.org/learn/build-system/#user-options) documents build summaries, verbosity, and `--time-report`: it **forces a full rebuild** and reports Zig-source compilation time (also enabling the web UI). | Compare cold and warm `--summary all` step durations/cache status first; `--verbose` identifies actual commands. Use `--time-report` only for uncached compiler attribution, not to measure normal incremental edits, shell transport or process-integration costs. Record toolchain, target, selected step, cache state and repeated wall time. |
| `-jN`, `--maxrss` | Both are documented in the [0.16 build CLI help](https://ziglang.org/learn/build-system/#user-options) as concurrent-job and memory limits, not optimizer flags. | Try bounded `-jN` if concurrent compiler/link jobs compete for RAM; Rui's transport script separately runs `make -j4`, so Zig's `-j` alone does not cap all subprocess parallelism. `--skip-oom-steps` skips work rather than proving a gate passed. Neither flag guarantees faster builds. |
| `-fincremental --watch` | [Zig 0.16 release notes](https://ziglang.org/download/0.16.0/release-notes.html#Incremental-Compilation) say incremental compilation works with LLVM but does not speed LLVM's **emit-object** phase; it is experimental, has known miscompilations, and is **off by default**. They suggest `zig build -fincremental --watch`. `--watch` and `--debounce` appear in [build help](https://ziglang.org/learn/build-system/#user-options). | Plausible local edit/compile-feedback experiment, especially for Zig logic changes; not a qualification substitute. Compare with ordinary builds, rerun non-incremental gates on the exact revision, and watch for failures/miscompilations. It cannot be assumed to accelerate SQLite C compilation, the OpenSSL/curl shell builds, ReleaseSafe LLVM object emission or integrations. |
| Optimization setting | [Zig's 0.16 build modes](https://ziglang.org/documentation/0.16.0/#Build-Mode) define Debug, ReleaseSafe and ReleaseSmall; [standard build options](https://ziglang.org/learn/build-system/#standard-options) explain `-Doptimize`. | `-Doptimize=Debug` affects the default CLI, **not** Rui's hard-coded ReleaseSafe tests/CLIs or ReleaseSmall cross builds. Do not silently replace these modes with Debug to make verification faster: it changes the validated artifact and safety/optimization behavior. |

### The external-command cache boundary

The [0.16 `Run` implementation](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L707-L728) treats a command with an output argument and no other side effects as cacheable. `addFileArg` tracks the script file; `addOutputDirectoryArg` provides the generated tree. But [`addDirectoryArg`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L461-L480) establishes a step dependency and [`Run.make`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L816-L850) hashes the directory **path**, not every file read under it; extra file inputs can be declared with [`addFileInput`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L700-L706). Rui's `addPinnedTransport` uses package directory args for the OpenSSL/curl source trees. Thus a warm cached transport result is useful, but do **not** assume an edited file in `zig-pkg` necessarily invalidates this shell step. Its script also discovers tools/Apple SDK and uses ambient shell environment: investigate those inputs before claiming reproducibility or sharing caches. The package pins and clean-build gate remain the authoritative baseline. This is a source-based cache-key caveat, **not** an observed stale-build incident.

Similarly, Zig's [`Compile.make`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Compile.zig#L1470-L1480) passes local/global cache directories to the compiler, and [`addCSourceFile`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Module.zig) declares SQLite C input/flags. Cache reuse across different named executables, targets and optimization modes must be *measured*, not inferred from their common `sqlite3.c` path. Altering SQLite macros, source provenance or link arrangement to share an object is a separate build/behavior change requiring clean builds and relevant gates; no speedup is established by this note.

## Low-risk measurement order (not an implementation plan)

1. For the *same* revision/toolchain/target, capture ordinary warm `zig build test-logic --summary all`, `zig build test --summary all`, `zig build --summary all`, and the relevant `check`/cross gate summaries; record each step's cached/uncached state and wall time. Change one Zig source file in a disposable working copy to compare edit rebuilds (do not use a cache deletion as a stand-in for an ordinary edit). Attribute native/shell and process-test wall time separately. Never report an unrun gate as passed.
2. Only if compiler time dominates, compare a local `-fincremental --watch` edit loop to the normal loop; only if native compilation dominates, inspect `--verbose` and the generated step durations. Keep target/optimization and cache state comparable. Do not treat an official Zig compiler benchmark or a different project's build time as Rui's measured gain.
3. Preserve the required non-incremental clean-cache and platform checks before changing build graph or dependency handling. macOS runtime/SDK qualification still needs macOS; Linux cross compilation cannot establish native macOS behavior. [Canonical gates](../VERIFICATION.md#canonical-gates).

## Local observations (not edit-rebuild or clean-cache qualification)

Measured sequentially on 2026-09-23 at Git revision [`8a5a74a`](https://github.com/DivyanshGolyan/rui/commit/8a5a74ac953b775f55a308c19ff394431b052f99) in the Linux x86-64 orb (4 reported CPUs, 7.8 GiB RAM), Zig 0.16.0, with existing `zig-pkg` and partially populated `.zig-cache`; commands used `/usr/bin/time -f 'wall=%e user=%U system=%S maxrss_kb=%M' zig build <step> --summary all`. The working tree was clean at the start; the research note became untracked (dirty) during later runs, but no tracked source/build inputs changed. This is neither a clean source export nor a changed-source incremental benchmark. Step times printed by Zig are rounded and overlapping steps are not additive.

| Command in run order | Wall | Decisive summary |
| --- | ---: | --- |
| `test-logic` | 25.95 s | 58/58 passed; ReleaseSafe compile 25 s, run 337 ms |
| `test-logic` again | 0.37 s | 58/58 passed; compile cached 10 ms, run 308 ms |
| `test-logic -Dtest-filter='request encoding'` | 18.89 s | 13/13 passed; distinct filtered ReleaseSafe compile 18 s, run 296 ms |
| `test` | 330.25 s | 245/245 passed; pinned transport 1 m, ReleaseSafe test compile 2 m, test run 1 m |
| `zig build` (default install) | 11.51 s | Debug CLI compile 11 s; transport cached |
| `test` again | 69.29 s | 245/245 passed; compile cached 19 ms, run 1 m |

These numbers show why a filtered test can cost a new compilation on first use, and why caching does not eliminate the full test's execution time. They do **not** show that changing SQLite linkage, transport `make -j4`, optimize mode or Zig's incremental mode improves latency. For a fair proposed speedup, compare repeated source edits and the same gates on this machine, and separately run the required clean-cache verification.

## Routine versus long qualification, 2026-09-29

Linux x86-64 orb, four reported CPUs, Zig 0.16.0. Baseline: [`ffc5eb7`](https://github.com/DivyanshGolyan/rui/commit/ffc5eb76852f62466123bd4a79339b6fa30ef652). Candidate: [`277f120`](https://github.com/DivyanshGolyan/rui/commit/277f120), with identical production sources and compiler modes. Commands used `/usr/bin/time -f 'wall=%e user=%U system=%S maxrss_kb=%M' zig build STEP --summary all`, serially, without concurrent builds or qualification workloads. Only documentation changed during baseline measurements; the candidate was initially uncommitted and then committed while its gate ran, without changing build/test inputs.

An initial baseline `check-full` passed in **608.66 s**, including uncached transport/compilation work; this is not the warm comparison. A missing QuickJS download first failed with Zig `ResolvConfParseFailed`; downloading the pinned archive with curl and verifying its `zig fetch` hash resolved the environment issue. No runtime/test failure was hidden by that retry.

| Warm command | Baseline wall | Candidate wall | Evidence |
| --- | ---: | ---: | --- |
| `zig build check-full --summary all` | 350.58 s | 277.54 s | Both 22/22 steps; baseline 278/278 native tests, candidate 277/278 with the exact-duration witness explicitly skipped |
| `zig build check --summary all` | 122.58 s | 111.52 s | Both 19/19 steps and 277/278 native tests, one explicit skip; all scheduled process suites passed |
| `zig build test-full --summary all` | — | 71.36 s | 278/278 native tests, including the production-duration witness |
| `zig build evaluator-churn --summary all` | — | 10.78 s | 5/5 steps; 1,000 real same-parent evaluations, exact output and descriptor balance after each cycle |

Warm compiles were cached. Before the candidate comparison, `workflow-check` rebuilt the build graph and changed C fixture (120 ms compilation) and passed in 18.07 s total; its Python boundary suite took 16 s versus 26 s in the warm baseline. Full native execution fell from roughly 71 s to 10 s by moving, not shortening, the 61-second witness. The serial process-integration step still took about four minutes in both builds. These are single observations, not medians or a production-source edit/rebuild benchmark: **73.04 s (20.8%)** less for serial `check-full`, **11.06 s (9.0%)** less for parallel `check`. They do not establish faster compilation. Using the candidate `check` rather than the old `check-full` at routine checkpoints reduces this observed wait by about 68%, while deliberately deferring sanitizer/isolated-latency and long-witness evidence to the documented cadence.

An independent synthetic child counted exactly 10 invocations for `repeat` and 1,000 for `churn`. It emitted framed `5` except for `6` on its second invocation: the candidate driver returned status 8 at cycle two. A disposable mutation checking output only on the final cycle instead returned success and final `5`, demonstrating that the new per-cycle oracle catches corruption that a final-result-only check misses. This is fixture-oracle evidence, not evaluator performance. Existing owner failure/cancellation/cleanup/reuse cases remain unchanged.

An exact `git archive` export of the candidate, checked against a manifest of every tracked source file, built with initially empty local/global Zig caches and no `zig-pkg`. Fresh curl downloads were hash-verified with `zig fetch` (OpenSSL first), then the complete graph passed `--fetch=all`; `zig build --summary all` passed 9/9 steps in 117.15 s excluding downloads/fetching. This verifies a clean native build, not Zig's network downloader or a cold full-suite run. A disposable UX-stack snapshot at [`9ac523a`](https://github.com/DivyanshGolyan/rui/commit/9ac523aa4b03638fc0cb2ab2de11ee62db372295) accepted the patch via `git apply --3way`; its `workflow-check` (6/6 steps) and `evaluator-churn` (5/5) passed. This is compatibility evidence for the changed evaluator/build boundary, not a new full-stack qualification or evidence for subsequent stack rebases.

The [raw logs, timings, source hashes and reproduction fixtures](../tests/qualification/build-feedback-linux-2026-09-29.tar.gz) retain these runs and the clean-cache bootstrap commands (archive SHA-256 `c403eecbf6964172698257bc5c5a167d8fb38fb2e6b578d44b4d1037a216ae4a`). For the synthetic oracle, initialize `/tmp/rui-repeat-counter` to `0`, make the archived fake child executable, and run the driver with that child, the archived source, `repeat` or `churn`, and budget `1000000`. Creating `/tmp/rui-repeat-corrupt` selects the bad second result. The negative-control mutation adds `&& i + 1 == repeat` to the driver's per-cycle output-check condition; use a disposable copy, never the qualification binary. Build logs can label expected injected-error stderr as a warning with `failed command`; the final exit status and build/test summaries above distinguish that diagnostic text from an actual failed gate.

No macOS runner was connected. Earlier 86–90-second Mac churn observations motivate the separate 300-second harness timeout, but are not measurements of this revision. Runtime child CPU/lifetime limits are unchanged; the longer harness timeout is not a throughput guarantee.

## Owner boundaries instead of elapsed holds, 2026-09-29

The follow-up candidate is [`7e2b0ea`](https://github.com/DivyanshGolyan/rui/commit/7e2b0eae631d795f17179410531b0c9fa7f899dc), on the same Linux x86-64 orb and Zig 0.16.0. Final commands ran sequentially with no competing builds or test workloads. The source was committed during the first rebuild run without changing its build/test inputs; the following warm runs used cached compiles. These are single observations, not medians or a compilation-speedup claim.

| Warm gate | Original baseline | First pass | Final candidate | Reduction from original |
| --- | ---: | ---: | ---: | ---: |
| `zig build check --summary all` | 122.58 s | 111.52 s | **78.12 s** | **36.3%** |
| `zig build check-full --summary all` | 350.58 s | 277.54 s | **172.64 s** | **50.8%** |

Both final gates passed: `check` 19/19 steps, `check-full` 22/22 steps; 278 native tests passed with the one documented exact-duration skip (279 total). The retained complete `zig build admission-debug-integration --summary all` passed 5/5 steps in 22.62 s. The earlier final-source `check-full` took 236.21 s with native-test/Debug/ReleaseSmall recompilation, after ReleaseSafe had already rebuilt for a focused check; it is neither a warm comparison nor an empty-cache build. Relative to the first pass, the new reductions are 30.0% and 37.8%, not another 50%. Dispatch remains the parallel critical path; reducing shorter suites cannot alone halve `check`.

Profiling located repeated artificial waiting: approximately 57 s in control, 30 s in the Bash journey, 39 s in Bash lifecycle and 67 s in dispatch. Intermediate focused runs reduced control to 18 s and the Bash journey to 17 s by holding exact boundaries until the fixture's assertion completed, rather than waiting out fixed multi-second delays. The final human CLI fixture took 11.40 s versus a prior profiled 19.25 s, retaining all four incomplete-input timeouts concurrently. These explanatory fixture observations have different instrumentation/cache conditions and are not additional whole-gate benchmarks.

The [verification contract](../VERIFICATION.md#canonical-gates) owns the replacement evidence: explicit sealed-result/cleanup/inspection gates; a supplied-time Bash phase/deadline matrix plus one real escaped-writer cutoff and all distinct native fault/recovery paths; one transport inactivity-to-retry witness alongside separate exhaustion/progress tests; and a Debug artifact/recovery smoke alongside the full ReleaseSafe matrix. This removes duplicate elapsed-time combinations, not the runtime custody, recovery, control-capacity or deadline guarantees. It deliberately stops testing every admission failure in both build modes at every routine checkpoint; the complete Debug step remains required for affected changes and release qualification. Exact-duration and cumulative-leak evidence still need their separate long witnesses.

The first intermediate serial gate passed in 222.16 s, but its parallel gate failed at marked-paste rejection: printed Action text preceded the editor's input flush, so fresh fixture input could be discarded. The final fixture waits on a borrowed readiness descriptor signaled after drain/flush; typeahead still arrives before readiness. Another review found that unlinking a FIFO and closing its last writer could strand a blocking late opener. The native gate now opens nonblocking, restores blocking reads, and treats the released no-writer handle as EOF. A controlled no-writer scenario timed out at the intended terminal-result assertion on the old binary and passed on the corrected one. An initial missing Python import failed setup and is recorded separately, not counted as the counterexample. The Bash deadline test also went red when `>=` became `>` at the exact-deadline closure assertion, then passed after restoration.

The [follow-up raw evidence](../tests/qualification/build-feedback-design-linux-2026-09-29.tar.gz) contains final/intermediate/failing logs, profiling script, FIFO reproduction probe, candidate source/binary hashes and commands (SHA-256 `9e71af3c68091d5e8e99f3875668f24fb715021dded6f765f5da9920dc1039db`). Independent read-only review assessed the evidence substitutions and the synchronization corrections. No macOS runtime or full UX-stack requalification was performed for this follow-up. The first-pass archive above owns the earlier empty-cache, 61-second and 1,000-cycle observations; they were not rerun on this candidate and are not claimed as final-revision results. Production timeout defaults, compiler modes, release resource targets and accepted failure/recovery behavior remain unchanged.
