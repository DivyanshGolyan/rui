# Zig 0.16 development build latency: source-backed options

Research note, initially 2026-09-23. Scope: Zig **0.16.0**, `build.zig`, `src/build_transport.sh`, and the [canonical gates](../VERIFICATION.md#canonical-gates). The original source-backed options and timings below remain historical evidence, not measured compiler/cache improvements. The [first gate comparison](#routine-versus-long-qualification-2026-09-29) measures separation of long witnesses; the [verification-design follow-up](#owner-boundaries-instead-of-elapsed-holds-2026-09-29) measures explicit synchronization and narrower duplicate artifact coverage.

## Graph at the original measurement

- `zig build` installs a Rui CLI built with the standard `-Doptimize` option (Debug by default) and notices. `zig build test` compiles/runs `src/tests.zig` in **ReleaseSafe**, including SQLite, Bash platform C and transport; `test-logic` compiles/runs `src/logic_tests.zig` in ReleaseSafe without those native attachments. `-Dtest-filter=...` filters tests but is not a way to compile only the selected source declarations. The [Zig build guide's test section](https://ziglang.org/learn/build-system/#testing) distinguishes compiling from running a test artifact; [build modes](https://ziglang.org/documentation/0.16.0/#Build-Mode) explain the optimization/safety tradeoff.
- `check` builds the ReleaseSafe and Debug CLIs, ReleaseSafe tests, a ReleaseSmall CLI, formatting, then process integrations; it is not a cheap compilation-only check. The named admission/dispatch/Bash/control steps use a ReleaseSafe CLI. `cross-check-linux` and `cross-check-macos` build ReleaseSmall CLIs for two architectures each; the macOS transport script requires Apple's SDK. These steps are different evidence, not redundant runs of the default Debug artifact. [Local graph](../build.zig), [gate contract](../VERIFICATION.md#canonical-gates).
- Each CLI and the main `test` compilation attaches `sqlite3.c` with the same C flags and macros and `bash_platform.c`; `test-logic` does not. The qualification SQLite shell adds `shell.c`. The CLI names, targets and optimization modes differ. The pinned transport command builds static OpenSSL/curl once per selected target *step* and supplies its generated include/lib directory to the compile steps; it invokes `make -j4` twice. Cross targets have separate transport outputs. [Build configuration](../build.zig), [shell recipe](../src/build_transport.sh).

## Supported controls and important limits

| Control / mechanism | Source-backed behavior | Applicability and caveat for Rui |
| --- | --- | --- |
| Reuse local `.zig-cache` and dependency caches | The [official build guide](https://ziglang.org/learn/build-system/#installing-artifacts) describes `.zig-cache` as rebuild acceleration. Zig 0.16 [release notes](https://ziglang.org/download/0.16.0/release-notes.html#Fetch-Packages-Into-Project-Local-Directory) specify that fetched packages live in `zig-pkg`, with canonical compressed copies in the global cache. `zig build --help` offers `--cache-dir`, `--global-cache-dir`, and `--fetch=needed\|all`. | Keep caches between ordinary iterations. Do **not** equate a warm local build with the required clean export/empty-cache build; the [verification recipe](../VERIFICATION.md#canonical-gates) explicitly excludes `zig-pkg`, uses fresh local/global caches, prefetches pinned OpenSSL and then fetches the full graph. `--fetch=all` fetches rather than benchmarking compilation. |
| Run a narrow existing step | The [official build guide](https://ziglang.org/learn/build-system/#installing-artifacts) models a DAG of independently runnable/concurrent steps, and its [test section](https://ziglang.org/learn/build-system/#testing) separates compilation from execution. | During edits use `test-logic` for portable owner/turn logic or a named filtered/native/integration gate as appropriate; retain `check` and cross gates for the evidence their contract requires. A narrower step does not prove the larger gate. Selecting a step does not imply the entire `build.zig` graph is never constructed. |
| `--summary all`, `--verbose`, `--time-report` | The [0.16 build guide's CLI help](https://ziglang.org/learn/build-system/#user-options) documents build summaries, verbosity, and `--time-report`: it **forces a full rebuild** and reports Zig-source compilation time (also enabling the web UI). | Compare cold and warm `--summary all` step durations/cache status first; `--verbose` identifies actual commands. Use `--time-report` only for uncached compiler attribution, not to measure normal incremental edits, shell transport or process-integration costs. Record toolchain, target, selected step, cache state and repeated wall time. |
| `-jN`, `--maxrss` | Both are documented in the [0.16 build CLI help](https://ziglang.org/learn/build-system/#user-options) as concurrent-job and memory limits, not optimizer flags. | Try bounded `-jN` if concurrent compiler/link jobs compete for RAM; Rui's transport script separately runs `make -j4`, so Zig's `-j` alone does not cap all subprocess parallelism. `--skip-oom-steps` skips work rather than proving a gate passed. Neither flag guarantees faster builds. |
| `-fincremental --watch` | [Zig 0.16 release notes](https://ziglang.org/download/0.16.0/release-notes.html#Incremental-Compilation) say incremental compilation works with LLVM but does not speed LLVM's **emit-object** phase; it is experimental, has known miscompilations, and is **off by default**. They suggest `zig build -fincremental --watch`. `--watch` and `--debounce` appear in [build help](https://ziglang.org/learn/build-system/#user-options). | Plausible local edit/compile-feedback experiment, especially for Zig logic changes; not a qualification substitute. Compare with ordinary builds, rerun non-incremental gates on the exact revision, and watch for failures/miscompilations. It cannot be assumed to accelerate SQLite C compilation, the OpenSSL/curl shell builds, ReleaseSafe LLVM object emission or integrations. |
| Optimization setting | [Zig's 0.16 build modes](https://ziglang.org/documentation/0.16.0/#Build-Mode) define Debug, ReleaseSafe and ReleaseSmall; [standard build options](https://ziglang.org/learn/build-system/#standard-options) explain `-Doptimize`. | `-Doptimize=Debug` affects the default CLI, **not** Rui's hard-coded ReleaseSafe tests/CLIs or ReleaseSmall cross builds. Do not silently replace these modes with Debug to make verification faster: it changes the validated artifact and safety/optimization behavior. |

### The external-command cache boundary

The [0.16 `Run` implementation](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L707-L728) treats a command with an output argument and no other side effects as cacheable. `addFileArg` tracks the script file; `addOutputDirectoryArg` provides the generated tree. But [`addDirectoryArg`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L461-L480) establishes a step dependency and [`Run.make`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L816-L850) hashes the directory **path**, not every file read under it; extra file inputs can be declared with [`addFileInput`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Run.zig#L700-L706). Rui's `addPinnedTransport` uses package directory args for the OpenSSL/curl source trees. Thus a warm cached transport result is useful, but do **not** assume an edited file in `zig-pkg` necessarily invalidates this shell step. Its script also discovers tools/Apple SDK and uses ambient shell environment: investigate those inputs before claiming reproducibility or sharing caches. The package pins and clean-build gate remain the authoritative baseline. This is a source-based cache-key caveat, **not** an observed stale-build incident.

Similarly, Zig's [`Compile.make`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Step/Compile.zig#L1470-L1480) passes local/global cache directories to the compiler, and [`addCSourceFile`](https://codeberg.org/ziglang/zig/src/tag/0.16.0/lib/std/Build/Module.zig) declares SQLite C input/flags. Cache reuse across different named executables, targets and optimization modes must be *measured*, not inferred from their common `sqlite3.c` path. Altering SQLite macros, source provenance or link arrangement to share an object is a separate build/behavior change requiring clean builds and relevant gates; no speedup is established by this note.

## Low-risk measurement order (not an implementation plan)

1. For the *same* revision/toolchain/target, capture ordinary warm `zig build test-logic --summary all`, `zig build test --summary all`, `zig build --summary all`, and the relevant `check`/cross gate summaries; record each step's cached/uncached state and wall time. Change one Zig source file in a disposable working copy to compare edit rebuilds (do not use a cache deletion as a stand-in for an ordinary edit). Attribute native/shell and process-test wall time separately. Never report an unrun gate as passed.
2. Only if compiler time dominates, compare a local `-fincremental --watch` edit loop to the normal loop; only if native compilation dominates, inspect `--verbose` and the generated step durations. Keep target/optimization and cache state comparable. Do not treat an official Zig compiler benchmark or a different project's build time as Rui's measured gain.
3. Preserve the required non-incremental clean-cache and platform checks before changing build graph or dependency handling. macOS runtime/SDK qualification still needs macOS; Linux cross compilation cannot establish native macOS behavior. [Canonical gates](../VERIFICATION.md#canonical-gates).

## Mac portability and assembled verification, 2026-09-29

The available Mac is an M1 Pro arm64, 16 GiB, macOS 15.7.7, Zig 0.16.0 and Python 3.14.7. Short checkouts avoid Unix-socket pathname overflow. Copy-on-write cache copies were not cold caches; moving sources still rebuilt path-sensitive transport inputs. The original `c81d1a8` Mac `check-full` failed at the first evaluator compile-only assertion after 282 native passes and two skips. Separately executing baseline `ffc5eb7` reproduced that failure. Neither failing run supplies a whole-suite latency baseline.

The evaluator failed closed before QuickJS because Zig's default Mach-O executable reserved a custom 16 MiB stack. [XNU rejects `RLIMIT_STACK` for custom stacks](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/bsd/kern/kern_resource.c#L1295-L1300). Removing that reservation made `setrlimit` succeed but did not establish protection: the native probe read back 1 MiB yet touched over 2 MiB successfully. The published [ordinary-stack shrink path](https://github.com/apple-oss-distributions/xnu/blob/xnu-11417.140.69/bsd/kern/kern_resource.c#L1388-L1397) computes a zero-length protection change; this supports the observed diagnosis, not a claim that the published source exactly matches the running kernel.

The corrected evaluator uses a 1 MiB guarded stack established at exec and verifies the main-thread stack size before source input. A native 32-frame page-touch probe succeeded; 512 frames of 4 KiB faulted with SIGSEGV, while the 16 MiB control completed. An actual 1 MiB evaluator compiled and returned exact `5`; a same-source 2 MiB artifact exited 3 directly and failed through the parent with no output, including with an inherited 1 MiB limit. Linux's resource-limit path and both platforms' core/CPU setters remain unchanged. The Mac mapping is fixed at 1 MiB rather than tightened from inherited stack limits; limit readback alone is not enforcement evidence.

Mac testing also found fixture assumptions: canonical `/private/var` paths differ from `/var`; allocator defaults can add a real inherited Unix socket; blocking FIFO EOF woke only one of ten readers; and a 100 ms cancellation timer could fire before child startup. Corrections independently resolve expected paths, calculate descriptor-budget terms while keeping defaults enabled, retain nonblocking FIFO reads with a 10 ms sleep, and cancel only after child readiness or received framed output. Both contention tests establish all ten waiters before release. The native descriptor test cross-checks directory enumeration against `F_GETFD`; integration accepts the diagnosed three/four inherited descriptors but still rejects below the independently calculated budget and admits at exactly that budget. It does not independently count that exact Host's inherited descriptors. Original failures and counterexamples remain evidence, not discarded retries.
