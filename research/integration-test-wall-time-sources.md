# Warm integration-test wall time: source-backed options

Research note, 2026-09-23. Scope: Zig 0.16.0/Python 3.11 semantics, the previous serial check and the measured fast/full gate change on Linux x86-64. [Development build latency](build-times-sources.md) separately covers compilation/cache costs. These local measurements do not establish macOS runtime or cold-build speed.

## Source background and previous graph

Before the change, `zig build check` depended on formatting, ReleaseSafe native tests and ReleaseSmall compilation before one `process_integrations` shell step. That step ran admission, dispatch, Bash owner/journey/lifecycle/recovery, control, descriptor-capacity, Debug admission and Host-process fixtures **in order** ([build graph](../build.zig), [serial script branch](../tests/integration/check.sh), [gate contract](../VERIFICATION.md#canonical-gates)). Zig's [build guide](https://ziglang.org/learn/build-system/#installing-artifacts) describes independently runnable/concurrent DAG steps; [testing](https://ziglang.org/learn/build-system/#testing) distinguishes compile from run, and [build options](https://ziglang.org/learn/build-system/#user-options) document `--summary all` and `-jN`. Raising `-j` cannot parallelize commands *inside* one shell process. Local trials with separate Zig Run steps took 209 seconds warm even with `-j8`; a bounded parallel batch within one step took under a minute. This is observed Zig 0.16 behavior on this machine, not a general claim about Zig's scheduler.

The loopback fixtures repeatedly start `http.server.ThreadingHTTPServer`, then call `shutdown()` and `server_close()` (for example, [dispatch](../tests/integration/dispatch_integration.py) and [control](../tests/integration/control_integration.py)). Python's [`serve_forever(poll_interval=0.5)` contract](https://docs.python.org/3.11/library/socketserver.html#socketserver.BaseServer.serve_forever) polls for shutdown at that default interval; [`shutdown()`](https://docs.python.org/3.11/library/socketserver.html#socketserver.BaseServer.shutdown) waits for the serving loop and must be called from another thread. The [Python 3.11.6 implementation](https://github.com/python/cpython/blob/v3.11.6/Lib/socketserver.py) waits in a selector for up to that interval, checks the shutdown flag after waking and signals loop completion. `ThreadingHTTPServer` handles requests in daemon threads ([HTTP server docs](https://docs.python.org/3.11/library/http.server.html#http.server.ThreadingHTTPServer), [Python source](https://github.com/python/cpython/blob/v3.11.6/Lib/http/server.py)); the [mix-in docs](https://docs.python.org/3.11/library/socketserver.html#socketserver.ThreadingMixIn) distinguish serving-loop shutdown from handler completion. The shared [test endpoint](../tests/integration/host_process.py) now polls at 10 ms; release events, `shutdown()`, `server_close()`, joins and outcome assertions remain in their owning fixtures.

## Local observations

The Linux x86-64 orb reported four CPUs and 7.8 GiB RAM, with Zig 0.16.0 and Python 3.11.6. Same-machine commands used `/usr/bin/time -f 'wall=%e ...' zig build <step> --summary all` with existing pinned dependencies and warm `.zig-cache` after the first build. The source tree was clean at the baseline and dirty for the implementation runs. This is not an edit-rebuild or empty-cache compilation comparison.

| Run | Wall | Coverage/attribution |
| --- | ---: | --- |
| Previous serial `check` (warm) | 306.90 s | 246/246 native passed; about 68 s native and 239 s process execution |
| Previous native binary alone | 68.48 s | One 61-second default-inactivity witness; other 245 tests about 7.5 s together |
| Dispatch fixture, default Python poll | 69.57 s | Same fixture with an in-memory 10 ms poll trial: 55.39 s, all assertions passed |
| New parallel `check` (warm) | 57.70 s; 55.92 s after fixture correction | All process suites; 246 native passed, one exact-timeout witness skipped |
| New serial `check-full` (warm) | 277.12 s; 280.49 s after fixture correction | All process suites in order; 247/247 native passed, including the 61-second witness |

The normal gate retains every process case, including high-population controls and Bash cleanup faults, and one short asymmetric client test checks that waiting before the first byte does not start inactivity. The full gate retains the exact elapsed default witness and serial process latency observations. Each parallel lane has a private Store and port-zero endpoint; the [batch](../tests/integration/check.sh) waits for every child, reports each failure's captured log, and returns failure if any case fails. A repeated parallel run exposed a [Bash-owner fixture](../tests/integration/bash_owner_integration.py) that asserted physical custody release immediately after provider continuation; waiting for the existing public custody-idle observation corrected that ordering mistake without changing the release assertion. Concurrent fixture load changes latency observations (one comparison increased control p95 from about 6 to 19 ms), so it is correctness feedback, not representative isolated timing evidence. [Go's first-party concurrency-testing guidance](https://go.dev/blog/testing-time) explains why elapsed time is not synchronization. No production deadline, accepted workload or test assertion was shortened.

**Evidence boundary:** Rui's [qualification workload](../VERIFICATION.md#qualification-workload-and-measurement-boundary) has fixed offered-load pacing, full event/result audits, two same-Host rounds and resource/latency targets. Concurrent test processes add CPU, I/O and scheduling contention, so run latency/resource qualification under its prescribed, comparable environment, separately from parallel correctness feedback. Instrumented handshakes prove ordering but perturb timing ([measurement synchronization](measurement-synchronization.md#separate-representative-measurement)). The full gate is still required on the exact revision for complete evidence; the warm feedback result does not qualify cold compilation, power loss or live-provider behavior.
