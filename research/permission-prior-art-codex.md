# Codex CLI permission prior art

Research date: 2026-09-13. Primary source repository: `openai/codex`, inspected at stable tag `rust-v0.154.0` (commit `6b9826e3aa83b1a5947db50f4332cb9c65f1b340`; the annotated tag object is `36eab01061df3cde5f95ec20a526777b430091ba`) and current main `a592c38c16cdd7623dacc9168926ebccedfb67d3`. Stable tag was used as the release baseline; main was inspected for relevant changes. Source links below are pinned to the inspected revisions.

## Evidence map

### Policy owner and enforcement

Codex separates the approval policy from the runtime permission profile. The runtime profile is a closed typed value: `Managed` means Codex constructs the sandbox, `Disabled` means no outer sandbox, and `External` means a caller enforces filesystem isolation; the source says the runtime must honor the profile and that the named-profile sidecar is display metadata ([main, `protocol/src/models.rs` lines 416-454](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/protocol/src/models.rs#L416-L454)). The execution path passes the selected profile into sandbox selection and then into process execution ([stable, `core/src/exec.rs` lines 122-133](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/exec.rs#L122-L133), [stable, lines 431-469](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/exec.rs#L431-L469)). This is evidence that offering a permission or approval choice does not itself enforce authority; execution reuses the effective profile at the executor boundary.

Approval policy chooses whether/when review is needed and can be constrained by requirements. The configuration comment says `approvals_reviewer` routes escalated requests and does not disable separate safety checks ([stable, `core/src/config/mod.rs` lines 656-659](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/config/mod.rs#L656-L659)). The v2 policy enum includes `UnlessTrusted`, `OnRequest`, granular categories, and `Never`; granular categories independently cover sandbox approval, rules, skill approval, requested permissions, and MCP elicitations ([main, `app-server-protocol/src/protocol/v2/shared.rs` lines 176-214](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server-protocol/src/protocol/v2/shared.rs#L176-L214)).

### Offering versus execution authority

The server emits an approval request containing the command, cwd, reason, environment, parsed presentation, proposed policy amendments, additional permissions, and an ordered list of allowed decisions ([main, `app-server-protocol/src/protocol/v2/item.rs` lines 1531-1595](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L1531-L1595)). The client response is mapped to core decisions: one-off accept, session-cache accept, exec-policy amendment, network-policy amendment, decline, or cancel ([main, lines 64-106](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L64-L106); [main, `app-server/src/bespoke_event_handling.rs` lines 1961-2001](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server/src/bespoke_event_handling.rs#L1961-L2001)). The response is therefore a decision input to the session; actual enforcement remains at core execution/sandbox policy.

The request is registered before being sent, keyed by `call_id` plus `approval_id`; the session awaits a one-shot callback and defaults to `Abort` if the sender disappears ([stable, `core/src/session/mod.rs` lines 2624-2726](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L2624-L2726)). Matching responses remove the pending entry and send the decision; an unmatched response is logged and has no authority ([stable, lines 3214-3233](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L3214-L3233)).

### Grant scope, lifetime, and reuse

For the explicit `request_permissions` flow, Codex accepts only the requested permission intersection. A normal approval produces a turn-scoped grant; `ApprovedForSession` produces a session-scoped grant; denials, timeout and abort produce an empty turn-scoped grant ([stable, `core/src/session/mod.rs` lines 2859-2904](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L2859-L2904)). The session records turn grants in turn state and session grants in session state ([stable, lines 3116-3135](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L3116-L3135)). A strict auto-review flag is rejected when paired with session scope ([stable, lines 3087-3113](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L3087-L3113)).

The permission intersection fails closed for externally enforced profiles, platform defaults, unsupported paths, and unmaterialized workspace roots; network access is enabled only when both inputs enable it ([main, `protocol/src/permission_profile_intersection.rs` lines 20-45](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/protocol/src/permission_profile_intersection.rs#L20-L45), [main, lines 74-99](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/protocol/src/permission_profile_intersection.rs#L74-L99)). This is a concrete reuse guard: a grant cannot widen the originating authority.

The ordinary command approval response `AcceptForSession` is described as using a session-scoped approval cache; an exec-policy amendment instead changes future matching-command policy, and a network amendment changes a persistent host rule ([main, `app-server-protocol/src/protocol/v2/item.rs` lines 64-80](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L64-L80)). The handler persists an exec-policy amendment before notifying the waiting approval ([main, `core/src/session/handlers.rs` lines 171-201](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/session/handlers.rs#L171-L201)).

### Policy changes versus pending actions

The approval payload is a snapshot of the exact command and context at request time. The client handler explicitly preserves the exact command for approval while redacting only history ([main, `app-server/src/bespoke_event_handling.rs` lines 707-719](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server/src/bespoke_event_handling.rs#L707-L719)). The response is routed by opaque callback identity, and a policy amendment is handled as a separate persisted effect before the callback resumes ([main, `core/src/session/handlers.rs` lines 173-200](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/session/handlers.rs#L173-L200)). These paths provide evidence for keeping a policy mutation distinct from the pending action it may authorize.

### Disconnect, reconnect, and restart

App-server request callbacks are process-memory state. `OutgoingMessageSender` stores request callbacks and request payloads in a mutex-protected hash map ([stable, `app-server/src/outgoing_message.rs` lines 124-153](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server/src/outgoing_message.rs#L124-L153)). On connection close, connection-scoped incoming request contexts are removed and user-verification ownership is disconnected; ordinary thread-scoped approval callbacks remain in the separate callback map ([stable, lines 254-259](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server/src/outgoing_message.rs#L254-L259)).

For a live thread, a reconnecting client can receive pending server requests again. Codex filters pending requests by thread, excludes special verification ownership, sorts by request ID, and resends the stored request payload ([stable, lines 425-443](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server/src/outgoing_message.rs#L425-L443), [stable, lines 561-575](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server/src/outgoing_message.rs#L561-L575)). Running-thread resume invokes that replay before declaring the thread idle ([stable, `app-server/src/request_processors/thread_lifecycle.rs` lines 790-798](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L790-L798)). Thus a client disconnect is recoverable for a still-running server process and live thread.

The evidence does not show persistence of `request_id_to_callback`, pending approval one-shots, or their full approval payloads into the rollout/thread store. They are in-memory fields and one-shot channels. Therefore a server restart is an explicit limit of this prior art: durable conversation history/settings may be resumable, but an unresolved approval callback and its execution continuation should be treated as lost or aborted unless another layer adds durable pending-action state. The core approval wait's `unwrap_or(Abort)` is the fail-closed behavior when its callback disappears ([stable, `core/src/session/mod.rs` lines 2724-2726](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L2724-L2726)).

### CLI exit and unattended operation

The source inspected here models app-server client disconnect and reconnect, not a detached CLI approval UI. While the server process remains alive, dropping the approval callback makes the core wait resolve as `Abort` ([stable, `core/src/session/mod.rs` lines 2724-2726](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L2724-L2726)). If the CLI process exits, its in-memory session and callback state are destroyed, so there is no continuation that can resume. Under `AskForApproval::Never`, ordinary commands are allowed to run relying on the sandbox, while unmatched commands classified as dangerous, or Windows managed restrictions without an enabled sandbox backend, are forbidden ([stable, `core/src/exec_policy.rs` lines 799-813](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/exec_policy.rs#L799-L813)). The explicit permission-request path instead returns an empty turn-scoped grant without eliciting a reviewer ([stable, `core/src/session/mod.rs` lines 2799-2818](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/session/mod.rs#L2799-L2818)); these are unattended fail-closed/escalation semantics, not an unattended approval queue. `AcceptForSession` and persisted policy amendments are explicit reuse mechanisms, but the approval protocol itself has no evidence here of an unattended approval queue, expiry ledger, or durable payload ownership. Any unattended mode that permits escalation would need an independently defined reviewer/authority and recovery contract.

## Stable release versus current main

The stable tag already contains the central approval design: typed v2 approval decisions, one-shot in-flight callbacks, turn/session permission grants, fail-closed intersection, and app-server replay of pending thread requests after reconnect. Current main retains those mechanisms. The relevant main-only changes found in this inspection are adjacent hardening: `RequestContext` now carries cancellation scope and checked response delivery, while user-verification ownership is cancelled promptly on disconnect ([main, `app-server/src/outgoing_message.rs` lines 124-153](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server/src/outgoing_message.rs#L124-L153), [main, lines 262-276](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server/src/outgoing_message.rs#L262-L276), [main, lines 658-690](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/app-server/src/outgoing_message.rs#L658-L690)). The main diff also reorganizes unrelated session/plugin/history code, so those changes are not treated as permission-contract evidence.

## Limits of this research

This is source and test inspection only; no Codex binary, provider, sandbox, or live app-server check was run. GitHub links are pinned to the two inspected revisions. Claims about restart behavior are bounded inferences from the in-memory ownership structures and the absence of a persistence path in the inspected approval code, not a separately executed crash/restart experiment.
