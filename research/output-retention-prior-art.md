# Optional output retention: prior art

Inspected 2026-09-12. This is source research for [Choose optional tool-output retention budgets and bookkeeping](https://github.com/DivyanshGolyan/rui/issues/146), not an accepted policy, implementation or runtime qualification. Current behavior remains in [shared scratch ownership](../ARCHITECTURE.md#shared-scratch-ownership).

The subsequent [user decision](https://github.com/DivyanshGolyan/rui/issues/146#issuecomment-5643175874) supersedes the initial recommendation below; this note preserves the source evidence and its limits.

## Finding

A second configurable file-count limit is common, but not inevitable. A positive charge per retained file derives a finite population from one byte allowance. That alone does **not** establish an acceptable resident-memory bound: a large disk allowance can still buy millions of tiny files. The narrow alternative worth evaluating first is the existing disk FIFO contract implemented as a small file queue, rather than replacing it with a general cache or a separate count policy. This recommendation is an inference from the implementations below and Rui's requirements; no implementation was measured.

## What a minimum charge actually buys

For scratch allowance `B`, minimum charged bytes per retained file `q > 0`, and resident queue record size `r`, retained population is at most `floor(B/q)`. An all-resident queue can therefore require approximately `r * floor(B/q)` bytes, plus allocator/container overhead. Active/protected resources remain additional populations owned by their execution limits.

With the current 8 GiB default, a hypothetical 4 KiB minimum permits 2,097,152 retained files. Even hypothetical 128-byte records consume 256 MiB before allocator overhead. Charging only a real 128-byte metadata record permits 67,108,864 empty entries: all-resident records could consume 8 GiB. These are arithmetic illustrations, not selected record sizes or filesystem measurements.

A larger minimum charge can make the derived RAM bound fit, but then it is a retention policy: tiny files consume budget disproportionately and disappear earlier. It should be explained as such. It also changes the current definition of logical owned bytes if the charge exceeds actual payload/index storage. Filesystem block rounding is not a portable substitute for a deliberate positive minimum: empty/sparse files, compression and filesystem metadata complicate that inference.

Only retaining outputs larger than their saved excerpt is another possible policy simplification: it avoids keeping full files that add no content, and supplies a payload-size lower bound. It does not automatically establish a useful memory bound at 8 GiB; paired stdout/stderr files need charging as a group or separate treatment. Exact threshold behavior must be checked against the combined-stream excerpt rules. This remains a policy option, not an assertion about the current implementation.

## Small representations to compare

1. **Disk FIFO with fixed records or bounded segments.** Keep just current head/tail state and a bounded I/O window resident. Record a generated file identifier and original charged length; reconstruct its path from the owned directory and identifier. Append on handoff and advance only after removal succeeds. Segments permit reclaiming consumed metadata without copying the complete index; a ring permits reuse but complicates expansion. This is a design inference, not a tested Tape port. Account for partial writes, a failed head unlink, segment rollover at full allowance, open handles, and charged unreclaimed segments. Avoid maintaining an in-memory list of every segment.
2. **Directory scanning.** A bounded-memory scan can select the oldest eligible entry without retaining the whole directory, but repeated scans trade memory for filesystem work. Ordinary collect-and-sort implementations above do not provide that bound. Directory entries alone cannot recover Rui's originally charged length from externally mutable file sizes. Encoding authoritative fields in owned names or separate metadata adds its own invariant. This alternative requires a concrete latency and ownership proof before displacing the queue.
3. **SQLite index.** Technically viable, but broader than a disposable FIFO. SQLite's [vacuum documentation](https://www.sqlite.org/lang_vacuum.html) explains that deleted pages usually remain reusable within the database and that full VACUUM can need up to twice the database size in free space. [Incremental auto-vacuum](https://www.sqlite.org/pragma.html#pragma_auto_vacuum) supports incremental reclamation, but adds page movement and configuration. A strict shared allowance must include database and transactional transient storage. This does not follow automatically from adopting DiskCache's size estimate.
4. **Resident FIFO plus count cap.** Straightforward and common. Select it if the explicit policy is acceptable and its simplicity wins against a demonstrated disk-queue cost. It adds the independent count boundary that prompted this investigation; disguising it as an arbitrary per-file byte surcharge does not remove the behavioral choice.

The immediate next evidence should compare the two narrow FIFO representations on partial append, failed unlink, full-allowance rollover/reuse and sustained churn, with bounded memory and handles. Prior art does not establish these properties for Rui on Linux or macOS.
