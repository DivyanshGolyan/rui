# Parallel tool-result ordering

Inspected 2026-09-17 for [Rui issue #199](https://github.com/DivyanshGolyan/rui/issues/199). This records design evidence; accepted behavior lives in the owning architecture contract, and no provider qualification follows.

## Conclusion

The current Responses protocol identifies each function result by `call_id`; the inspected official schema and guide do **not** say that sibling result position must equal sibling call position. Calls `A,B,C` with outputs `B,A,C` are therefore not shown to violate the documented correlation rule, provided every output carries the exact call ID and every call receives one result. However, no explicit first-party live-server fixture exercising `B,A,C` was found, so live acceptance is not established.

First-party clients consistently separate concurrent completion from ordered publication. Codex CLI, OpenAI Node, and both Agents SDKs gather parallel results and emit them in call order. OpenAI's Codex prompting guide separately says ordered parallel call items and responses are “helpful and more in-distribution.” That is model-quality guidance, not a stated wire-validity rule.

**Smallest correct contract for #199:** treat `call_id`, not array position, as result identity; require exactly one terminal result for each accepted call, reject unknown or duplicate IDs, and wait for complete coverage before continuation. Permit execution and settlement in any order and commit each outcome immediately. Derive the complete model-visible group from those outcomes in original call order, without a second result copy or publication state. Call-ordered rendering is Rui's deterministic/model-quality and recovery policy, not an OpenAI protocol requirement.

## Protocol requirements

- The [current Responses schema](https://platform.openai.com/docs/api-reference/responses/create) defines `input` as an item list, a function call's `call_id` as its unique ID, a function output's `call_id` as that generated call ID, and `parallel_tool_calls` only as permission to run calls in parallel. For custom tools it is explicit that `call_id` is “used to map this custom tool call output to a custom tool call.” It states no sibling positional relationship.
- The [official function-calling guide](https://developers.openai.com/api/docs/guides/function-calling.md#handling-function-calls) says an output should reference a specific call by `call_id`, applications should inspect every call and return a result for each, and reasoning items accompanying calls must also be replayed for reasoning models. Its examples append outputs while iterating calls, which preserves order incidentally; the prose does not make that order normative.
- The generated [OpenAI Python input type](https://github.com/openai/openai-python/blob/b77076d23b6f3e34453b0fadd8cd2a001627e365/src/openai/types/responses/response_input_item_param.py#L165-L197) likewise gives `FunctionCallOutput` a `call_id` and no position field or ordering constraint; [`parallel_tool_calls`](https://github.com/openai/openai-python/blob/b77076d23b6f3e34453b0fadd8cd2a001627e365/src/openai/types/responses/response_create_params.py#L138-L145) only controls whether parallel calls are allowed.

Complete ordered replay of prior provider output is a different rule. OpenAI Node tells manual-history clients to preserve the [complete ordered output](https://github.com/openai/openai-node/blob/0118f6cef73547d386a6f16dbd423c09c64b43bf/docs/responses.md#L47-L70), including reasoning and tool-call items. That does not make sibling output position the correlation key.

## Observed first-party client behavior

- **Codex CLI.** Tool futures are inserted in streamed call order into [`FuturesOrdered`](https://github.com/openai/codex/blob/f3da3861c557b4813d9840177a45940a465f9efe/codex-rs/core/src/session/turn.rs#L2640-L2649), then [drained and recorded in that order](https://github.com/openai/codex/blob/f3da3861c557b4813d9840177a45940a465f9efe/codex-rs/core/src/session/turn.rs#L2367-L2388) after the response completes ([drain site](https://github.com/openai/codex/blob/f3da3861c557b4813d9840177a45940a465f9efe/codex-rs/core/src/session/turn.rs#L2998-L3010)). Its parallelism test requires all calls before all outputs and zipped call/output IDs in [original order](https://github.com/openai/codex/blob/f3da3861c557b4813d9840177a45940a465f9efe/codex-rs/core/tests/suite/tool_parallelism.rs#L225-L300).
- **OpenAI Node.** The documented parallel example uses [`Promise.all(calls.map(...))`](https://github.com/openai/openai-node/blob/0118f6cef73547d386a6f16dbd423c09c64b43bf/docs/tools.md#L59-L85), which preserves input order despite completion order, and explicitly says to [match with `call.call_id`](https://github.com/openai/openai-node/blob/0118f6cef73547d386a6f16dbd423c09c64b43bf/docs/tools.md#L89-L95).
- **OpenAI Agents Python.** It drains tasks with [`FIRST_COMPLETED`](https://github.com/openai/openai-agents-python/blob/d59fdb8a789a54aff77ce61e503a04797355fc03/src/agents/run_internal/tool_execution.py#L1667-L1683), stores results by tool run, then [iterates the original `tool_runs`](https://github.com/openai/openai-agents-python/blob/d59fdb8a789a54aff77ce61e503a04797355fc03/src/agents/run_internal/tool_execution.py#L2250-L2263). A test checks call-order output even when a sibling is [cancelled](https://github.com/openai/openai-agents-python/blob/d59fdb8a789a54aff77ce61e503a04797355fc03/tests/test_agent_runner.py#L1932-L1977).
- **OpenAI Agents JavaScript.** Unbounded execution maps input-order tasks into the sibling runner; bounded execution writes each completion to [`results[currentIndex]`](https://github.com/openai/openai-agents-js/blob/506f736a10014df5c6d7c68a9987594674d4fabb/packages/agents-core/src/runner/toolExecution.ts#L539-L596), preserving call order in the returned array.
- **Model quality.** The [Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide.md#parallel-tool-calling) says it is “helpful and more in-distribution” to group parallel calls followed by their responses. This supports canonical publication order but does not declare other orders invalid.

## Reordered-output counterexample search

No explicit OpenAI fixture or test sending calls `A,B,C` and outputs `B,A,C` to a live Responses backend was found. The strongest acceptance counterexample is structural: Codex's first-party Responses mock validates call/output correlation and complete coverage with [`HashSet`s`](https://github.com/openai/codex/blob/f3da3861c557b4813d9840177a45940a465f9efe/codex-rs/core/tests/common/responses.rs#L1504-L1641), never comparing positions. Thus `B,A,C` passes that validator when IDs are known and complete. This demonstrates that a first-party protocol fixture treats IDs rather than positions as the invariant; it is not proof that every live backend/model accepts or performs equally with reordered outputs.

For Rui, call-ordered derivation is the smaller recovery contract. Each rejection or Action Resolution remains the sole authoritative terminal fact and is accepted independently; complete coverage gates only the next model Operation. At request materialization, traversing durable calls and their outcomes by call ordinal needs neither completion-order tracking nor a copied result batch. It makes retries, crash recovery, transcript comparison, cache behavior and debugging deterministic while matching first-party clients and model guidance. Reverse-order denials in #199 therefore change only when calls become terminal, never their rendered order.
