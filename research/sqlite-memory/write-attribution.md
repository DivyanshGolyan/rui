# Production SQLite write attribution

The earlier **2,334,601,216-byte** process-write result was not 2.33 GB of new database content or repeated whole-database saves. It measured 10,000 independently committed Session creations. A fresh baseline reproduced **2,320,719,872 bytes** with a **5,423,104-byte** final database. The instrumented production path requested about **963 MB** of database plus rollback-journal writes; macOS charged about **2.36 GB** during the corresponding sync calls. Small writes being flushed at larger units explain most of that difference.

There is a modest avoidable cost from the current small cache: an existing 128 KiB profile reduced journal syncs and process-accounted writes without changing any transaction or durability boundary. There is no evidence here of redundant database-page rewrites within a transaction, unnecessary full-value rewriting by Rui, or WAL/checkpoint amplification.

## What the fixture did

`src/host_store_density.zig:82` opens each Store before the timed interval, resets pager counters, then creates and closes one Session per iteration. It allocates/releases transient scratch metadata, resolves the workspace and calls production `Session.create`. There is no provider, model response, task execution or user subprocess in this population loop. The fixture's later response/scratch cases are outside its 10,000-Session interval.

`src/session.zig:1796` calls `StorageOwner.createSessionWithContent`. Each call performs one `BEGIN IMMEDIATE` and one `COMMIT`, inserting a Session, its 36-byte task content, one transition and one conversation entry. The diagnostic independently verified **10,000 rows in each relation**, **360,000 content bytes**, **40,000 INSERT statements**, **10,000 begins**, **10,000 commits** and **zero rollbacks**. Schema/index and metadata maintenance are useful work beyond those 360,000 content bytes; treating only task text as the denominator would misdescribe the workload.

The effective mode was **DELETE**, synchronous **EXTRA (3)**, 4,096-byte SQLite pages and mmap off. WAL opens/writes were zero: there was **no WAL or checkpoint cycle**. The older production implementation had `fullfsync=0`; the diagnostic preserved it. This is not qualification of the accepted redesign's macOS fullfsync requirement.

## Where the bytes went

The detailed 64 KiB production run recorded:

| Counter | Database | Rollback journal | Total |
| --- | ---: | ---: | ---: |
| Successful native-VFS write requests, bytes | 479,801,344 | 482,859,072 | 962,660,416 |
| Write calls | 117,139 | 375,873 | 493,012 |
| File sync calls | 10,000 | 28,332 | 38,332 |
| Process write-byte increments during file syncs | 1,568,473,088 | 790,515,712 | 2,358,988,800 |

The database byte count equals `SQLITE_DBSTATUS_CACHE_WRITE × 4,096` exactly. All native write calls succeeded. There were 10,000 journal opens, closes and deletes, each delete requesting directory sync for EXTRA. That directory-sync request and its latency are counted separately; zero process-counter increments during deletion do not mean no metadata/device work occurred.

The process counter did not increment around the buffered write calls, but its complete measured delta appeared inside the file-sync intervals. The attribution residual outside those measured syncs was zero in both detailed runs. These are operation-interval observations; the kernel field is not a path-labelled byte log or SSD/NAND-write counter.

The final detailed-run database occupied **5,349,376 logical bytes / 6,307,840 allocated bytes**. File growth and traffic differ: modified pages are rewritten across independent transactions and old page images protect each transaction in the rollback journal. The page bitmap found **zero writes of the same database page twice within one transaction**. It does not label repeated writes across different committed transactions unnecessary. Average useful work per Session requested **96,266 VFS bytes** and was charged **235,899 process-write bytes**; neither is final storage per Session.

## The Mac's write granularity

The independent control used an existing 1 MiB file, 100 write/sync rounds, and no SQLite. The Mac reported a 16,384-byte system page and 4,096-byte filesystem fragment. Each case preserved its stated write pattern:

| Pattern before each sync | Logical bytes across 100 rounds | Process-write delta |
| --- | ---: | ---: |
| One 4 KiB write | 409,600 | 1,638,400 |
| Four adjacent 4 KiB writes | 1,638,400 | 1,638,400 |
| Four 4 KiB writes in separate 16 KiB units | 1,638,400 | 6,553,600 |
| One 16 KiB write | 1,638,400 | 1,638,400 |
| Write the same 4 KiB range twice | 819,200 | 1,638,400 |

All increments occurred during sync. This demonstrates why syscall bytes and process-accounted bytes can differ without SQLite issuing duplicate full-page writes. It does not establish hardware write amplification.

A second production diagnostic tracked distinct 16 KiB units dirtied by successful VFS writes between syncs. For the journal, clipping the last unit to its file length rounded to the filesystem fragment predicted the observed counter **exactly** at both profiles: **786,624,512 bytes** at 64 KiB and **679,370,752 bytes** at 128 KiB. The un-clipped estimate for database syncs was **1,550,827,520 vs 1,544,728,576 observed** and **1,543,864,320 vs 1,538,899,968 observed**—within 0.4%. Tail clipping underestimated database accounting by about 37–38 MB. That remaining database difference is not fully attributed; the evidence does not justify assigning it all to filesystem metadata, preallocation or device behavior.

## Cache comparison, timing and useful work

The two light instrumentation runs at each existing profile retained all 10,000 commits, 40,000 inserts and 10,000 database syncs:

| Measure | 64 KiB profile | 128 KiB profile |
| --- | ---: | ---: |
| SQLite cache spills | 16,781 / 16,695 | 0 / 0 |
| Journal syncs | 28,174 / 28,136 | 20,000 / 20,000 |
| Process-write bytes | 2,341,527,552 / 2,319,867,904 | 2,216,247,296 / 2,227,232,768 |
| Population-loop elapsed seconds | 12.432 / 12.760 | 9.824 / 9.939 |
| Per-Session p95 milliseconds | 1.769 / 1.847 | 1.486 / 1.414 |
| Retained SQLite live bytes | 200,976 / 200,976 | 233,232 / 233,232 |
| SQLite peak bytes | 433,088 / 433,088 | 452,032 / 465,344 |

Mean process-accounted writes fell **4.67% (108,957,696 bytes)**, journal syncs **28.96%**, and elapsed time **21.55%**, for **32,256 additional live SQLite bytes**. The amount of database VFS writing stayed approximately unchanged. The detailed 128 KiB run had three spills and 20,002 journal syncs, so “128 KiB always eliminates spill” is not supported.

These are two samples per profile on a shared Mac, with the fixture's original random identities. B-tree layout and final size therefore vary. The original fresh baseline took **11.250 seconds**, while the detailed default-profile instrumentation took **14.800 seconds**; frequent kernel sampling has meaningful overhead. The light samples avoid per-operation kernel queries, making them the relevant paired timing comparison, but they still include measurement overhead. Timings are observations, not stable production targets or confidence intervals.

## Smallest justified follow-up and limits

The bulk of the traffic is explained by indexed, separately committed work, rollback journaling and Mac flush granularity. The narrow avoidable part demonstrated here is extra journal synchronization from the small cache. Qualify the ordinary transaction working set within the finite whole-process SQLite heap and compare an existing larger cache profile on required platforms. The measured 128 KiB profile is a candidate, not a new architectural constant or a selected production change. Do not batch independent acknowledgements, weaken durability, change journal mode or reshape the schema merely to reduce this counter.

Only the SQLite verification paragraph changed: cache/spill comparisons now distinguish useful work, database/journal requests, syncs and OS accounting from final size while preserving transaction/durability boundaries. The architecture already requires sizing caches against the Host budget; no additional architecture rule or runtime implementation was needed.

The diagnostic adds a fixed 32 KiB page-write bitmap, fixed counters and per-open-file wrapper headers; the granularity variant adds another fixed 32 KiB bitmap. These are measurement overhead, not proposed runtime allocations. It forwards native VFS operations, retains their flags/results and does not suppress writes or syncs. Successful publication counts, transaction counts, journal lifecycle, page-byte equivalence and zero VFS failures were asserted for all measured populations. Compilation was warning-free. Provenance/link checks, Python syntax checks and `git diff --check` passed. Production source/build files were unchanged, so broader runtime/live-provider gates were not rerun.

Linux remains unexecuted: page size, filesystem behavior, native VFS, OS I/O counters and timings need their own measurements. Real volume-full, power-loss, native fullfsync qualification, SSD wear and a complete redesigned Host workload are outside this evidence. The unresolved implementation choice is the eventual bounded cache size under those conditions, not whether to introduce a new storage architecture.
