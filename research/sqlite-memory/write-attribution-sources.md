# Write-attribution evidence sources

Checked 2026-09-11. These sources define how to interpret the follow-up counters; they do not supply benchmark results or establish physical device writes.

| Measurement | Meaning and limits |
| --- | --- |
| macOS `proc_pid_rusage`, `ri_diskio_byteswritten` | Apple's current XNU [`fill_task_io_rusage`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/bsd_kern.c#L1295-L1310) takes the task lock and reports `task_io_stats->total_io.size - disk_reads.size`; unavailable task I/O statistics produce zero. [`gather_rusage_info`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L3385-L3388) fills these fields for V2 and later flavors. Treat a before/after difference as kernel-accounted bytes attributed to that process over the interval. It has no database/journal/path attribution and is not a sum of SQLite calls. A zero delta alone does not prove no I/O. |
| SQLite `SQLITE_DBSTATUS_CACHE_WRITE` | Counts dirty cache pages written to the main database in rollback mode or WAL in WAL mode. It excludes rollback/recovery writes; its behavior after a write error is undefined. It is a page count, not a count of filesystem calls or total filesystem bytes, and omits rollback-journal records and synchronization. Multiplication by page size estimates this particular page-write category only. [`Database status parameters`](https://sqlite.org/c3ref/c_dbstatus_options.html#sqlitedbstatuscachewrite) |
| Native VFS wrapper | SQLite's [`xOpen` flags](https://sqlite.org/c3ref/vfs.html) identify `MAIN_DB`, `MAIN_JOURNAL`, `WAL`, and other file classes. Accumulate [`xWrite`](https://sqlite.org/c3ref/io_methods.html) byte arguments per class, distinguishing requested/failed writes from successful requests; count `xSync` calls and flags separately. These are requests at SQLite's native-VFS boundary. A lower layer may split, retry, buffer, or combine them. File growth is different again: repeated writes to one offset add traffic without adding file length. |

## DELETE/EXTRA interpretation

In the ordinary rollback-journal commit path, SQLite records original page images in the journal, synchronizes the journal before overwriting protected database pages, writes modified database pages, synchronizes the database, and deletes the journal to commit. Large transactions can spill before the final commit; the journal must protect those overwrites too. Journal headers and record metadata add bytes, while new pages beyond the original database size need not each have a before-image. Exact counts depend on the workload and VFS capabilities, so do not assume one payload write plus one equal-sized journal write. See [Atomic Commit sections 3.5–3.11 and cache spill](https://sqlite.org/atomiccommit.html).

[`synchronous=EXTRA`](https://sqlite.org/pragma.html#pragma_synchronous) adds synchronization of the containing directory after unlinking the rollback journal in DELETE mode. Consequently, counting only file `xSync` calls misses a requested directory sync: record `xDelete` and its `syncDir` argument too. The native VFS may perform that directory synchronization internally. On macOS, [`fullfsync`](https://sqlite.org/pragma.html#pragma_fullfsync) selects `F_FULLFSYNC`; preserve the selected setting and native delegation. Sync-request counts do not establish how many hardware flushes occurred or qualify power-loss durability.

With effective `journal_mode=DELETE`, this experiment uses rollback journaling: there is no WAL append/checkpoint cycle to explain measured writes. SQLite documents WAL as a distinct [journal mode](https://sqlite.org/pragma.html#pragma_journal_mode). Record any WAL-class opens/writes as an unexpected observation to investigate, not ordinary DELETE-mode cost.

## Boundaries of attribution

Report three separate views: cache pages written, VFS bytes by file class plus sync/delete requests, and operation-interval process I/O deltas. Their differences are observations, not an exact residual labelled filesystem overhead. The process interval can include scratch/output writes and kernel accounting outside the wrapped SQLite files; buffering and accounting timing can cross operation boundaries. Place samples around explicitly named operations and retain post-operation samples rather than forcing equality between counters.

The XNU source above is pinned to current upstream commit `f6217f891ac0bb64f3d375211650a4c1ff8ca1ea`, not proven identical to the measured macOS 15.7.7 kernel. Its implementation establishes the accounting category, not a version-independent promise of exact attribution. **None of these counters measures physical SSD/NAND writes** or controller write amplification. A claim about device wear would require separate device-level evidence; do not derive it from VFS bytes or the kernel field's name.
