# SQLite memory evidence sources

Checked 2026-09-10 against current official documentation. These are dependency facts and experiment interpretations, not an amendment to `ARCHITECTURE.md` or proof that the production runtime implements its selected contract. The checkout pins SQLite 3.53.4 (`build.zig.zon`); `build.zig` currently sets `SQLITE_THREADSAFE=0`, whereas the accepted storage contract selects thread-safe SQLite.

| Question | Documented behavior and consequence for this experiment |
| --- | --- |
| Hard heap limit | [`sqlite3_hard_heap_limit64`](https://sqlite.org/c3ref/hard_heap_limit64.html) limits SQLite heap across connections in the process and causes allocation failure at the limit. It is not an application-memory or process-footprint limit. Documented enforcement exceptions include zero limit, disabled memory accounting, alternative page-cache implementation, and a separately supplied page-cache pool. Query the effective limit and force an allocation failure; successful configuration alone proves neither enforcement nor successful cleanup. |
| Zero-filled admission | [`sqlite3_bind_zeroblob`](https://sqlite.org/c3ref/bind_blob.html) represents zero-filled content with fixed memory while processing, specifically for later incremental writes. This describes the placeholder, not the complete SQL plan, pager working set, or every expression that consumes it. `SQLITE_TRANSIENT` bindings copy their input; binding a complete payload that way would invalidate a claim of bounded application intermediates. Reset does not clear bindings. |
| Incremental content handles | [`sqlite3_blob_open`](https://sqlite.org/c3ref/blob_open.html) opens TEXT/BLOB by rowid; it cannot resize a value, operate on WITHOUT ROWID tables, or write indexed/key columns. Every opened handle needs closing. Updating any column of its row expires the handle; subsequent I/O returns `SQLITE_ABORT`, but expiration does not undo already written bytes. Therefore close a writable handle before updating publication metadata, and roll back the enclosing transaction on failed import. |
| RETURNING | [`RETURNING` processing order](https://sqlite.org/lang_returning.html#processing_order) accumulates all returned output in memory before emitting rows. Returning payloads or many rows directly creates a memory multiplier. A scalar `RETURNING id` does not itself prove a payload-sized allocation; if that occurs with a zero-filled insert, it is a measured/version-specific execution-path result requiring source or allocation evidence, not a general documented guarantee. |
| Complete-row access | [`sqlite3_column_blob`](https://sqlite.org/c3ref/column_blob.html) exposes the complete column value and length, not an offset/length reader. Slicing that pointer afterward cannot establish streaming. SQLite owns its lifetime until conversion/step/reset/finalize; conversions can allocate. A NULL pointer can indicate zero-length BLOB, SQL NULL, or conversion OOM: inspect the error immediately where ambiguity matters. Measure peak around `step` as well as column access, because materialization may precede retrieval. |
| Dirty-page spill | [`cache_size` and `cache_spill`](https://sqlite.org/pragma.html#pragma_cache_spill) distinguish a suggested cache capacity from a spill minimum: spilling requires exceeding both thresholds. Disabling spill or retaining a larger spill threshold can allow dirty-page growth despite a small cache setting. Cache size is per open database file. Spill may acquire an exclusive lock. Read settings back and measure dirty-page spill/cache bytes during a large single transaction; a setting is not a global allocation bound. |
| Failure atomicity | [`Response to errors within a transaction`](https://sqlite.org/lang_transaction.html#response_to_errors_within_a_transaction) says FULL/NOMEM/IOERR/INTERRUPT may roll back either the statement or the entire transaction. Inspect autocommit/transaction state and explicitly roll back an active transaction; never infer full rollback from the error alone. Open BLOBs count as unfinished statements. Verify prior committed content and absence of incomplete publication after reopen. This is API failure evidence, not power-loss qualification. |
| Rowid instead of RETURNING | [`sqlite3_last_insert_rowid`](https://sqlite.org/c3ref/last_insert_rowid.html) reports the latest successful rowid insert on the connection, including an insert later rolled back; failed inserts can leave an earlier value. Concurrent inserts on the same connection make it unpredictable. Under this prototype's single connection owner, ordinary rowid table, no triggers/virtual-table inserts, and immediate retrieval only after successful insertion, using it avoids a RETURNING result without changing inserted content. It is not a committed-content identity until commit. |
| Thread safety | [Threading modes](https://sqlite.org/threadsafe.html) make clear that `THREADSAFE=0` omits mutex code and cannot be upgraded at startup. Single-owner connections are compatible with a thread-safe build; a prototype selecting that build preserves the contract rather than benchmarking mutex removal as an improvement. It still does not qualify concurrent owner integration. |

The experiment must separately account for application buffers, SQLite live/high-water heap, cache/statement ownership, retained idle allocations, process physical footprint, and journal/database growth. Neither the hard heap API nor incremental BLOB documentation promises constant total memory for arbitrary payload sizes or schema/query shapes. Any flat or growing curve in the results applies only to the recorded build, representation, workload and tested population.

## Pinned source: incremental cursor metadata scales with value size

Inspected the downloaded SQLite **3.53.4** amalgamation, `generated/sqlite/N-V-__8AAGVtrgCcOcmjrOJnagmnRyMrcKaOo09KbU-vu8w8/sqlite3.c`; its SHA-256 is `b1dd5d74ec7f29055a6684fa06fb3c2f6821c87dd38f9a458dfd2e8a1db28189`, recorded with dependency/package and checkout provenance in [provenance.json](provenance.json). This is pinned implementation evidence, not an API guarantee for other releases.

At lines 78409–78435, incremental payload access maintains `BtCursor.aOverflow`, a lazily populated array indexed by overflow page. It calculates `nOvfl = ceil((payload_bytes - local_bytes) / (usable_page_bytes - 4))` and, when allocation/growth is needed, requests `nOvfl * 2 * sizeof(Pgno)` bytes. `Pgno` is `u32` (line 16830), so the request is **8 bytes per overflow page**. Allocation failure returns `SQLITE_NOMEM`. The multiplier is per simultaneously open cursor, not per committed content row. The array can be retained/reused while that cursor remains open; `sqlite3BtreeCloseCursor` frees it at line 78075. `sqlite3_blob_close` finalizes its internal statement at lines 106351–106368, providing the BLOB-handle release path.

The normal thread-safe, one-row, spill-enabled, no-RETURNING cases in [results.json](results.json) show SQLite peaks of **424,944 bytes for 16 MiB** and **523,248 bytes for 64 MiB**. The 64 MiB case's largest allocation is **131,200 bytes**, consistent with the overflow-page array; loaded live memory is **359,408 bytes** in both cases after the write cursor closes, and connection close returns SQLite live allocation to zero. This explains a value-size-dependent transient allocation without a complete payload copy. Incremental BLOB I/O therefore supports bounded application buffers here, but does **not** provide constant SQLite memory as value size grows. These aggregate measurements plus source support the attribution; they are not an allocation stack trace.
