# HTTP transport alternatives

Research checked 2026-09-11 against official APIs and pinned source. **Keep pinned libcurl as the accepted baseline following its supported-settings experiment. If it cannot qualify, probe direct nghttp2/OpenSSL next. AWS CRT is the strongest complete-client candidate found for receive control, but its fatal allocation policy blocks straightforward adoption. Both expose independent receive-credit controls. Neither has demonstrated OnePage's whole-Host memory, latency, security or recovery guarantees.** This report changes no accepted contract or production transport.

For example, when capture storage stalls, the desired behavior is to stop granting capacity for more response bytes, keep other eligible streams and controls progressing, retain every byte already accepted, and finish cancellation only after its remaining consumers are safe. A small application queue alone does not establish that behavior throughout a library.

## Baseline and scope

[Architecture](../../ARCHITECTURE.md#platform-capabilities) selects bundled pinned libcurl/OpenSSL, asynchronous resolution, Apple SecTrust on macOS, Linux host CAs and explicit CA-file configuration. [Verification](../../VERIFICATION.md#canonical-gates) separates source/prototype evidence from production qualification. Default Active Capacity is 1,000 shared executions/cleanup; the whole-Host reference ceiling is 256 MiB, with p95 durable control acknowledgement ≤1 second. Preserve completed request staging, full capture, custody through pending I/O, and core-owned admission/retry/recovery. No library-driven effect replay is permitted by this investigation.

## Completed curl adjustment evidence

The [final adjustment report](https://github.com/DivyanshGolyan/onepage/blob/36daff7cf11880e59b61be2fc29306b32444e377/research/transport-memory/adjustment-README.md), read from the sibling checkout at that commit, strengthens the curl-first recommendation. Its validators report 55 successful capacity cases / 65 bursts and three sanitizer smoke cases. For 1,000 staged 1 MiB requests with 9,493-byte SSE responses (110.46× illustrative ratio), 16 versus 64 KiB upload buffers achieved 31.38 versus 31.20 MiB/s through the shaped relay; client physical peaks were 90.5 versus 152.7 MiB and curl allocation peaks 82.9 versus 129.8 MiB. Growing/shrinking requests and overlapping upload/download with stalled capture also completed. These are synthetic full-byte checks, not real provider lowering or compaction qualification.

Receive settings remain tradeoffs: at 1,000 streams with 384 KiB responses and 1 ms sink writes, unlimited / 32 / 128 KiB/s settings measured 311.1 / 119.8 / 289.8 MiB physical, with similar capture-limited duration. The 32 KiB/s setting adds roughly one second of terminal lag in the fast paced profiles. Aligned ten-connection/100-stream partitioning improved measured paced retention while preserving the all-active barrier. None establishes a hard memory bound or a universal rate. Large HTTP/1.1 uploads at 1,000 connections failed with ENOBUFS, including the requested 16 KiB socket-send-buffer experiment; no working H1 capacity or remedy was demonstrated. The relay models application delivery delay/bandwidth, not WAN TCP/kernel behavior. Durable controls, replay prevention and production recovery remain unqualified. These results justify continued curl work before replacement, without changing the alternatives' API findings.

## Shortlist

| Candidate | Actual receive control | Remaining buffers/accounting | Integration and maintenance cost |
| --- | --- | --- | --- |
| Pinned libcurl/OpenSSL/nghttp2 | Public pause/unpause and rate controls; no independent public H2 receive-window setter identified in 8.22.0. Previously advertised credit survives a pause. | Paused stream data, TLS, headers, connection caches and resolver allocations; application queue is only one owner. | Lowest change cost; existing C ABI, HTTP/1.1/H2, DNS, trust integration and connection lifecycle. Supported settings still need measurement. |
| Direct nghttp2 1.70.0 + OpenSSL | Disable automatic updates; independently consume stream and connection bytes after capture releases capacity. Application supplies bounded parser input. | HTTP/2 metadata/HPACK/control queues, input/output windows, TLS/CA/session allocations, DNS, sockets and allocator retention remain separate. | HTTP/2 protocol engine, **not a complete client**. Same main dependencies as the curl experiment, but OnePage owns substantially more client code and security-sensitive lifecycle. |
| AWS CRT `aws-c-http` | Both manual stream and connection modes, separate update APIs, configurable initial stream credit. | Channel/TLS pools, headers/HPACK, frames and dependency allocations remain; default connection auto-credit is enormous unless separately disabled. | Complete asynchronous C HTTP/1.1/H2 client. Less missing client code than direct nghttp2, more dependencies and a different TLS integration. Best complete-client credit API found, but fatal OOM is an adoption blocker. |

H2O was screened out below for concrete buffering and failure behavior. No popularity-based list is useful here.

## What libcurl still buys, and what settings do not prove

The [pause contract](https://curl.se/libcurl/c/curl_easy_pause.html) explicitly documents buffering on multiplexed connections and synchronous callback delivery during unpause. The [8.22.0 H2 implementation](https://github.com/curl/curl/blob/curl-8_22_0/lib/http2.c#L308-L344) adjusts desired credit when paused, but cannot recall data already authorized. Smaller upload buffers demonstrably helped the sibling experiment; receive buffer size, rate limits and partitioning are different controls, with throughput/connection/TLS costs. A nominal rate is not an independent static receive-memory budget, especially across repeated unpause.

[curl_global_init_mem](https://curl.se/libcurl/c/curl_global_init_mem.html) provides curl allocation hooks, which must be thread-safe with the threaded resolver. These do not by themselves account for all TLS/system allocations. Its existing Apple SecTrust integration and protocol coverage avoid a substantial replacement burden. Keep callback work nonblocking with respect to slow capture, retain request/header storage through teardown, and measure complete library-call occupancy, not just callback duration.

No-replay is a separate gate: [Curl_retry_request](https://github.com/curl/curl/blob/curl-8_22_0/lib/transfer.c#L592-L657) contains dead-reused-connection and REFUSED_STREAM replay paths. Disabling an application retry loop is insufficient evidence. Test staged POSTs under those conditions, including failure before/after upload; do not claim curl already meets this constraint or use reconnect replay to improve a comparison.

## Direct nghttp2: control demonstrated, client still missing

The exact mechanism is [no automatic WINDOW_UPDATE](https://nghttp2.org/documentation/nghttp2_option_set_no_auto_window_update.html), with [consume](https://nghttp2.org/documentation/nghttp2_session_consume.html) or independent connection/stream consumption. Set SETTINGS_INITIAL_WINDOW_SIZE before requests, retain the protocol's initial 65,535-byte connection credit or deliberately increase it, and replenish only when equivalent capture capacity becomes reusable. Stream credit and aggregate connection credit constrain different populations. Never return stream credit merely because a borrowed callback was copied into an already-charged queue.

The [pinned consumption implementation](https://github.com/nghttp2/nghttp2/blob/v1.70.0/lib/nghttp2_session.c#L5141-L5192) batches updates from consumed counters. Small credit can constrain throughput over long RTTs; withholding aggregate credit can stall peers if one slow stream occupies all of it. Fair credit allocation and capacity for already-advertised bytes are integration obligations. With no automatic application-DATA replenishment, compliant outstanding DATA is limited by aggregate connection credit and the sum of stream credits; this is **not** a whole-library byte bound. Headers/control frames are not DATA-flow-controlled, and padding/discard paths need separate accounting. A later local window reduction cannot recall earlier wire credit.

The [protocol probe](credit_probe.c), run with [run_credit_probe.py](run_credit_probe.py), uses two real in-memory nghttp2 sessions and two 256 KiB deterministic response streams. It verifies each byte against position-derived expected content. Manual mode stops each at 16 KiB; connection-only consumption cannot reopen either stream; consuming stream 1 permits it to progress while stream 2 stays stopped. Both later complete without loss. The automatic-mode negative control completes without application consumption. [Results](credit-results/results.jsonl) and [metadata](credit-results/metadata.json) record the actual run. This isolates API behavior; it is not a socket/TLS, slow-scratch, 1,000-stream, allocator, latency, cancellation or recovery experiment.

[session_mem_recv2](https://nghttp2.org/documentation/nghttp2_session_mem_recv2.html) processes caller-supplied input and permits callback pause. Feed bounded chunks and retain unconsumed input; a callback pause affects parsing of that connection, so it is not a substitute for per-stream credit. [session_client_new3](https://nghttp2.org/documentation/nghttp2_session_client_new3.html) accepts a custom session allocator; callback/option objects and all other libraries still need their own owners. HPACK tables, outgoing headers, retained stream metadata and ACK/control queues require explicit accounting and flood behavior; [continuation](https://nghttp2.org/documentation/nghttp2_option_set_max_continuations.html) and [outbound ACK](https://nghttp2.org/documentation/nghttp2_option_set_max_outbound_ack.html) options are protection mechanisms, not permission to truncate semantic provider input. Allocation exhaustion must fail explicitly and preserve cleanup.

The missing client work is material:

- Own asynchronous DNS, addresses/connect attempts, sockets, timers, ALPN, connection pooling and peer stream limits. Retain 1,000 actually dispatched streams in comparisons; pending requests are not equivalent concurrency. nghttp2 does not supply H1 fallback or proxy CONNECT; implement only justified protocol needs, or a combined path whose total complexity is honestly counted.
- Configure OpenSSL peer verification, hostname verification via [SSL_set1_host](https://docs.openssl.org/3.6/man3/SSL_set1_host/), SNI, Linux CA loading/explicit files and Apple SecTrust integration. OpenSSL alone does not recreate curl's SecTrust glue. A TLS handshake succeeding is not proof hostname/trust configuration was correct.
- Handle nonblocking [WANT_READ/WANT_WRITE and retried I/O arguments](https://docs.openssl.org/3.6/man7/ossl-guide-tls-client-non-block/), partial encrypted writes and TLS shutdown under the connection owner. [OpenSSL allocation hooks](https://docs.openssl.org/3.6/man3/OPENSSL_malloc/) require early initialization; native trust/resolver/kernel allocations remain outside them. Bound caches and account retained memory separately from live bytes.
- Feed completed request scratch through the [request data provider](https://nghttp2.org/documentation/nghttp2_submit_request2.html), preserving source lifetime and deferring slow reads rather than blocking the control owner. Capture raw body chunks fully; SSE framing/termination remains provider interpretation work. A bounded parser input does not cap TLS, DNS or filesystem call latency.
- [RST_STREAM](https://nghttp2.org/documentation/nghttp2_submit_rst_stream.html) requests cancellation; it neither proves remote termination nor releases pending scratch/TLS consumers. Retain request, callbacks and queued output until their final consumer. OnePage owns GOAWAY/error mapping and must never resubmit effects internally. Session destruction must follow safe I/O detachment.

nghttp2's [MIT-licensed C library](https://github.com/nghttp2/nghttp2/tree/v1.70.0) can be built library-only; OpenSSL 3.x uses Apache-2.0. This avoids introducing CRT's dependency graph, but moves maintenance into OnePage: protocol interoperability, trust integration, race/OOM tests and security updates. Smaller dependency count does not establish smaller total implementation.

## AWS CRT and screened alternatives
Pinned upstream HEAD: `2b563f8a7bd67a902a8b558bb44113748045877c`; aws-c-io inspected at `c2d222b73000ddcc5aeed837f4434560a47bad47`. These are observed source pins, not a tested compatible dependency lock.

Unlike an application-managed HTTP/2 protocol engine, this C99 HTTP/1.1 and HTTP/2 client includes async connection setup, request/response streams and integration with CRT DNS/socket/TLS/event loops. Zig can use the C ABI. Its Apache-2.0 source and CMake build require aws-c-common, aws-c-cal, aws-c-io and aws-c-compression; the documented Linux route adds aws-lc and s2n-tls. This is considerably more dependency surface than nghttp2/OpenSSL, but substantially less HTTP-client implementation work. [README](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/README.md)

**The exact needed credit APIs exist.** Set both `aws_http_client_connection_options.manual_window_management=true` and `http2_options.conn_manual_window_management=true`. The first controls stream credit using `initial_window_size` (including zero, emitted as SETTINGS_INITIAL_WINDOW_SIZE); the second retains HTTP/2's initial 65,535-byte connection credit. Replenish stream credit with `aws_http_stream_update_window()` and aggregate connection credit with `aws_http2_connection_update_window()` only after capture ownership releases equivalent capacity. Configurable thresholds batch WINDOW_UPDATE emission. Headers are outside this body-credit budget; padding is automatically replenished. Enabling stream control alone is insufficient: automatic connection mode expands credit to 2^31-1. [Options and contracts](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/connection.h#L223-L259), [stream options](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/connection.h#L340-L374), [automatic connection expansion](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/source/h2_connection.c#L1853-L1862).

This demonstrates a public mechanism for aggregate DATA credit that the libcurl pause experiment lacks. It does **not** demonstrate a whole-library memory bound. H2 deliberately keeps the underlying channel read window open to service protocol frames. TLS records, socket/channel message pools, HPACK/headers, outbound frames, per-stream metadata, DNS and crypto allocations require separate budgets. Non-DATA input can keep the event loop busy while DATA is stopped. SETTINGS exchange timing, zero initial stream credit and a malicious/noncompliant peer require tests. [Read path](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/source/h2_connection.c#L2637-L2675)

**Allocator exhaustion is a known mismatch, not merely untested:** inspected aws-c-common `aws_mem_acquire()` calls `AWS_PANIC_OOM` on NULL, defined as `abort()` in ordinary builds. A rejecting custom allocator cannot return an ordinary typed capacity failure through this path. CRT needs a demonstrated bounded-allocation design with reservation before admission, or a maintained change to failure behavior; crash recovery does not make process-abort capacity handling acceptable. [Allocation path](https://github.com/awslabs/aws-c-common/blob/c4803685d3df70b1b2e0b929aeebf65e60c3847f/source/allocator.c#L201-L210), [abort definition](https://github.com/awslabs/aws-c-common/blob/c4803685d3df70b1b2e0b929aeebf65e60c3847f/include/aws/common/assert.h#L30-L38). aws-c-io installs s2n allocator hooks only when initializing s2n itself; externally initialized s2n bypasses them. The s2n bridge assumes `aws_mem_acquire` succeeds, consistent with that fatal contract; initialization also includes fatal assertions. Backend allocation attribution still needs audit. [s2n allocation and initialization](https://github.com/awslabs/aws-c-io/blob/c2d222b73000ddcc5aeed837f4434560a47bad47/source/s2n/s2n_tls_channel_handler.c#L246-L294)

Each connection has one event-loop thread for callbacks. Blocking scratch writes in those callbacks still block its work; bounded capture offload and completion-to-credit handoff remain necessary. Request scratch can be supplied as `aws_input_stream`; the message does not own it, and it must survive message completion. SSE remains OnePage parsing/capture work over streamed body chunks. Stream completion is distinct from destruction, and release does not cancel. Cancellation closes H1 or resets H2; preserve callback/request/capture custody through completion/destruction and connection shutdown. [Callback ownership](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/request_response.h#L163-L222), [body ownership](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/request_response.h#L938-L947), [release/window/cancellation](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/request_response.h#L1148-L1238)

TLS exposes peer verification and server-name configuration for SNI **and** X.509 validation; both need secure integration. macOS can use Apple Security or s2n, whereas documented Linux builds use s2n: trust-store, hostname, certificate failure and allocation results must be qualified per backend. Explicit proxy options and environment proxy selection exist; choose only accepted provider transport behavior, not every supported feature. [TLS verification API](https://github.com/awslabs/aws-c-io/blob/c2d222b73000ddcc5aeed837f4434560a47bad47/include/aws/io/tls_channel_handler.h#L689-L694), [hostname](https://github.com/awslabs/aws-c-io/blob/c2d222b73000ddcc5aeed837f4434560a47bad47/include/aws/io/tls_channel_handler.h#L780-L787), [backend selection](https://github.com/awslabs/aws-c-io/blob/c2d222b73000ddcc5aeed837f4434560a47bad47/CMakeLists.txt#L125-L143), [proxy options](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/include/aws/http/connection.h#L311-L325)

Use direct connection/stream APIs, not SDK retry layers. On received GOAWAY, the inspected implementation completes affected streams with AWS_ERROR_HTTP_GOAWAY_RECEIVED and tells the caller to retry; it does not replay there. This supports explicit core-owned failure, but is not an exhaustive proof of all reconnect/request paths. Qualification must assert one request dispatch under GOAWAY, REFUSED_STREAM, connection loss, authentication rejection and proxy failure. [GOAWAY completion](https://github.com/awslabs/aws-c-http/blob/2b563f8a7bd67a902a8b558bb44113748045877c/source/h2_connection.c#L1750-L1774)

### H2O client: screened out

Inspected upstream HEAD `cac7e6568ad98a848f099ecd0a18b881f632479a`. Its HTTP/2 client exposes `update_window`, but this derives stream credit from `max_buffer_size - buffered_body_size`. DATA is copied into a per-stream body buffer; the connection independently and automatically replenishes a compile-time 16 MiB window. Therefore it supplies per-stream buffer-oriented backpressure, not AWS CRT's explicit aggregate capture-credit control. Across 1,000 streams the configured per-stream allowance remains a population multiplier. Its allocation helpers include abort-on-failure `h2o_buffer_append`, used directly in this response path. These are concrete reasons to rank it below CRT for OnePage before undertaking broader TLS/proxy/retry qualification. [connection constant and response buffering](https://github.com/h2o/h2o/blob/cac7e6568ad98a848f099ecd0a18b881f632479a/lib/common/http2client.c#L575-L601), [stream update](https://github.com/h2o/h2o/blob/cac7e6568ad98a848f099ecd0a18b881f632479a/lib/common/http2client.c#L1396-L1403), [fatal allocation contracts](https://github.com/h2o/h2o/blob/cac7e6568ad98a848f099ecd0a18b881f632479a/include/h2o/memory.h#L293-L312)

## Targeted next qualification

The recommendation remains conditional: continue curl integration investigation using the completed adjustment evidence below. If its retained/live footprint and control responsiveness fit with adequate whole-Host margin, staying avoids replacing an already-selected transport. If it still lacks a usable bound, probe direct nghttp2 with TLS/capture next. Keep CRT as the complete-client comparison only after resolving its fatal-OOM mismatch and dependency/trust costs. Source APIs and the protocol probe justify this comparison, **not migration**.

Use the same 1,000-request barrier, fully staged requests, independent full-output verifier, delayed/late-stalling capture and repeated bursts. Measure actual connection/stream credit, received/accepted/written bytes, all allocator families, retained pools/handles, physical footprint and complete call/control delays. Vary peer stream limits, body size, item/event count and connection count independently. One fixed small connection window is a throughput experiment, not a new product limit. Judge headroom against paced provider SSE, not bulk-download throughput: the completed adjustment report measures actual event-size/batching, captured-wire-byte and capture-latency behavior. Its 100–1,000 output-token/s range is a workload assumption, with roughly 400–4,000 text bytes/s per stream before SSE/JSON/TLS overhead and variable token encoding; it is not measured provider capacity. Retain burst/stall cases to test safety, but do not select a replacement or larger caches merely for higher bulk MiB/s.

Large uploads must be varied independently of slow responses. The user's illustrative 100× request/response ratio is not a measured constant: repeated turns resend required context according to accepted history lowering and compaction, and provider cache reuse must not be counted as omitted wire bytes without evidence. Add growing-context turns with large, integrity-checked staged requests and small paced SSE responses, overlapping uploads/downloads at unchanged concurrency while capture slows. Measure upload throughput, request-completion time and its contribution to time to first token separately from provider processing; also record response/control latency, simultaneous TLS/library/application memory, disk read/write volume and complete request/response byte totals. Check smaller upload buffers under realistic RTT/link constraints; low output rate and bulk-download results alone cannot select them.

This leaves the shortlist unchanged. The cited nghttp2 data-provider and CRT input-stream APIs support staged request streaming; the missing evidence is bounded asynchronous scratch-read delivery, fair bidirectional scheduling and retained request/TLS buffers under overlap, rather than another client capability. Preserve completed staging and no automatic replay. The curl adjustment report owns this additional workload comparison; no alternative benchmark was rerun for this clarification.

Then falsify the missing guarantees: certificate/hostname/CA failures and SecTrust; ALPN/H1 compatibility; huge/compressed headers, padding/control floods and oversized frames; allocation failure across dependencies; request reads and capture writes held through cancellation; partial TLS writes and late callbacks; GOAWAY/REFUSED_STREAM/dead reuse/auth rejection with independently counted dispatches; sink failure after network completion; complete cleanup and burst reuse. Recovery must still use committed facts and core-owned retry, never surviving scratch or a client's reconnect state. Integrated durable acknowledgements and production recovery require the real Host, not this probe.

**Platform limits:** only the tiny protocol probe executes here on macOS ARM64. No CRT or replacement HTTPS client was built; Linux behavior and cross-compilation are unexecuted. Existing sibling Mac curl results do not transfer to these alternatives. No live provider traffic, production migration, contract changes or power-loss qualification occurred.

## Reproduce source and protocol evidence

Pinned links above identify source revisions rather than assuming online development manuals are identical to a release. [source-evidence.json](source-evidence.json) records retrieved source URLs, SHA-256 and checked mechanism symbols; rerun `python3 research/transport-client-alternatives/audit_sources.py --verify` to retrieve and check the same bytes. This is a source provenance check, not compilation or behavioral proof. CRT's three inspected source pins are not a resolved compatible dependency graph.

For the credit probe, use the nghttp2 1.70.0 static build from the sibling transport experiment (its builder verifies release archive SHA-256 `e05cb1388eaca3830aded4ccf20044b6e1ac1a61411dcca11b0437c4285c8bc2`), then run:

```sh
python3 research/transport-client-alternatives/run_credit_probe.py --prefix /tmp/onepage-transport-memory-build/ng --output /tmp/new-credit-results
```

The runner refuses an existing output directory, serializes compilation/execution with `/tmp/onepage-memory-experiments.lock`, and bounds compilation and execution time. It records compiler, source/library/binary hashes and platform. The probe does not measure allocation peaks, and its library was not sanitizer rebuilt. Body bytes are generated and checked by position without whole-body buffers; assertion failures fail the run. Documentation validation checks references and `git diff --check`; production gates are unrun because production/build/contract code is unchanged.
