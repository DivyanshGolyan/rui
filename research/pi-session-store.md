# Mapping pi session JSONL onto Rui's Store

Part of #2034, answering #2037. Inspected 2026-11-23 against pi 1.6.0 (`@earendil-works/pi-coding-agent`, `pi-ai`, `pi-agent-core` 1.6.0 tarballs, unpacked locally) and Rui at `5a6b6e5` (Store schema 88, `src/store/schema.zig`). This is source reading only: nothing was run, and no Store was written.

**Sample files.** No real pi session file exists on the research box (searched `~/.pi`, the project mounts and the unpacked packages, which ship none). Every shape below comes from pi's docs and code, not from a captured session. Entries marked *(inference)* follow from reading Rui's contract or schema and have not been exercised.

Paths: `PI` = `pi-coding-agent-1.6.0/package`, `PIAI` = `pi-ai-1.6.0/package/dist`.

## Result in one paragraph

Rui's Store has no door that accepts prior history. `docs/contracts/admission.md` (line 74) says "V1 has no fork, history transfer or cross-provider handoff", and `ARCHITECTURE.md` (line 147) excludes conversation branching and says a future fork "creates a new Session with ancestry". Conversation entries exist in three kinds only (`conversation_entry.entry_kind`): a User Message admission, a System Instruction from a settings revision or skill catalog, and an assistant output item owned by a resolved model Operation (`src/store/schema.zig`). Tool Results are not entries: they are derived from the Action Resolution or call rejection that joins a Tool Call (`docs/contracts/execution.md`, "No copied Tool Result ... is durable authority"). So a faithful migration needs a new, contract-level import path that writes synthetic Operations, Actions and revisions; that is a Store-format and contract change, not a mapping. Text-only user and assistant history, plus pi's own compaction and branch summaries as plain user text, maps cleanly. Everything that depends on pi's tool set (`read`, `edit`, `write`, `grep`, `find`, `ls`), on non-OpenAI providers, on the tree, or on session-level bookkeeping is lossy or has no home. Replay with the same context as pi's `buildSessionContext` is achievable for the text and OpenAI-Responses subset and not otherwise; details in [Replay fidelity](#replay-fidelity).

Two target tiers are used in the table:

- **Native**: the Rui Store row an import would have to write.
- **Transcript fallback** *(inference)*: render the projected pi context as text inside ordinary User Message(s) of a new Session. Needs no Store change, is always possible, and keeps no structure.

## Replay fidelity

Question: can Rui replay a migrated session with the same context as pi's `buildSessionContext`?

**Same-context claim holds only for this subset.** Text-only user, custom, bash, summary and OpenAI-Responses assistant text. Even there it is the *messages* that match: Rui does not send pi's system prompt, because it renders its own baseline before saved instructions (`model-io.md`, "Codex wire binding"), and Rui's tool declarations replace pi's. "Same context" therefore means same conversation messages, not same request.

**Non-OpenAI assistant messages.** Rui has one provider family, the OpenAI Responses codec (`src/codecs/responses.zig`, pinned `openai-responses/1`-`/3`), and replays assistant items rebuilt from neutral form plus bag. Text from an Anthropic, Google or Mistral assistant message is plain text and maps to a `message` item (rebuilt with Rui's `status`/`phase`, which are absent in the source, so the item is synthetic; Rui says absence "is not a fabricated phase", so the phase stays unphased). Its `id` would be invented, as pi does with `msg_pi_<n>` when `textSignature` is missing (shared.js ~244). Tool calls from those providers map to `function_call` with their own call ids. Everything provider-specific is opaque and unusable: pi's own cross-model path already strips `thoughtSignature` and (when a normalizer is supplied) rewrites tool call ids, and keeps `text` blocks as bare text (`transform-messages.js`). Rui's equivalent rule is D192: a different requested model keeps visible messages, calls and results and omits reasoning and compaction items.

**Thinking blocks and signatures.**

- *OpenAI-origin, same model*: lossless. `thinkingSignature` is the full reasoning item including `encrypted_content`; pi replays it verbatim (shared.js ~234), Rui's `reasoning` item bag holds the same. Pi's condition is provider + api + model all equal (`transform-messages.js` `isSameModel`); Rui's is the requested model string of the producing Operation's revision. A pi session that ran on `gpt-5-codex` through `openai-codex-responses` and is continued by Rui on a different Codex model loses reasoning in both systems. Qualification caveat (inference): encrypted content from pi's OpenAI API-key route versus Rui's ChatGPT-plan route (`store:false`, explicit `include`) has not been shown to decrypt across routes; Rui itself says "No cross-model continuation is qualified" (`model-io.md`).
- *Anthropic, Bedrock, Google, Mistral, openai-completions*: not replayable by Rui. Pi drops them when the model differs, and a Responses model cannot accept them either. Storing the visible text as private `reasoning_text` parts keeps it readable but never sent. A redacted Anthropic block has no visible text and is only an opaque payload, so Rui keeps nothing useful.
- *Empty-text signed blocks*: pi keeps them if `redacted` or signed (transform-messages.js), Rui needs non-empty `encrypted_content` or fails `continuation_unavailable`. An OpenAI block pi kept for replay will pass; any other will not, and must be pre-omitted at import rather than left to fail at request time.

**Images.** Pi's `ImageContent` is base64 `data` plus `mimeType` in user messages and tool results. Rui accepts PNG and JPEG only, streams them unchanged, checks model capability per attempt and refuses a retained image for a known-negative model with `model_image_input_unsupported` (`model-io.md`, "Ordered Message and Tool Result input"). Pi instead replaces images with a text placeholder when the model lacks vision (`transform-messages.js` `downgradeUnsupportedImages`: "(image omitted: model does not support images)"), and for Anthropic error results moves images after the tool results. So: PNG/JPEG on a vision model replays identically; non-vision or other formats diverge (Rui fails, pi substitutes text). Rui caps 1,500 images and 512,000,000 bytes per request, which a long pi session with screenshots could exceed. Tool-result images additionally need a Rui Action Resolution to hold them (see `toolResult` row).

**Tool call ids.** Pi's OpenAI ids are `call_id|item_id` and can exceed 450 characters with `|` (comment in transform-messages.js); pi normalizes only when it converts to another provider. Rui keeps call ID and item ID distinct ("Item ID and call ID are distinct", `model-io.md`), so import must split on `|`; a malformed id with no `|` leaves no item ID. Rui requires one result per call (`UNIQUE(operation_id, call_id_content_id)`, `call_ordinal`) and pairs them by position. Pi inserts synthetic `"No result provided"` error results for orphaned calls (transform-messages.js second pass) and moves system messages out from between a call and its result. An import has to reproduce both, or Rui's request preparation will see an unanswered call *(inference)*.

**Compaction and ordering.** A pi compaction summary replays as a user message; Rui replays it as a user message too, so context text is equal. It is not a Rui Compaction Base, so Rui's trigger weighs it as ordinary uncovered bytes, so an imported session can start closer to Rui's compaction trigger than pi's own accounting suggests *(inference)*.

**Not verified.** No Rui import code was written, so none of the "would" claims was run. The OpenAI-route decryption question and `thinkingSignature` parsing against real files are untested.

## pi session versions 1 to 3

Source: `session-manager.js` lines 11-90 and `session-format.md` "Session Version".

| Version | Shape | Differences that matter for import |
| --- | --- | --- |
| **1** | No `version` field in the header (`header?.version ?? 1`); entries have no `id`/`parentId`; entries are a linear list; `compaction` stores `firstKeptEntryIndex` (a position in the file) | Order is the only structure, so the whole file is one branch. Migration assigns random 8-hex ids (`generateId`) and a linear `parentId` chain, then turns `firstKeptEntryIndex` into `firstKeptEntryId` by indexing the entries array. Ids are not deterministic: two migrations of the same v1 file give different ids. |
| **2** | `version: 2`; `id`/`parentId` tree; `compaction.firstKeptEntryId`; assistant extension messages use role `hookMessage` | Tree and multiple roots are possible. |
| **3** (current, `CURRENT_SESSION_VERSION = 3`) | `version: 3`; role `hookMessage` renamed `custom` | Only that rename. |

Version 1 to 3 differ in: id/tree structure (v1 none), compaction cut reference (index vs id), and the extension-message role. Entry types added since (`usage`, `context_edit`, `system` messages, `systemMessage` on compaction, `label`, `session_info`, `thinkingLevel` on assistant messages) did **not** bump the version: they are additive optional fields or entry types in v3, so a v3 header does not tell an importer which of them can appear (`session-format.md` marks `systemMessage` "absent on older session entries"). Consequences for Rui *(inference)*:

- An importer should accept all three and run pi's migrations itself (they are three short in-memory loops), or require pi to open and rewrite the file first. Pi rewrites the file in place on load when a migration ran (`_loadEntries` calls `_rewriteFile`), which is what makes later ids stable. Importing a v1 file directly means Rui generates its own ids; use positional ones and do not claim equality with pi's.
- Without a version bump, tolerate unknown entry `type`s and unknown message `role`s (pi's own docs say consumers "should tolerate unknown custom roles"); Rui's closed-discriminator rule for provider output (`unsupported_provider_output`) should not be applied to pi files.
- Null or missing `content` appears in old, forked or hand-edited files and pi normalizes it to `[]`/`""` (`sessionEntryToContextMessages`, `transform-messages.js`); an importer needs the same.
- Malformed lines are skipped and a missing or non-`session` first line makes the whole file invalid (`loadEntriesFromFile`, `parseSessionEntries`), so import should do likewise, not fail on the first bad line.

## What this implies for Rui

1. There is no Store mapping to write until Rui decides on a history-import or fork door (open decision; owner `docs/contracts/admission.md` and `ARCHITECTURE.md`, both currently exclude it). That decision, not the table above, is the blocker.
2. If imported history is accepted, the natural owner is "one Session per pi leaf", not tree storage: it matches `ARCHITECTURE.md`'s "future fork creates a new Session with ancestry" and loses nothing pi's replay uses.
3. A tool-neutral import (text of user, custom, bash, summaries and assistant messages, with tool calls and results rendered as text) is lossy but needs no synthetic Actions. Faithful tool history would require Actions Rui never ran; that should be a deliberate contract choice, not a side effect.
4. The transcript fallback is available today and keeps pi's own summary text; it needs no Store format step.
