# Terminal line-editing sources

Inspected 2026-09-25. This note is design research, not a contract change or platform qualification. Rui's current contract remains [Inspection and local protocol](../ARCHITECTURE.md#inspection-and-local-protocol).

## Rui boundary

At the research baseline, `src/cli.zig` gave the explicit `rui session` path a 64 KiB stack buffer, changed stdin to noncanonical/no-echo/no-signal mode with `VMIN=1`, discarded unread input with `TCSAFLUSH` before each prompt, and restored saved settings on return. It only edited at the end: Backspace removed one UTF-8 code point; cursor keys, Home/End, word/line deletion and escape sequences did not work. `tests/integration/human_cli_integration.py` already distinguished the PTY-driven Session from prompt-free one-shot commands, including overflow, Ctrl-C, restoration, exact Action display and pre-Action typeahead. This baseline motivated the bounded editor implemented separately; see [ARCHITECTURE.md](../ARCHITECTURE.md#public-operations) for its current ownership. Exact Action rendering and the subsequent exact-target decision remain CLI/Core behavior, not editor behavior.

Any replacement therefore has to be a **CLI-only input adapter**, with no Host or protocol dependency. It must return bytes only after an accepted line, reject rather than truncate input over 64 KiB, and preserve the existing prompt-boundary flush. It must not let a library's history, macro, paste, startup file or queued-input facility turn bytes typed before an Action was displayed into an approval.

## What terminals actually provide

- POSIX terminal input is bytes plus line-discipline state, not macOS key identities. In canonical mode the kernel implements erase/kill and line limits; in noncanonical mode it does not, and `VMIN`/`VTIME` govern reads. `TCSAFLUSH` discards received unread input while applying attributes; `tcflush(fd, TCIFLUSH)` separately discards unread input. See the POSIX-conforming interfaces and semantics in Linux's [termios(3)](https://man7.org/linux/man-pages/man3/termios.3.html) and NetBSD's primary [termios(4)](https://man.netbsd.org/termios.4). NetBSD also documents the conventional `VERASE=^?`, `VWERASE=^W`, `VKILL=^U`, `VEOF=^D`, and `VINTR=^C`; `VWERASE` is a BSD extension, so Rui cannot rely on canonical mode alone for portable word editing.
- GNU Readline's manual describes Meta as either an eighth-bit character or, commonly, an `ESC` prefix generated by the terminal. Its standard Emacs bindings include `M-DEL` (`backward-kill-word`), `C-w` (whitespace-delimited word deletion), `C-u` (delete to line start), `C-a`/`C-e`, arrows/history, and safe consumption of otherwise unknown CSI sequences. [Manual: interaction, bindings and programming API](https://tiswww.case.edu/php/chet/readline/readline.html).
- macOS Terminal exposes **profile-specific** key mappings and a “Use Option as Meta key” setting. Apple's [keyboard shortcuts](https://support.apple.com/guide/terminal/keyboard-shortcuts-trmlshtcts/mac) recommend Ctrl-U to delete a line and Ctrl-W to delete the previous word; they do **not** specify Command-Delete as a portable input sequence. [Apple Terminal Keyboard settings](https://support.apple.com/guide/terminal/change-profiles-keyboard-settings-trmlkbrd/mac).
- iTerm2 likewise says `+Esc` is the usual Option/Meta representation, permits arbitrary profile key mappings (including Cmd combinations), and documents that extended Command/Option reporting only applies when an application and terminal use an extended keyboard protocol. [iTerm2 Keys documentation](https://iterm2.com/documentation-preferences-profiles-keys.html).
- Ghostty's legacy encoder maps [Alt-Backspace to ESC DEL, but Super/Command-Backspace to plain DEL](https://github.com/ghostty-org/ghostty/blob/main/src/input/function_keys.zig#L150-L180), indistinguishable from ordinary Backspace. [Option-as-Alt is configurable](https://github.com/ghostty-org/ghostty/blob/main/src/input/config.zig#L1-L8); a Ghostty [`text` keybinding](https://github.com/ghostty-org/ghostty/blob/main/src/input/Binding.zig#L302-L337) can emit Ctrl-U for Command-Backspace. Ghostty's [grapheme width](https://github.com/ghostty-org/ghostty/blob/main/src/unicode/grapheme.zig#L84-L136) is terminal-side policy, not proof of the child process's displayed cursor across other terminals; its [C API is unstable](https://github.com/ghostty-org/ghostty/blob/main/src/lib_vt.zig#L1-L9).

**Guarantee boundary:** Rui can guarantee behavior for byte sequences it receives, notably `ESC DEL`/`ESC ^H` as backward-word deletion and `^U` as deletion to line start. It cannot guarantee that **Option-Backspace** or **Command-Backspace** reaches Rui: the terminal emulator or macOS may consume or map it differently. Documenting an emulator mapping can make either shortcut work (for example, map it to `ESC DEL` or `^U`), but probing the byte stream cannot reliably recover the original physical modifier. A Kitty/CSI-u keyboard mode would improve key identity only in supporting/configured terminals and would enlarge this task beyond ordinary line editing.

## Established choices

| Choice | Primary-source evidence | Fit and cost for Rui |
| --- | --- | --- |
| **NetBSD libedit (`histedit`)** | The [editline(3) API](https://man.netbsd.org/editline.3) provides `el_gets`, Emacs/vi modes, key binding, history, termcap rendering, locale-aware wide-character input, custom descriptors, signal policy, reset and resize. Returned storage is library-owned and must be copied if retained. The maintained portable distribution describes a Berkeley-style license, UTF-8/wide-character support and `-ledit` plus curses linkage: [thrysoee.dk/editline](https://www.thrysoee.dk/editline/). NetBSD's source carries the permissive license in [COPYING](https://github.com/NetBSD/src/blob/trunk/lib/libedit/COPYING). | Mature editing without GPL coupling, but its public API has **no line-size limit** and its [ordinary insertion automatically grows several buffers](https://github.com/NetBSD/src/blob/trunk/lib/libedit/chared.c#L484-L571). Enforcing Rui's pre-insertion byte bound appears to require a custom reader or a private growth patch; neither is a proven simple adapter. It also adds C, termcap/curses, locale and reproducible packaging work. |
| **GNU Readline** | `readline()` owns terminal preparation/redisplay and returns allocated input; callback mode supports event loops and restores the terminal before invoking a complete-line handler. It supports configurable keymaps, history, UTF-8 according to locale, bracketed paste, terminal reset and signal cleanup. [Programming manual](https://tiswww.case.edu/php/chet/readline/readline.html). Upstream states Readline is GPLv3 and distribution must be GPL-compatible: [official project page](https://tiswww.case.edu/php/chet/readline/rltop.html). | Feature-complete and familiar, but the GPLv3 distribution constraint is a consequential product/license decision. It also has global state and dynamically growing buffers. Do not choose it merely because a developer machine has it. |
| **Linenoise** | Upstream describes a BSD-licensed, single-file editor with history, arrows/Home/End, Ctrl-W/U, UTF-8/grapheme tests, bracketed/large paste and a caller-buffer asynchronous API. [Upstream README/source](https://github.com/antirez/linenoise), [BSD-2-Clause license](https://github.com/antirez/linenoise/blob/master/LICENSE). | Its bounded caller buffer is close to Rui's needs, but [ordinary input past capacity is silently dropped](https://github.com/antirez/linenoise/blob/master/linenoise.c#L1506-L1536); Enter can return a truncated prefix. [Oversized bracketed paste](https://github.com/antirez/linenoise/blob/master/linenoise.c#L1774-L1823) is drained and discarded with a beep, not a typed error. Its decoder and renderer also need work; see the spike below. |
| **fx.sh (Zig agent)** | The [fx source](https://github.com/vercel-labs/fx) maps [ESC-DEL/ESC-BS and extended Alt/Super Backspace](https://github.com/vercel-labs/fx/blob/main/src/ui/input/escape_parser.zig#L394-L445) to semantic word/line deletion, with [Ctrl-U](https://github.com/vercel-labs/fx/blob/main/src/ui/input/shortcuts.zig#L11-L27) as a fallback. Its [paste framing](https://github.com/vercel-labs/fx/blob/main/src/core/input/paste_framing.zig#L17-L36) bounds composer input separately from decision input, and [overflow rejection](https://github.com/vercel-labs/fx/blob/main/src/core/app/input_paste_runtime.zig#L143-L169) discards the whole paste. | Strong reference for keeping keyboard decoding and approval ownership separate, and for testing atomic paste rejection. Its custom editor, keyboard protocols, transcript renderer and 8 MiB composer are a larger UI architecture than Rui's synchronous 64 KiB line; importing its whole design is not the small fix. Super/Command requires terminal support for the extended key protocol. |
| **Keep extending `readTerminalLine`** | POSIX supplies raw bytes and terminal controls, not a portable editor or a universal mapping for modified keys. | Small only while behavior is tiny. Accumulating escape parsing, cursor/display width, history, paste framing, UTF-8 graphemes and ambiguous-sequence timing in the CLI's existing read loop scatters the editing policy. This is distinct from intentionally owning one bounded editor module. |

## Linux feasibility spike

On 2026-09-25, cloned antirez/linenoise at commit [`a473823d`](https://github.com/antirez/linenoise/commit/a473823d74b93eab2ba83480df16ed37617493f2) into a disposable `/tmp` directory and compiled its unmodified `linenoise.c` with `cc -std=c11 -D_DEFAULT_SOURCE -O2`. A C harness called `linenoiseEditStart(&state, 0, 1, buffer, 65537, "probe> ")`, fed until completion, stopped editing and reported `strlen(line)`, the first 16 bytes in hex or `errno`. Python drove it through an 80-column PTY (a zero-width PTY instead stalls in its terminal-width query). These are **stock-library counterexamples**, not Rui behavior or macOS qualification:

| PTY input | Observed | Required for Rui |
| --- | --- | --- |
| `ESC[200~` + 65,536 ASCII `x` + `ESC[201~` + `z` + CR | Accepted `65536` bytes: `z` was silently omitted. Terminal restored. | Reject the whole line, even if overflow is followed by deletion. |
| `first second` + `ESC DEL` + `Z` + CR | Accepted 12 bytes, hex `6669727374207365636f6e64`: word stayed and `Z` was consumed by the ESC parser. | Delete `second` and retain `Z` (7 bytes). |
| Bytes `C3 28` + CR | Accepted bytes `c328`, invalid UTF-8. | Reject invalid input before capture. |
| 65,537 unbracketed ASCII characters + CR | No completion within 25 seconds in this PTY run. | A reasonable paste cost without admitting a truncated prefix. |

The probe initially sent LF like Rui's current PTY fixture, but stock linenoise recognizes CR as Enter in raw mode; a migration would need to account for both. `linenoiseEditFeed` also blocks for more bytes after ESC or a UTF-8 lead byte, and its paste path discards an overlarge paste with a bell without reporting it. The timed unbracketed run is a diagnostic, not a latency benchmark; the source scans the displayed width on ordinary insertion and refreshes at wrap, but the probe did not isolate that cost. A local UTF-8 check after completion would catch malformed output but would not repair incomplete decoder reads or make over-limit input observable. Merely adding an overflow flag therefore does not satisfy the input/terminal boundary.

## Recommended design

1. **Keep the existing CLI-only input boundary until a candidate passes**, rather than vendoring either stock editor or loosening the 64 KiB no-truncation rule. The linenoise spike disproves the narrow overflow-only patch: overflow, escape/UTF-8 decoding, LF compatibility and unbracketed paste cost would all need correction in an owned fork. Libedit's public `EL_GETCFN` reads characters rather than vetoing edits; its history/insertion paths can grow the line and related buffers before a caller checks their length. Neither is currently a small, proven adapter. Prefer a focused bounded CLI editor module, where input decoding, editing decisions, capacity rejection and terminal lifetime have one owner; selectively reuse audited rendering code if that proves simpler than owning it. Keep one-shot/scripted commands unchanged; do not load user macros, enable filename completion or persist approval choices as history.
2. **Keep prompt ownership and authorization outside the editor.** Discard unread input at each prompt boundary with `TCSAFLUSH` or `tcflush(stdin, TCIFLUSH)` as tested, without retaining user-space read-ahead between prompts. At an Action boundary, exact escaped Action presentation and a separate exact-target Host decision remain unchanged. Preserve a fresh editor state for the new prompt; verify that prior pasted `a` cannot approve an Action not yet displayed.
3. **Define a portable minimum keymap:** Backspace/Delete, arrows, Home/End, previous/next history, `C-a/e`, `C-w`, `C-u`, `C-c`, `C-d`, and both `ESC DEL` and `ESC ^H` for backward-word deletion. Explicitly test unknown/truncated escape sequences and Escape timing. History is optional but if enabled must have bounded bytes and entries and exclude Action choices.
4. **Preserve whole-line admission and cleanup.** Never send a truncated message: overflow/invalid UTF-8/unsupported control must reject before capture, including after edits, paste, completion and history recall. Bracketed paste remains data and drains to its closing marker after failure. Restore exact termios state on line acceptance, EOF, interruption, overflow and errors; Ctrl-C detaches at a prompt, Ctrl-D is EOF only on an empty line, and terminal resize must not corrupt the editor. Do not put terminal editing or permission behavior in Host code.

Before integration, complete the PTY gate against the selected candidate on Linux and macOS. Preserve the existing negative typeahead test and add byte-level cases for `ESC DEL`, `ESC ^H`, Ctrl-W/U, arrows/Home/End, UTF-8 graphemes, 65,536/65,537-byte paste, bracketed paste containing newlines/control bytes, unknown/truncated escapes, Ctrl-C/D, resize, every error restoration path, and exact Action display followed by stale-target revalidation. Physical Option/Command key tests belong in optional terminal-specific qualification, not portable PTY tests. Following [Bernhardt's *Boundaries*](https://www.destroyallsoftware.com/talks/boundaries), test bounded editing decisions without terminal doubles, then use the PTY to verify the input/approval handoff; do not treat a pure parser test as terminal or Host evidence.

## Limits and unverified assumptions

- **Unverified:** a maintained fork could correct every insertion source and distinguish EOF/interrupt without replacing much of the decoder/renderer; no candidate has passed the full gate. The Linux stock spike above is a counterexample, not a measurement of a patched editor or a Mac-native run. [Linenoise's partial UTF-8 reads](https://github.com/antirez/linenoise/blob/master/linenoise.c#L2033-L2049), [escape handling](https://github.com/antirez/linenoise/blob/master/linenoise.c#L1965-L2005) and paste normalization need explicit qualification.
- **Unverified:** either library's default unknown-CSI handling and `ESC ^H` binding; install/test explicit behavior rather than relying on defaults.
- **Unverified platform packaging:** Apple commonly provides libedit and Linux distributions package it, but neither fact is a portable build guarantee. A Zig 0.16 C-link/build prototype is still required, including static/dynamic linkage and curses/termcap license notices.
- No cited source makes Command-Backspace portable. Rui can publish Terminal.app/iTerm2 setup examples, but cannot override profile settings, macOS shortcuts, SSH hops, multiplexers or remote terminal translations.
- “UTF-8 support” does not by itself prove identical grapheme segmentation, emoji width or combining-character deletion across locales and terminal emulators. Qualification should assert accepted bytes and terminal recovery first, then record display differences rather than claiming universal rendering.
