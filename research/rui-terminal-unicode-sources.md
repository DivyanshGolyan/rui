# Unicode boundaries and terminal cells for bounded Rui input (#297)

Research evidence for [#297](https://github.com/DivyanshGolyan/rui/issues/297), under [#296](https://github.com/DivyanshGolyan/rui/issues/296). Inspected 2026-09-25 in a separate Linux orb on `origin/main`, without the source thread's uncommitted CLI changes; this note was subsequently copied into that thread's feature checkout. This is a recommendation for the interaction and owner-boundary decisions, not an accepted contract, editor implementation, Mac test, or terminal-compatibility qualification. Rui's current public-operation boundaries live in [ARCHITECTURE.md](../ARCHITECTURE.md#public-operations) and its caller proof in [VERIFICATION.md](../VERIFICATION.md#inspection-and-waits). The map settles no history/completion, bracketed multiline paste as one Message, fresh explicit `a`/`d`/`l` for Action, and preservation of the 64 KiB whole-line rejection and typeahead guard until replacement.

## Separate the three units

| Unit | Primary source and consequence |
| --- | --- |
| **UTF-8 bytes** | The installed Zig **0.16.0** [`std.unicode.utf8ValidateSlice`](https://ziglang.org/documentation/0.16.0/std/#std.unicode.utf8ValidateSlice) rejects illegal starters, overlong encodings, surrogate halves, out-of-range scalars and incomplete tails; [`Utf8View.init`](https://ziglang.org/documentation/0.16.0/std/#std.unicode.Utf8View.init) validates before code-point iteration. [`utf8ByteSequenceLength`](https://ziglang.org/documentation/0.16.0/std/#std.unicode.utf8ByteSequenceLength) only identifies a potential starter's length: it is **not** validation. These were checked directly in the installed release's `lib/std/unicode.zig:25-39,231-351,358-411` (SHA-256 `6b7243b43bb1467b48d3027bcb379078f9ca077086bfe6f887d04de6259c2934`); [official release archive](https://ziglang.org/download/0.16.0/zig-x86_64-linux-0.16.0.tar.xz). A raw TTY can split a sequence across reads; validate complete candidate input before dispatch, or validate completed scalars incrementally with a bounded pending prefix and reject incomplete/malformed input at submission. Count the *actual* UTF-8 bytes, not code points or screen columns, against 65,536; preserve exact bytes, without normalization or silent prefix acceptance. |
| **Extended grapheme clusters** | [UAX #29 §3 and §3.1](https://www.unicode.org/reports/tr29/#Grapheme_Cluster_Boundaries) gives default editing boundaries for combining marks, Indic sequences, flags and emoji ZWJ; a cluster can be arbitrarily long, so counting clusters is **not** a byte cap. Zig's inspected `std/unicode.zig` has code-point facilities, not a grapheme/terminal-width API. [utf8proc v2.11.3 `utf8proc_grapheme_break_stateful`](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.h#L643-L668) implements extended boundaries with an initial-zero state, processing *every adjacent pair in order*; the stateless legacy API omits necessary rules. Compute previous/next cluster boundaries on the bounded validated line after edits, or maintain state and recompute affected suffixes. Delete/move whole clusters, never one arbitrary byte/scalar. |
| **Terminal columns** | [utf8proc `charwidth` and `charwidth_ambiguous`](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.h#L704-L721) provide **per-code-point** estimates, not a grapheme-width or terminal-width API. The former returns 0 even for nonprintable characters: it does **not** make controls safe to echo. [UAX #11 §2](https://www.unicode.org/reports/tr11/#Scope) explicitly says East_Asian_Width is not an off-the-shelf terminal width; [§4.2 and §5](https://www.unicode.org/reports/tr11/#Ambiguous) explain ambiguous-width context and a narrow default. [UTS #51 §1.4](https://www.unicode.org/reports/tr51/#Emoji_and_Text_Presentation_Sequences) distinguishes VS15 text from VS16 emoji presentation. Renderer/terminal font/multiplexer may differ even when byte and grapheme counts agree. |

**Asymmetric PTY counterexample (UTF-8 bytes shown in hex):** `A中e\u0301🧑\u200d🌾` = `41 e4 b8 ad 65 cc 81 f0 9f a7 91 e2 80 8d f0 9f 8c be`. It is **18 bytes, 7 code points, 4 extended clusters** (`A`, `中`, `é`, `🧑‍🌾`). utf8proc's code-point widths are `1,2,1,0,2,0,2`, sum **8**; a terminal displaying the joined farmer emoji as one wide cluster uses **6** cells for the whole example, while one that advances separately for the two emoji may use **8**. Backspace once should remove all **11 bytes** of `🧑‍🌾`, not one byte/code point; moving the terminal cursor back by either 2 or 4 cells unconditionally is unsafe. The [Ghostty author's terminal comparison](https://mitchellh.com/writing/grapheme-clusters-in-terminals) observed 2/4/5/6 cells for the farmer alone in different terminals in 2023, not a Rui or current-Mac qualification. In a local Linux `openpty` byte roundtrip the 18 input bytes were intact; no visual cell measurement was made.

Other distinguishing inputs: `a\u0308` is 3 bytes / 2 code points / 1 cluster / approximately 1 cell; `🇺🇸` is 8 / 2 / 1 and utf8proc's individual widths sum to 2, but rendering as one flag is a separate presentation decision; `⌚\uFE0E` and `⌚\uFE0F` each are 6 / 2 / 1 and utf8proc returns 2+0 for both, despite requesting different presentations. `α` is 2 / 1 / 1 and utf8proc chooses 1 cell, but ambiguous width can render as 2. At the bound, `"a" × 65,534 + "é"` is exactly 65,536 UTF-8 bytes and fits; `"a" × 65,535 + "é"` is 65,537 and must reject the **whole** candidate, not submit the first 65,536. The editor must consume/fence remaining pasted/typeahead bytes so that the overflow tail cannot become the next fresh Action choice. [UAX #29 §3](https://www.unicode.org/reports/tr29/#Grapheme_Cluster_Boundaries) also warns that one cluster has no fixed maximum size.

## Library and packaging choice

| Candidate | What it actually provides; dependency and limitations |
| --- | --- |
| Zig 0.16 stdlib alone | Strict UTF-8 scalar decoding/iteration, no extra third-party package or Unicode table, but no extended grapheme or width model. A one-off approximate grapheme implementation is a risky substitute for UAX #29's stateful rules. |
| [libgrapheme 3.0.0](https://github.com/FRIGN/libgrapheme/tree/bf20d2f7bce13c7d006a9ca442221399753bce9d) | [Public header](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/grapheme.h#L9-L64) has UTF-8 next-cluster and stateful boundary APIs, **no width function**. Its [decoder](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/man/grapheme_decode_utf8.sh#L13-L54) substitutes U+FFFD for malformed sequences; do not use that as Rui input validation. [ISC code license](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/LICENSE); bundled Unicode data has its own notice. [README](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/README#L4-L35) and [Makefile](https://github.com/FRIGN/libgrapheme/blob/bf20d2f7bce13c7d006a9ca442221399753bce9d/Makefile#L6-L44) describe Unicode 17 and C99/POSIX make plus build-time table generation from bundled data. The checked-out repository was ~26 MB including `.git`, **not** a shipping-size measure; README's separate conformance paragraph still says 15.0.0. Would require a second width source/policy. |
| **utf8proc v2.11.3 (preferred evidence base)** | [Stateful extended boundary](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.h#L643-L668), [code-point width and ambiguous property](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.h#L704-L721), explicit-length [UTF-8 decoder](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.h#L473-L483). [MIT code + Unicode data license/notice](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/LICENSE.md); [ordinary Makefile](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/Makefile#L74-L87) compiles pregenerated tables with one C source; regenerating tables is not needed. The pinned [Unicode version function](https://github.com/JuliaStrings/utf8proc/blob/e5e799221b45bbb90f5fdc5c69b6b8dfbf017e78/utf8proc.c#L99-L105) reports 17.0.0. Still **no cluster cell width** or terminal-width guarantee. |

**Cost, not a Rui measurement:** In a throwaway Linux checkout, utf8proc's `utf8proc.c` was 33,114 bytes, pregenerated `utf8proc_data.c` 2,360,214 bytes, and a `cc -Os -fPIC -shared` x86-64 Linux build produced a **350 KiB** `.so` (not a Rui link result or Mac footprint). A statically linked binary may include different code/data; measure the final linked CLI on both targets. A byte-bounded line needs at most 65,536 content bytes per active editor plus a few UTF-8/grapheme state scalars if boundaries are recomputed; an additional full redraw snapshot doubles that line storage to ~128 KiB per editor, and one `u32` per byte for a worst-case ASCII boundary index costs another 256 KiB. Avoid per-byte/cluster indexes and whole-line copies absent a measured need. Explicit-length functions can preserve embedded NUL as data; the input/renderer still needs a policy for nonprintable NUL/control scalars and must never echo untrusted ESC/control bytes as terminal commands.

## Recommendation and unresolved display policy

Use Zig 0.16 for strict UTF-8 validation and exact byte accounting, pin utf8proc for stateful extended-cluster navigation/deletion and **provisional** scalar width, and keep the 64 KiB whole-line rejection at the owning input transition. Do not normalize, replace malformed input silently, rely on the stateless grapheme API, or confuse `charwidth` with the width of an emoji cluster. Treat each paste's bytes as data between [xterm's bracketed-paste start/end sequences](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h3-Bracketed-Paste-Mode); newlines inside the marked paste are one Message, ordinary Enter submits, and stale/pasted input must not answer the fresh Action prompt. Bracketed paste is a terminal convention, not provenance authentication; parse escape sequences fully and bound the parser, disable the mode on cleanup, and retain the existing noninteractive file/stdin path.

For rendering, [xterm CUB/CUP/EL](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h2-Functions-using-CSI-_-ordered-by-the-final-character-lparen-s-rparen) move by **columns**, not clusters; [cursor-position reports (`CSI 6 n`)](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h4-Functions-using-CSI-_-ordered-by-the-final-character-lparen-s-rparen:CSI-Ps-n:Ps-=-6.1E06) and [mode 2027](https://mitchellh.com/writing/grapheme-clusters-in-terminals) are possible optional probes, not universal prerequisites or proven fixes through multiplexers. Do not redraw/backtrack uncertain emoji, variation-selector, ambiguous-width or soft-wrapped text on the assumption that each cluster is two cells. The interaction ticket must choose a conservative fallback, e.g. known-anchor full redraw only where its row/wrap position is known, otherwise stop cursor-dependent editing and offer a clear noninteractive input route rather than submit a visually ambiguous/truncated line. Bound probe waits and never mistake a probe reply for Message text or Action choice. Whichever rendering policy is selected, test actual PTY bytes plus cursor position and visible redraw for combining, wide, flags, ZWJ, variation selectors, ambiguous width, wrap and resize on supported terminal/platform combinations; Linux-only or cross-compilation evidence cannot claim native Mac behavior. [xterm notes special-key escape sequences are conventions, not a standard](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html#h3-Special-Keyboard-Keys); Option-/Command-Backspace only exists when the terminal emits a recognized sequence, never by portable physical-key identity.
