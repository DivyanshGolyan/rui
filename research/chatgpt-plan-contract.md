# Official ChatGPT plan contract and concurrent VM credentials

Research for #1031, checked November 6, 2026 against OpenAI primary documentation. Documentation only: no login, secret inspection, inference experiment, or runtime qualification. Headed and headless use are both explicit human requirements; authorization once and bootstrapping concurrent ephemeral thread VMs from a protected cloud-project bundle is a requirement, not a demonstrated capability. No retention, default, migration or capability policy is decided here.

**Bottom line:** official transfer to a self-hosted VM is transfer of an existing session, not documented independent renewable grant creation. Copying one stored bundle to concurrent VMs is not established as a supported independent-session fleet. Same-session refresh needs serialization and the newest replacement; the cloud requirement remains an unresolved support/design gap.

## 1. Scope, registration identity and machine identity — explicit

The public OSS/local flow grants optional permission for eligible Responses requests, not existing ChatGPT conversations/account context. Paid or remotely hosted offerings are directed to OpenAI's interest process; user-managed VMs have their own documented procedure. An issued client ID binds one authenticated user/workspace registration and its access/usage settings. Several hosts may share it. A host is an app-defined runtime lifecycle, not each restart/sign-in. Persist its distinct opaque `ext_agent_host_id` **before** initial authorization. Accepted forms: JWK-thumbprint URI (preferred), UUID URI, or `did:key`. Key-derived IDs currently prove no private-key possession. [Overview: introduction and client/host distinction](https://developers.openai.com/siwc/token-sharing-open-source#introduction), [host identity](https://developers.openai.com/siwc/token-sharing-open-source#a-client-vs-an-agent-host).

**Implication:** neither an app display name nor host identifier establishes hardware identity, account identity, or a global app registration. Exact host lifetime across reinstall/clone/worktrees remains an app decision, not an OpenAI mandate. Same source above.

## 2. Direct first-time and returning authorization — explicit, with Rui implication

Initial registration: `client_id=dynamic_agent_client`, actual app name, host ID. **Implication:** `agent_name_hint=Rui`, consistently, initially only; editable display metadata, not allowlisting. Persist/reuse the **returned issued ID**, not bootstrap ID. Returning callbacks cannot substitute another ID. No client secret/partner key. [Registration/sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Authorize: `https://auth.openai.com/api/accounts/authorize`; system browser, fresh state/nonce, S256 PKCE. Scopes: `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`; resource `https://api.openai.com/v1`. Callback uses HTTP `127.0.0.1`, not `localhost`; only its port may vary across attempts. Authorization/exchange URIs must match exactly within an attempt. Form-code exchange: `https://auth.openai.com/api/accounts/oauth/token`, issued client ID, code/verifier, same redirect/resource. Validate ID-token signature/JWKS, issuer, audience, expiration, nonce and selected identity; check returned plan-use scope separately. Hints do not change registered workspace. [Sign-in steps 2–4](https://developers.openai.com/siwc/token-sharing-open-source/sign-in#2-start-authorization).

## 3. Headed versus headless/remote modes — support boundaries

- **Explicit direct-SIWC mode: local human browser.** The loopback/PKCE flow above is the documented initial registration path. A browser on a laptop cannot directly reach a remote VM's loopback listener. [Sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in#2-start-authorization), [VM procedure](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms).
- **Explicit direct-SIWC mode: credential handoff to a headless VM.** Generate/persist the VM's own host ID first. Complete OAuth locally using the same tool/client, user and workspace. Securely transfer the selected registration's protected credentials, including issued ID, access/refresh tokens and retained metadata/ID token. Import must preserve the VM's host ID, not overwrite it with the laptop's. VM owns subsequent refresh; next authorization uses its own ID. This transfers an existing session; host-specific usage attribution and plan-access revocation for transferred sessions are **not yet available**. [Self-hosted VMs, steps 1–4](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms).
- **Explicit Codex product modes, NOT direct dynamic-client guarantees:** Codex documents beta device-code login (`codex login --device-auth`, policy-enabled, human browser/code approval), auth-cache copying, and SSH loopback forwarding (`ssh -L 1455:localhost:1455 user@remote`, then Codex login remotely). [Codex headless authentication](https://developers.openai.com/codex/auth#login-on-headless-devices).
- **Unknown for Rui's direct registration:** the reviewed SIWC pages specify no device-authorization endpoint/client parameters or guaranteed device-code grant. Codex's device-code support does not prove a dynamic registration can use it or yields equivalent scopes/billing. Forwarding the exact direct-SIWC callback is technically plausible, but is an **implementation inference**, not an explicitly supported procedure in those pages. No reviewed mode documents fully unattended, no-human first-time consent. Human approval on another machine is not unattended authorization. Sources: sign-in, VM and Codex pages above.

## 4. Credential custody, rotation and concurrency — explicit

Keep registrations/accounts separate. Refresh at `https://auth.openai.com/api/accounts/oauth/token` using form `grant_type=refresh_token`, issued ID, refresh token and the same resource; omit scope to retain grant. Serialize refresh of the **same session** across processes. Protect tokens in runtime storage, not browser storage/logs/analytics/transcripts; retained ID-token authorization URLs need redaction. [Accounts, refresh and security](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#refreshing-tokens).

Access lifetime is one hour; refresh lifetime is 30 days, renewed by each replacement without a fixed successive-renewal limit. Token response also lists `earliest_refresh_at`, without detailed scheduling semantics. Access-token client ID/scope claims identify the grant; OpenAI authentication metadata remains opaque. [Token response/lifetimes](https://developers.openai.com/siwc/token-sharing-open-source/token-reference#token-lifetimes).

Use app-defined protected credential files, atomic writes, Unix `0600`; persist account/client mapping, tokens/scopes/expiry; replace rotating credentials together. Keychain-only storage is not mandated. [Credential persistence](https://developers.openai.com/siwc/token-sharing-open-source/sign-in#5-store-credentials-in-a-local-file).

**Implication:** copying a refresh token does not create an independent renewable session; concurrent laptop/VM refresh can race. Follow documented VM ownership rather than letting both copies refresh. Cross-host lock/distribution, rotation crash recovery, token-reuse grace, and independent-session provisioning are not specified here. [Refresh rule](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#refreshing-tokens), [VM ownership](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms#4-let-the-vm-manage-token-refreshes).

## 5. Logout and revocation — explicit versus unknown

Sign-out stops requests, attempts renewable-session revocation at the endpoint discovered through `https://auth.openai.com/.well-known/openid-configuration`, then clears selected tokens while retaining client/account mapping and host ID. Form fields: refresh token, refresh-token hint, issued client ID. Empty HTTP 200 includes already-invalid tokens. Retry network/5xx with backoff while token remains; if local logout finishes unconfirmed, say so and direct users to ChatGPT settings. Revocation does not delete the registered client. [End renewable session](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#end-the-renewable-session).

**Implication/unknown:** copied session credentials do not establish independent logout domains. Do not promise per-host revocation, revocation of every registration, immediate access-token invalidation, or laptop/VM isolation; transferred-session limitations are explicit, but revocation propagation/access-token survival details are not specified. [VM limitations](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms#4-let-the-vm-manage-token-refreshes).

## 6. Public endpoint, model catalog and request completion — explicit

Use OAuth bearer token with `GET https://api.openai.com/v1/models`. This route's response has `models[]`; present entries with `visibility == "list"` in server order, show `display_name`, send selected `slug`. Reload on account switch. Use `POST https://api.openai.com/v1/responses`, bearer authorization and JSON content type, **not ChatGPT backend-api**. Every HTTP inference sets `store:false`, `stream:true`. Success requires terminal `response.completed`; started/output-producing streams can subsequently fail, including usage-limit errors. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

The examples specify no legacy ChatGPT account-ID header or partner key. **Unknown:** do not infer compatibility or transfer old private-route headers/claims from their absence. No static model list is promised. The requested `/making-api-requests` currently returns HTTP 404; the overview instead links the live Models and inference page. [Overview navigation](https://developers.openai.com/siwc/token-sharing-open-source#next-steps).

## 7. Capability constraints — explicit preview contract

HTTP requires context/history in array `input`; no `previous_response_id`. Use instructions/developer messages, not explicit system message items. WebSocket continuation is connection-local, not persistent storage. Unsupported fields: `background`, `conversation`, `max_output_tokens`, `max_tool_calls`, `metadata`, `moderation`, `multi_agent`, `prompt`, `prompt_cache_retention`, `safety_identifier`, `temperature`, `top_logprobs`, `top_p`, `truncation`, `user`. [Responses requirements](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations#responses-api-requirements).

Function/custom tools require namespaces or `additional_tools` input items. Web search depends on model/workspace policy. Hosted image generation, file search, Code Interpreter, native computer use, hosted MCP/connectors and Responses `tool_search` are unavailable; top-level programmatic tool calling is rejected. Model-supported text/image/file inputs work; audio/video, Files upload and transcription APIs do not. Local shell/MCP and child-agent coordination through supported functions are distinct from prohibited hosted tools. Codex app-server's documented env-token mode needs restart with the renewed token and thread resume. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

## 8. Eligibility and billing — preserve official-source tension

**Explicit:** developer quickstart describes eligible Plus/Pro users and all OSS partners; the Help Center says supported OSS tools remain available to all ChatGPT users, while distinguishing Go/Plus/Pro commercial-app eligibility. These are not a sufficient consistent exhaustive OSS inference-entitlement matrix. **Unknown:** precise free/Go/workspace/region/rollout eligibility; don't hard-code Plus/Pro exclusivity from one page. [Developer quickstart](https://developers.openai.com/siwc/quickstart#choose-an-integration), [Help Center availability](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites).

Eligible calls consume shared ChatGPT Work/Codex usage; app weekly caps do not create reserved pools. ChatGPT credits require separate opt-in and an app cap of 100%; that cap alone does not enable credits. Credit permission spans participating apps; automatic credit-purchase settings can result in charges. App charges remain separate. [Help Center usage/billing](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites). Plus's five-hour cap is shared across apps, including OSS/private clients; Pro does not have that five-hour cap. [Accounts usage](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#tracking-usage).

## 9. Recovery and required user-facing information — explicit

No automatic OpenAI fallback to another billing path. Missing plan scope allows identity sign-in but **not inference**; offer explicit plan enablement or another billing option. Eligibility errors must not cause OAuth loops; usage-limit errors pause requests and link usage settings, without guessing reset time or total-plan exhaustion. Unsupported-capability errors require request correction. Preserve credentials on temporary network/503 failure; confirmed disconnect/terminal refresh failure requires reauthorization with saved issued ID. There is currently no disconnect push notification. [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

UX guidance specifies approved **Continue with ChatGPT** branding; first-plan-use confirmation shown once; plan-use choice during onboarding/billing and later settings; active-account indication; **Using ChatGPT plan** near composer/model picker and **Manage usage** links to `https://chatgpt.com/settings/usage`. Usage-limit state's primary action manages usage; optional app-credit purchase is secondary. Distinguish app charges and identify which app plans support plan usage. For CLI/headless displays, exact visual adaptation is a **design choice not resolved here**, not permission to omit disclosures. [UI/UX guidelines](https://developers.openai.com/siwc/ui-ux-guidelines), [active-account guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#switching-chatgpt-accounts).

## 10. Concurrent ephemeral VMs: implications and unknowns

**Fact:** The [VM procedure](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) transfers an existing credential session, preserves the VM host ID, and assigns later refresh to the VM; host-specific usage attribution and plan-access revocation for transferred sessions are not yet available. The [refresh contract](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#refreshing-tokens) requires serializing same-session refresh and using the newest replacement. The [error guide](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery#refresh-errors) lists reused/invalidated refresh tokens and requires reauthorization on terminal refresh errors.

**Inference:** Distinct host IDs do not fork a grant; parallel independent refreshers of copied tokens violate the documented serialization rule. A static cloud bundle can become stale after rotation. Parallel inference using a current shared access token is different from independent renewal: neither independently renewable copies nor independent quotas/logout are established. A single refresh owner distributing current credentials is a possible cloud architecture hypothesis, not a documented grant-fork API or a validated solution. Storage controls, coordinated write-back and recovery remain design responsibilities.

**Unknown:** No reviewed direct-SIWC source documents unattended creation of independent renewable grants from one bundle, nor simultaneous-refresh winner behavior, replay grace, invalidation scope, immediate access-token revocation, per-VM isolation, or guaranteed unattended recovery after terminal failure. Do not infer that every stale copy immediately fails or that replay always invalidates an entire family. Independent grant provisioning, cloud-vault fleet support and eligibility for the particular deployment require confirmation.

This research does not decide deployment, migration, retention, defaults, or capability policy. No silent billing or authentication fallback is authorized.
