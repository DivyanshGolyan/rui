    What this interpretation still leaves open

    • Whose answer does B receive? The docs bind B to the failed Turn even if later included. Automatic continuation alone does not decide whether B’s waiting caller gets that failure or the successor’s answer.
    • What if continuation cannot start? This demo assumes valid saved context and settled effects. It does not invent a retry loop for invalid credentials, unavailable continuation, or storage failure.
    • Stop remains different. The intent view inherits the written stop/cancellation and crash rules for comparison. Your requested change concerns failure; those other rules have not been newly decided.

    Why similar results are not identical designs

    Latifa’s pending B is already admitted to A’s Turn. Codex’s durable queued B is waiting to start its own Turn. OpenCode v2 stores input before promotion, and Pi separates steering from follow-ups. An automatic next action can look the same while the original caller’s answer and recovery guarantees differ.

    These diagrams summarize inspected source. They are not executions of those products, and “continues B” never means “safely replays every failed effect from A.”

    Latifa: written behavior

    “failure leaves those messages pending without starting more work.”

    • Architecture: failing and continuing a Turn — failure retains pending input; new input starts continuation.
    • Architecture: pending messages — active messages join the Turn; projection occurs before the next assistant-response operation.
    • Required verification — failure then new input, original result bindings, no duplicate projections, no uncertain-effect replay. These are requirements, not passing evidence.
    • Choose unapplied-message behavior after a failed Turn — open discussion of requiring explicit resubmission.
    • Epic: finish V1 design and establish implementation readiness — readiness remains a separate decision.

    Your intent, as understood here

    “If session fails before the boundary, the queued message would resume it.”

    The intent view changes one rule: pending, unprocessed input can itself trigger a successor Turn after failure. A message arriving after failure also starts work immediately. A failed Turn with no pending input stays idle.

    The implementation of the successor and B’s original result binding remain open. This prototype does not change ARCHITECTURE.md or close the decision ticket.

    Limits of the demonstration

    State is held only in this page. Reload resets it. The failure button means a definitive terminal failure after required tool results and effect cleanup allow settlement; it is not a transient provider hiccup, transport disconnect, or a process crash.

    Messages stand in for complete inputs. “Included” means appended to model context, not confirmed provider consumption. This prototype does not model permissions, effect replay, corrupted continuation, budgets, database commits, or production crash recovery.
