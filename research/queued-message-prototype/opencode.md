## Findings

The v2 Session API separates prompt admission from execution. `sessions.prompt` durably inserts a `session_input` row and returns an admission receipt. Exact ID reuse returns the same receipt; reuse with another Session, prompt, or delivery mode fails. `resume` omitted/true schedules execution after admission; `resume: false` admits only. See [`specs/v2/session.md`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/specs/v2/session.md#L7-L37).

Admitted input is outside model-visible history until the serialized runner publishes `Prompted`. The projector atomically writes the visible user message and marks the inbox row promoted. Thus the durable inbox is the queue authority; an in-memory notification is only a wake hint. The same source defines `admittedSeq` as the durable sequence clients can use to observe queued input before promotion.

Delivery mode determines the next boundary:

* `steer`: pending inputs are promoted in admission order at the next safe provider-turn boundary, including while the current drain is continuing.
* `queue`: inputs remain FIFO while the current drain requires continuation. Once the Session would otherwise become idle, exactly one queued input is promoted, then continuation is reevaluated before another queued input is promoted.

The implementation matches this contract. At run start, pending `steer` wins over `queue`; each provider turn promotes all eligible steers up to a cutoff. Queue mode promotes one queued row, then promotes steers. After a turn, continuation keeps running and checks for new steers; when continuation ends, the outer loop checks for queued rows and promotes one on the next pass. See [`runner/llm.ts`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/packages/core/src/session/runner/llm.ts#L390-L413) and [`input.ts`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/packages/core/src/session/input.ts#L250-L305).

`run` is an explicit resume: it joins an active execution or starts a forced drain while idle. `wake` is the admission-triggered path; repeated wakes coalesce and it only calls the provider when eligible input exists. `interrupt` stops active process-local execution, waits through coordinator cleanup, clears a coalesced follow-up wake, and preserves durable inbox rows for a later wake or explicit resume. See [`session.md`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/specs/v2/session.md#L160-L171).

The coordinator serializes one Session locally, lets different Sessions run concurrently, and tracks only foreground activity in a process-local active registry. Overlapping wakes set one `pendingWake` bit. On successful completion, a pending wake starts a successor drain without leaving the active entry; otherwise the entry is removed. If a run exits with failure but a pending wake exists, a successor is also started, but the successor uses `force: false` and the runner's no-eligible-input guard. Therefore, if A is active and B is admitted with the default `resume: true`, then A fails before B is promoted, B's coalesced wake starts a successor and B can be promoted and run. This is automatic continuation of still-pending B, not a retry of A's already-promoted or ambiguous provider attempt. If no pending inbox work exists, a terminal failure has no automatic successor. See [`run-coordinator.ts`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/packages/core/src/session/run-coordinator.ts#L51-L103).

Failure and retry behavior is deliberately incomplete in v2. The Session spec says provider timeout, retry, and watchdog policy is deferred and there is no universal provider inactivity or absolute timeout. Context-overflow is the narrow exception: before durable assistant output/tool execution, v2 may perform one overflow-triggered compaction and rebuild the same logical turn with one remaining physical attempt; a second overflow, unavailable compaction, or overflow after durable output is an ordinary terminal failure, with no recovery loop or partial-side-effect replay. See [`session.md`](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/specs/v2/session.md#L115-L121) and [the deferred retry/recovery TODO](https://github.com/anomalyco/opencode/blob/f69beceaffca94bed05a7669af93602125c37248/specs/v2/todo.md#L47-L72).

Post-crash continuation is explicitly deferred. A wake does not infer that ambiguous provider work is safe to retry after input has been promoted. Explicit `run` may deliberately continue from durable projected history, but v2 does not currently define automatic resume of an already-promoted prompt after terminal provider failure, process loss, or an unknown dispatch outcome. It does define automatic continuation of separate inbox work that was admitted while the failed run was active, because that work's wake remains pending and the successor rechecks the durable inbox. The future slice is expected to define provider preparation versus dispatch ambiguity, required post-tool continuation, retry/abandon decisions, bounded automatic retry where idempotency permits it, retry budget/backoff, visible recovery status, startup discovery, and ownership fencing together. It also explicitly rejects inventing a durable enclosing execution identity solely to group these facts.

For Latifa's prototype, model `admitted`, `pending-steer`, `pending-queue`, `promoted`, `provider-turn`, `continuation`, `idle`, `interrupted`, `terminal-failure`, and `unknown-dispatch` separately. Represent `wake` as an edge-triggered hint, not durable proof of provider consumption. Preserve the distinction between automatic successor execution for still-pending B and unspecified/deferred retry or crash recovery for already-promoted A.
