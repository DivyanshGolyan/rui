# CLI guideline evidence for Rui's shared human journey

Research input for [#293](https://github.com/DivyanshGolyan/rui/issues/293) and the interaction-model decision in #287, using the [caller trace](https://github.com/DivyanshGolyan/rui/issues/286#issuecomment-5825363367). The confirmation/TTY boundary below also informs [#322](https://github.com/DivyanshGolyan/rui/issues/322). This note compares the primary [Command Line Interface Guidelines](https://clig.dev/) with Rui's accepted authority boundaries; it does **not** select an interface model, TUI, or framework. The clig.dev section anchors below were checked against the page's heading IDs on 2026-09-25.

## TTY versus pipe scenario

- **TTY (proposed presentation, not observed behavior):** after a message admission, render “Accepted; not complete” and offer commands that preserve the exact key. If inspection finds Action 7, show the exact Bash payload before offering explicit Action-bound allow/deny. A restart notice should tell the user to start the Host against the same Store and recover the same capture/key; it must not start the Host or generate a replacement request silently.
- **Pipe/noninteractive constraint:** `rui ... --json | jq ...` must emit only the selected structured data on stdout, never prompt, and return without terminal decoration. Pending Action data must be discoverable and approval must require an explicit exact-target command. If a reply is lost, automation reuses the retained record/key and separately observes/reads the saved outcome.

## Confirmation choices and the TTY boundary (#322)

- **Short choices are normal, not a security primitive.** The practitioner-maintained, open-source [CLI Guidelines](https://clig.dev/#arguments-and-flags) (advice, not a formal standard) call `y`/`yes` a common interactive confirmation for dangerous commands, reserving a non-trivial typed resource name for *severe* destruction. POSIX [`rm -i`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/rm.html) specifies a line with an affirmative response (interpreted according to locale), not a one-time code; GNU [`rm -i`/`-I`](https://www.gnu.org/software/coreutils/manual/html_node/rm-invocation.html) prompts per file or once for a bulk operation. Those deletion examples establish the convention, not Rui's authorization model.
- **Relevant agent-CLI precedent is `vercel-labs/fx`, not the unrelated JSON viewer.** At pinned [fx commit `59bf4372`](https://github.com/vercel-labs/fx/tree/59bf4372bd7914f9b229827937c09085f33e9776), its [input decoder](https://github.com/vercel-labs/fx/blob/59bf4372bd7914f9b229827937c09085f33e9776/src/ui/input/runtime.zig#L59-L70) maps `1`/`2`/`3` to choices; the [approval state](https://github.com/vercel-labs/fx/blob/59bf4372bd7914f9b229827937c09085f33e9776/src/core/permissions/approval_decision.zig#L129-L175) submits those digits immediately as allow once/allow always/deny (Enter submits the selected option). The [worker](https://github.com/vercel-labs/fx/blob/59bf4372bd7914f9b229827937c09085f33e9776/src/core/agent/worker_runtime.zig#L2382-L2445) rejects a response whose request ID is not the pending one. This demonstrates short approval input plus request correlation, not Rui's durable Host/Action authority. Its [event loop](https://github.com/vercel-labs/fx/blob/59bf4372bd7914f9b229827937c09085f33e9776/src/ui/event_loop.zig#L45-L73) dispatches buffered/readable bytes before frame commit; the inspected [terminal mode path](https://github.com/vercel-labs/fx/blob/59bf4372bd7914f9b229827937c09085f33e9776/src/ui/shell_runtime.zig#L93-L138) supplies no approval-boundary input flush. Thus its single-digit UI is *not* evidence that queued, unmarked typeahead cannot decide. Ghostty is a terminal emulator, not the approving CLI ([terminal-input research](terminal-line-editing-sources.md#what-terminals-actually-provide)).
- **Typed identity addresses a different failure.** [Heroku's destructive command reference](https://devcenter.heroku.com/articles/heroku-cli-commands) documents `spaces:destroy --confirm=<space-name>` and `data:pg:destroy --confirm=<app-name>`; [GitHub CLI's repo deletion](https://cli.github.com/manual/gh_repo_delete) ignores `--yes` for an *implicit* current-repository target and requires the repository to be named for noninteractive deletion. These add friction or disambiguate an otherwise implicit, destructive target. The [CLI Guidelines](https://clig.dev/#arguments-and-flags) recommend a typed name for severe destruction, with an explicit scriptable alternative. They do not prescribe a random one-time allow code for each ordinary permission decision. Such a code might make stale typeahead less likely to match by accident, but would add copying/reading burden and still would not prove the human read the Action or prevent intentional/automated input.
- **Rui's actual boundary differs from `rm` or deleting a repository.** The [CLI](../src/cli.zig) (`approveSessionAction`) inspects and displays the exact Action and escaped arguments, then captures a separate exact-target decision. [SessionTerminal](../src/SessionTerminal.zig) (`readChoice`) owns its independent fresh-choice parser. The [Store](../src/store.zig) (`decidePermissionLocked`) rejects a different Session or a no-longer-pending Action inside its transaction. The [PTY fixture](../tests/integration/human_cli_integration.py) checks that an `a` pasted with the preceding Message does not authorize, while fresh `a` can; it also rejects padded and marked-paste choices. These are source/fixture observations for this checkout, not human-attention or all-terminal guarantees. Unlike an `rm -i` confirmation of a user-initiated deletion, this is approval of a model-proposed, specific effect, so the *display and exact-target Host revalidation* carry the safety meaning; a one-letter choice need not be its authority.
- **POSIX flushing clears a queue, not intent or display time.** [`tcflush(fd, TCIFLUSH)`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/tcflush.html) discards input *received but not read* at the flush; [`tcsetattr(fd, TCSAFLUSH)`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/tcsetattr.html) waits for written output to be transmitted and discards input so far received but unread before changing attributes. Neither removes bytes already read into application memory, promises to discard bytes generated before the call but delivered afterward, nor marks whether later bytes were typed before or after the user saw the prompt. Rui's [terminal owner](../src/SessionTerminal.zig) drains prior output and flushes queued input *before* publishing the fresh choice prompt, independently of ordinary composition. [`tcdrain`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/tcdrain.html) waits for terminal output *transmission*, not human-visible rendering or attention. Already-queued typeahead is discarded without losing a prompt-visible key; delayed earlier bytes delivered after the flush may still be read. There is no POSIX atomic “visible prompt → fresh key” barrier. The PTY test proves the exercised queued-paste ordering, not that stronger claim.

**Evidence conclusion:** these sources distinguish short-choice conventions, ambiguous destructive-target confirmation and durable authorization. They do not establish a post-visible-prompt human-attention guarantee, whether the response is a letter or a random code. Rui's selected approval behavior belongs to [the human-caller contract](../ARCHITECTURE.md#public-operations); the comparison here supplies rationale and POSIX evidence limits, not a second interface policy or qualification claim.

## Concrete observed and proposed text

**Source-observed (local current binary, exit 1, stdout empty; stderr excerpt; source `src/cli.zig:514-534`):**

```text
usage:
  rui message --store PATH --record FILE --key KEY --session REF --text FILE|-
  rui retry --store PATH --record FILE --kind configure|message|...
error: InvalidArguments
```

The Debug binary also printed an internal Zig stack trace. This is a concrete diagnostic observation, not evidence about a release build. Actual #286 message output was raw JSON with `answer.status=accepted`, `queue.status=queued`, and `execution.status=queued`; retry returned the original queued admission with `replayed=true`, not current completion (#286 comment lines 6-7).

**Proposed wording for comparison only (not a contract or interface choice):**

```text
Accepted message key “second”; work is queued, not complete.
Next: observe the same key. If this reply is lost, retry record second.json;
do not submit a new key to recover this request.
```

This illustrates clig.dev's next-step advice while preserving Rui's acceptance/completion and exact-capture distinctions. The final model must decide whether such prose is a TTY rendering, help example, or another mode; it must not contaminate machine output.
