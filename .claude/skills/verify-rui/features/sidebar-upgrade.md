# Sidebar memory and updates

The list bottom has a divider immediately above one pinned row: Settings on the left, either quiet Rui memory or a visible native update target on the right. Available, running and failed updates replace memory completely. Bare wide launch opens a focused empty chat beside the 40-column list; a narrow chat hides the list. Sidebar specimens preserve the wide split. Before narrowing, a focused empty composer moves to the list with native Left, keeping the chat open; the input cursor must become hidden before resize. Narrow Esc is only a fallback when Settings is absent.

## Sub-features

- Hidden current/completed versions, available `Update to <version>`, `Updating…` and retryable `Update failed` without a reason on the bottom row.
- Separate Settings and update hit targets on the shared row; Settings Version retains the installed version, full failure diagnostic and upgrade entry point.
- A successfully upgraded conversation keeps its ordinary chat footer without upgrade notices.

## How to get to it (user POV)

Open Overview. Settings shares the row below the divider with either memory or update state. Click an available update or the failure text to start or retry an upgrade. Settings opens the app panel; its Version row also starts Upgrade. Continue the already open conversation after installation.

## Driving it with verify-rui

Frame states: `sidebar-current`, `sidebar-available`, `sidebar-updating`, `sidebar-failure`, `chat-after-upgrade`, `day-sidebar-current`, `day-sidebar-available`, `day-sidebar-updating`, `day-sidebar-failure`, `day-chat-after-upgrade`

Build each pinned revision with `build FULLSHA --upgrade` before capture. This explicitly adds the same-source synthetic release actor and its source and binary hashes to the cached manifest; frames never builds it implicitly. Use the working frames.json as an explicit shared `--scenario` for before/after, selecting these states at `--sizes 140x40,46x30`. Every state gets a private managed installation and production Host, but Upgrade discovery is UID-global: a synthetic HOME does not isolate other Hosts owned by that account. Capture only under a dedicated fixture account such as `rui-s7-sidebar`, setting `VERIFY_RUI_UPGRADE_FIXTURE_USER=rui-s7-sidebar`. The runner refuses root and requires the explicit login name to match its non-root UID. Never use an account with unrelated Rui Hosts. The runner pauses and waits for its ordinary parent Host to retire before the first isolated Upgrade, retires every managed Host after its state, and restores the parent only when subsequent ordinary states need it. These boundaries are recorded in `upgrade-host-lifecycle.jsonl`; a failed Upgrade teardown stops the run rather than admitting another UID-global Upgrade. Only release HTTP responses and the existing provider fixture are synthetic.

Current and available use production discovery. Available advertises a newer metadata tag without installing its intentionally mismatched archive. Updating installs the valid actor from an older selected release and holds the existing after-publication file gate. Failure returns HTTP 403 at latest-release lookup. Both themes wait for the real post-attempt list read: the short failure label and ordinary chat info must coexist, without Reading this Session or the attempt-only Host paused row. No side waits for or permits the retired `enter open` hint. Observing the failed run alone is too early. At 140 and 46 columns the failure label is exactly `Update failed`; its complete reason remains in Settings Version. Every visible update label replaces memory, even when both would fit. Row patterns require the divider directly above Settings and reject a second memory/update row or a visible current version. Positive row patterns stop at the actual vertical pane separator, so chat content beside the list cannot satisfy a sidebar assertion. Chat-after-upgrade completes installation and relaunch while preserving the already open saved conversation. The same frame collector exports cells, text, ANSI, HTML and PNG. Per-state upgrade evidence records actor identity, candidate, selected installation and HTTP requests.

The shared scenario selects strict `comparison.before` row/notice expectations on the old revision and the ordinary expectations after. Before has no sidebar update target: the runner clicks Settings then Version, closes Settings after publication (when Escape cannot cancel), and captures the old global Publishing or failure diagnostic. The old failure diagnostic replaces ordinary footer info; that side waits for the exact diagnostic without the Host paused or Reading this Session transition. After also starts the initial attempt through Settings Version, because a current version has no sidebar target; the failure journey retries through the native sidebar update target. Baseline availability has no visible control and retains its version beside Settings. Before assertions deliberately pin that old layout rather than accepting after-only assertions.

## Gotchas

No internal setters or synthetic painted UI are used. Upgrade specimens start wide so Settings Version and post-read chat progress are observable, even when only a narrow capture is selected; the narrow viewport is then reached by native list-focus preparation and real resize. A committed publication gate stays held throughout this transition; the harness never releases it merely to navigate. The publication gate stays held across both viewports, then is released during state cleanup. A normal unreleased pinned binary cannot replace the release actor. Runtime captures are L1 PTY input, not hardware proof. After both failure viewports are captured, an after-side native retry journey clears the HTTP 403, holds the archive response while capturing Updating, releases it and proves the selected installation and replacement ready Host, with the bottom version hidden again. It then clicks Settings and Version, proving up-to-date behavior. Extra cells, HTML, ANSI, text and generations live under `journeys/STATE/`; primary frames retain the original failed state. Supply an explicit shared scenario when the baseline does not contain these new state names; default revision-specific pairing otherwise reports New screen.
