# OnePage resource architecture

This is part of the normative [ARCHITECTURE.md](../../ARCHITECTURE.md) contract. [Corresponding verification](../verification/resources.md) supplies the required checks.

## Capacity and memory

### Capacity ownership

Physical Custody is one startup-sized in-memory table of content-free records. Use plain bounded table scans in V1, without a separate free list, active-record index, resident Session collection, or durable SQLite slot table. Reserve a record before Attempt admission; rollback returns the unused reservation, while successful admission permits dispatch only after its commit is observed. SQLite owns Session occupancy, Operation current execution/Resolution facts, cancellation and retry eligibility; it does not duplicate live handle ownership. Logical settlement does not free a record whose physical cleanup is still outstanding. Reuse requires safe resource release and rejection of stale or duplicate events by exact admitted identity. The accounting invariant is free records plus occupied records equals startup Active Capacity; it does not introduce a second credit pool.

Edit preparation before Authorization occupies one record in the same shared Active Capacity table before acquiring preparation resources. It creates neither an Attempt nor a Dispatch Permit and cannot mutate the target. Persist the exact Edit Intent and required immutable inputs before requesting permission, then safely release preparation buffers, scratch and custody; waiting for permission retains none of them. Approved work reacquires shared capacity to reconstruct and revalidate the same authorized intent before application. A changed target does not authorize a changed edit. Preparation and application each consume one record while active, not two simultaneous credits for the same work. The default 1,000 therefore bounds preparation, execution and outstanding cleanup together, with no independent preparation pool. Preparation records require exact volatile ownership identity for stale-event rejection without inventing an admitted Attempt. Failed preparation, cancellation and crash release volatile resources without manufacturing effect uncertainty for a mutation that was never admitted.

### Capacity backpressure

Temporary exhaustion of Active Capacity is backpressure on physical execution, not a terminal failure of already-accepted work. Leave that work eligible in its existing canonical SQLite facts until a custody record becomes available. Waiting for a record admits no new Attempt, consumes no Attempt allowance, creates no Dispatch Permit, and materializes no outbound request scratch. It retains no per-waiter thread, socket, payload buffer, or resident queue entry. Do not add a durable capacity-wait flag, queue position, or second scheduling authority. This does not bypass independent command-ingress, storage, permission, or effect-budget checks.

Safe custody release notifies the existing Host driving path to reconsider eligible work through bounded queries and ordinary admission checks. Revalidate cancellation, applicability and due times before admitting an Attempt; cancellation of waiting work needs no execution credit. Restart derives eligibility from the same durable facts, without manufacturing a prior Attempt or restoring a volatile permit. Preserve the existing effect-specific recovery rules for work that did have an admitted Attempt. These rules select neither FIFO ordering nor numeric capacity or latency guarantees.

When no runnable work or required deadline/poll is due, sleep until an existing I/O/control notification or required wake. Do not add periodic scans merely to revisit an empty or full custody table. Work waiting only for capacity is not a reason to spin; controls, cleanup, other runnable work, required deadlines and the existing retry poll still receive their service turns. Run the existing single bounded SQLite retry-eligibility poll every second, using an indexed due-time query and bounded processing turns. Revalidate eligibility at admission. After sleep or delayed service, perform a current poll rather than queueing missed ticks. Poll discovery is separate from capacity admission and effect launch; backoff policy remains with the provider/effect decision. This is not a whole-process prohibition on allocation after startup: library, evaluator, transport, and scratch resources retain their existing bounded ownership and accounting.

One startup-fixed `active_capacity` bounds the Physical Custody table. The planned V1 startup default is 1,000 shared model/Bash/Edit executions. This is a capacity ceiling, not an up-front allocation of per-execution transports or payloads, and it is not a hard maximum. Actual owner resource requirements must pass startup validation and the supported build must qualify at this default before release; prototype feasibility is not production certification. Reserving a free record before admitting an external Attempt occupies one Active Credit; releasing that same record after its physical resource obligations finish returns it. A cancelled model outcome may precede that release. Bounded Decision Snapshots and the shared validation/import workspace are borrowed serially; neither is preallocated per credit.

Durable Dormant Session, terminal Turn, and Blocked Workflow Run populations reserve no resident driver, Slot, Active Credit, thread, socket, subprocess, evaluator, materialized Conversation, or context graph merely by existing. Temporary cleanup after logical model cancellation remains owned and charged by the Host's Physical Custody until release, not by a resident Session object. Long-lived in-flight work may retain only its credit, content-free custody record, transport handles, and dynamically charged unlinked scratch.

Memory claims report whole-process RSS and the slope of each population separately: durable Sessions, terminal Turns, Active Capacity, provider transports, temporary Action executors and transport resources, SQLite, semantic-validation workspace, evaluator, and model-requested subprocesses. Workload memory is observed separately from OnePage-owned orchestration memory.

Release operation resources explicitly at their owning lifecycle boundaries and reuse the existing bounded processing workspaces. Distinguish allocator-live allocations, allocator-reserved space and process physical footprint after cleanup; freed allocations need not immediately reduce the last measure. The current evidence does not require a custom allocator or explicit pressure-relief mechanism in V1. Any later reclamation policy must follow the selected idle-footprint requirement and measurements on the supported dependency/platform build. Retained memory remains part of Host accounting.

Every large value moves through explicit stages—SQLite or wire, unlinked scratch, one shared validation/import workspace, canonical SQLite content, and presentation window—with one owner and release boundary. Variable content goes to disk unless a measured CPU-critical operation requires a fixed borrowed memory window. A byte limit never authorizes a resident allocation of the same size.

The Host's aggregate scratch allowance defaults to **8 GiB**, configurable for the Host. It limits temporary data written and retained by OnePage across existing owners, including request materialization, captured output and parser metadata, ingress, current/completed reports, temporary exports and retained Spillover Output. It is neither preallocated disk space nor a RAM allowance. Canonical SQLite application state and persistent diagnostic retention have separate lifetimes and do not consume this scratch allowance. Temporary copies of those contents do count while held. Release files with no remaining consumer once safe. Files retained for optional later use follow the shared FIFO policy below; they are not canonical history. Physical custody stays occupied until its execution cleanup obligations finish; optional retained files transfer to the shared temporary-file owner without keeping that execution slot occupied. The allowance counts logical file bytes, including sparse gaps, rather than filesystem-allocated blocks. It is not a guarantee of free volume space, an all-process held-byte ceiling, or successful completion of arbitrary work. For published spillover, external mutation, additional links and data held by other processes after removal are outside the enforced allowance.

### Shared temporary-file retention

One shared temporary-file owner and byte allowance cover all temporary content. A file is protected while required to finish current work, including active output capture, result publication, Edit preparation/reconciliation, report delivery or an outstanding Host-owned read. Once required work has released it, a file retained only for possible later use is disposable. Spillover becomes disposable after its small Tool Result and command outcome are saved and execution no longer needs the file. Files with no later consumer are released immediately rather than retained just to fill the allowance.

When a new temporary-storage reservation needs space, discard the oldest eligible retained files first until enough space is available. FIFO applies only to disposable files; it cannot evict protected files or required canonical evidence. Access does not turn this into a least-recently-used policy. For private scratch, actual safe release must succeed before its charge is reusable. For published spillover, successful removal of the retained name and closure of OnePage's own handles releases its retention charge; unknown external readers do not keep that charge or make the file ineligible for FIFO. If safe reclamation cannot provide enough space, use the existing pre-admission wait or post-admission explicit failure behavior. This runs through the shared owner when space is needed, without another storage pool, per-tool policy, background cleanup service or expiry timer.

A retained spillover file may remain across Turns until FIFO reclamation or Host exit. Loss on crash or cleanup is acceptable and leaves the saved result unchanged; later retrieval reports unavailable and never silently retargets the reference or reruns the old command. Host exit releases OnePage's names and handles safely; other programs may still hold data. Restart does not promise reconstruction of full spillover. This does not make raw provider capture or other private execution files a new diagnostic archive. Retained-file metadata, handles and retrieval must still fit the Host resource envelope; their concrete bounded representation is an implementation obligation within the existing Host envelope, not a promise to account for all external file users.

Published spillover is ordinary filesystem output. Its retention charge is the Host-produced logical size recorded at publication, preserved during transfer from capture and returned on successful name removal plus Host closure. External writes, truncation, links, replacement or open handles are outside that enforced allowance and cannot change the saved Tool Result. FIFO may unlink a published file while a shell reader has it open; normal filesystem behavior applies, and physical disk space may remain in use after the retention charge is returned. OnePage does not promise that the shared allowance bounds that external usage. Real disk exhaustion still fails explicitly. Add no sandbox, global file-reader tracking, advisory-lock protocol or periodic external-mutation scan merely to recover the stronger guarantee; the [ownership research](../research/spillover-path-ownership.md) records why ordinary paths cannot provide it. This is one shared budget with a scoped ownership boundary, not a second spillover pool.

Build model execution with an outgoing request file and a captured response file, allowing their lifetimes to overlap through settlement. Build Bash capture with separate stdout and stderr files and a materialized input file only when needed. Stream content through bounded windows and release each file after its last use and safe I/O completion. These file roles derive resource populations for accounting and descriptor sizing; they introduce no per-tool file-count quota or admission check. Their bytes and pending growth count against the shared scratch allowance.

Local client uploads and temporary report/export files use the same aggregate scratch accounting. An ordinary exchange has an incoming-content file role and an outgoing-content file role, materialized only when needed; reports and diagnostic exports share the outgoing role. Their lifetimes may overlap, and both copies count while held. Release each after its last use and safe I/O completion on success, failure or disconnect. A transfer of ownership preserves the charge and release obligation; disconnect does not discard content still needed by saved work. These roles derive file/descriptor populations, not an additional client file quota or accounting system.

### Growth accounting

Each private scratch or active-capture file has one current owner and one tracked logical size. Published spillovers use the retention charge defined above. Before a write or other size-increasing operation, reserve its possible growth against one synchronized Host total; include outstanding reservations in that total so concurrent owners cannot oversubscribe. For a positional write, growth is the positive difference between its proposed ending offset and the current size, with overflow rejected before reservation or I/O. After partial completion or failure, retain only the actual growth and return the unused reservation. Overwrites within the existing size do not add a charge. Successful truncation returns removed logical bytes; failed truncation does not. Ownership transfer preserves the charge, and temporary copies count separately while both exist.

For private scratch and active capture, the owner serializes mutation and release of its file; no writable alias or alternative growth path may bypass this boundary. Release the remaining charge only after final safe closure with no outstanding I/O or retained handles requiring the file. Initial unlinking alone does not release the charge. Use the existing file/owner state and one shared total, without per-write heap allocation, directory scans, SQLite transactions, or a global lock held across disk I/O. Logical accounting does not model filesystem block rounding, compression, metadata, or cache; real storage faults retain the existing explicit failure behavior.

### Storage exhaustion

If required temporary storage remains exhausted after safe FIFO reclamation before Attempt admission, leave already-accepted work waiting in its existing SQLite facts without consuming Attempt allowance or retaining per-waiter execution resources. Reconsider availability through the existing Host driving path; do not add a storage-pressure scheduler or busy retry loop. Available space before admission is not a reservation of all future output and cannot guarantee later writes.

If temporary storage remains exhausted after safe FIFO reclamation after Attempt admission, including during outbound request materialization or active output capture, stop the affected execution safely through its existing effect owner and report an explicit storage failure. Do not rewind the real admission, buffer the remaining output in RAM, silently truncate it into success, indefinitely pause the execution while it retains scratch, or automatically redispatch the failed work. Retain custody and any evidence still needed for safe settlement until their ordinary release boundaries. Bash may already have changed external state; storage failure grants no rollback or blind replay. Edit and other effects keep their existing reconciliation and uncertainty rules. Successfully committed results remain authoritative.

A storage fault that prevents SQLite from durably saving semantic state stops new dispatch and initiates bounded, effect-aware Host shutdown. Do not claim a committed failure, cancellation completion or logical occupancy release when its transaction did not commit. After storage is restored, explicit Host restart uses existing recovery; stopping the Host is not itself a failed or cancelled Turn and does not authorize redispatch outside those rules. Diagnostic-write failure alone keeps its separate non-authoritative behavior. Incomplete ingress and inspection still fail explicitly without publishing partial content or a successful truncated report. Beyond the shared FIFO reclamation of disposable temporary files, this policy introduces no automatic Host restart, emergency memory backlog or numeric disk reservation.


### SQLite ownership and limits

V1 adds no artificial canonical-database size/page-count quota or emergency admission reserve. Canonical state remains subject to SQLite's supported representation boundaries and actual storage availability, with the storage-fault shutdown rule above. A page-cache or heap budget does not impose a durable-history quota. The historical implementation's database cap and reserved admission pages are not retained V1 policy; their removal belongs to implementation against this contract.

Host resource configuration is read at startup, without hot quota resizing, free-space-percentage tuning or an emergency scratch pool. Metadata growth after admission follows the same explicit failure/settlement rule; it must not wait indefinitely while retaining a full quota. Small controls need neither external execution credit nor content scratch, though their semantic writes still depend on canonical storage. Startup validation must derive file/descriptor requirements from bounded owner populations and actual platform availability. Every temporary file, including an empty file, belongs to a bounded live owner; a byte cap alone is insufficient. No additional descriptor pool or per-waiter resource population is introduced.

SQLite incremental import must not retain payload-sized dirty-page memory merely because its page cache has a small suggested size. Retain an enforced finite SQLite heap ceiling; derive and verify its value during implementation against the accepted 256 MiB whole-Host physical-footprint target rather than selecting another product quota in advance. Cache sizes and transfer windows are internal implementation choices. The historical 8 MiB heap allowance is a starting candidate, not an accepted requirement. Required workloads must qualify under the chosen settings before release; if necessary work misses the Host target or a setting restricts promised behavior, review that result explicitly rather than silently changing the contract.

Store initialization explicitly configures spill behavior and verifies the effective cache size, spill threshold, and enforcement of the chosen SQLite heap limit on the pinned build. A successful setter alone is not evidence of enforcement. The Storage Owner owns these internal settings, with no caller-facing SQLite tuning surface. The SQLite heap limit is not a whole-Host resident-memory bound. Verification includes large imports and failed-import rollback. The exact heap/cache/window values are implementation and qualification work, not a prerequisite to resolving the [SQLite resource decision](https://github.com/DivyanshGolyan/onepage/issues/95).

Retain the existing single-owner `DELETE` journal and `EXTRA` synchronization as the implementation baseline, with mmap disabled, file-backed temporary work and explicit verified spill. Preserve foreign-key enforcement, defensive configuration, untrusted-schema restrictions and the existing disabling of unused attachment, extension, trigger and worker features. Qualify these settings against the actual schema and statements; a required feature must have an explicit consumer rather than being enabled speculatively. Page size and SQL implementation bounds are internal choices, not new user quotas. A journal/read-ownership change still needs its own reason and durability evidence through the inspection decision.

SQL text, column, compound-select, function-argument, pattern, parameter and compiled-program ceilings follow the Host's owned statement shapes and the pinned engine's supported representation. Retain a tighter setting only when a concrete consumer or resource boundary justifies it, and verify all supported statements under it. Historical numeric reductions are not automatically V1 requirements. A row/blob representation limit must preserve the accepted content contract and must not become a Conversation, message-count, Run or durable-history quota. Remove obsolete reductions only with their replacement storage, binding and traversal checks in place. The historical database cap/reserve, fixed cache-profile allowlist and buffer-derived content ceilings in `src/host_store.zig`, and the fixed heap default in `src/host_runtime.zig`, must be removed or rederived under these rules; this design decision does not itself alter production checks.

`SQLITE_LIMIT_VDBE_OP` constrains compiled statement size, not executed work or elapsed time; exceeding it can report `SQLITE_NOMEM` during preparation. Preserve operation/error context rather than treating that code alone as proof of actual heap exhaustion. Bound command work through the owned query shapes, indexes and bounded service turns between atomic transactions; import windows bound resident materialization, not total transaction time. Preserve atomic publication, existing cancellation traversal/recovery and fair control/settlement service. Inspection access shape and read ownership remain with their separate decision rather than a guessed statement timer.

Keep SQLite busy handling immediate (`busy_timeout=0`) on the sole Storage Owner; expose typed failure rather than hidden blocking retries or automatic command replay. Rejections before semantic admission and failed read-only captures publish no partial success. Where a command requires a durable stable result, an unsaved result cannot be acknowledged as recorded. After a transaction error, resolve rollback and confirm autocommit state before connection reuse; an unusable or uncertain connection cannot continue semantic work. A fault preventing required canonical state from being saved follows the accepted dispatch-stop and effect-aware shutdown rule. No uncommitted failure, outcome, cancellation completion or occupancy release may be reported as durable. Diagnostic failure keeps its separate non-authoritative behavior.

Values marked derived must be calculated and qualified against the selected implementation rather than copied from historical buffers. Engineering targets are not runtime admission controls. Complete inspection remains unpaginated and captured on the sole Storage Owner, with control and settlement service between captures. No elapsed-time abort or hard maximum capture delay is selected. The one-second p95 target includes capture delay under the defined workload; it is not promised for arbitrarily large reports.

Unsupported durable-backlog, whole-Turn, content-size, evaluator cardinality and universal field quotas are not retained. Their coordinated replacements and source/test obligations are in [Limit replacement verification](../verification/resources.md#limit-replacement-verification). No obsolete guard may be removed alone while its fixed buffer/table remains. No compatibility layer or second implementation track is required for unreleased V1 state; subsequent implementation slices follow overall V1 readiness.
