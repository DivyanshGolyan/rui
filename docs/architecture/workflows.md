# OnePage workflow architecture

This is part of the normative [ARCHITECTURE.md](../../ARCHITECTURE.md) contract. [Corresponding verification](../verification/workflows.md) supplies the required checks.

## Workflow Runs

### Keys and replay

V1 retains an explicit caller-supplied call key for each durable Session configuration and message submission within a Workflow Run. Session keys separately identify reusable conversations; constructing a reference is pure local work. Pure JavaScript calculations, helper calls and awaits need no separate key or step wrapper. Distinct intentional operations use distinct keys even when their inputs match; replay uses the original key and complete binding. Run Keys separately identify whole-workflow submissions. Caller keys preserve exact text without trimming, case folding or Unicode normalization. Impose no arbitrary character whitelist or independent key-length quota; any narrower restriction must derive from the actual representation or consumer, with exchange and resource limits enforced by their existing owners.

Explicit keys preserve operation identity when cached results change the order in which concurrent branches reach calls. A global invocation counter is not stable under this evaluator's snapshot replay; a code location alone cannot distinguish repeated loop/helper calls, and an input hash cannot distinguish intentional identical operations. V1 does not add compiler-generated identities or historical promise-delivery replay solely to remove caller keys. See the [industry comparison](../research/durable-workflow-step-identity.md) and [call-order counterexample](../../research/workflow-call-order/README.md). These establish the design rationale, not production recovery evidence.

Workflow authors must derive durable operation keys and canonical inputs from stable source identities, arguments and original recorded results, rather than the order in which concurrent branches become available. For example, identify a verifier by scanner identity and finding identity (or its stable position within that scanner's original result), not a shared counter incremented by whichever scanner resumes first. When several branches contribute to one request, explicitly join their required results and construct its inputs in a stable order. Ordinary local JavaScript mutation remains available; authors must not let completion-sensitive shared state change the identity or inputs of the same logical operation across evaluations.

The Host enforces equal-key binding reuse and rejects changed kind or canonical inputs. This detects conflicting reuse, not every violation of the authoring contract: accidentally producing a different new key can appear to be intentional new work. OnePage does not promise arbitrary shared-mutation determinism, statically police workflow JavaScript, or reconstruct historical promise delivery to repair such programs. Independent branch progress and fresh evaluation after interruption remain unchanged.

### Session operations

Workflow Runtime owns the durable Run lifecycle: Caller Run Key, Workflow Definition bytes, arguments, Workspace, semantics identity, evaluator limits, Evaluation Generations, keyed calls and original results, cancellation and terminal outcome. Its disposable evaluator is private implementation. Session core owns ordinary Session admissions, execution and outcomes; Workflow Runtime invokes that API without access to core tables. Separate ownership does not require separate processes or database files.

Session keys are opaque caller-scoped values accepted unchanged by the core within a Store. The illustrative workflow helper `session(name)` scopes a short local name by Run identity and returns a reference immediately, with no core request or claim that the Session exists. An exact full Session key can be used directly in configuration or messaging, including from another Run. Do not rescope, trim, normalize or replace a supplied full key. Key possession grants no access. Exact representation and function spellings remain implementation work; Session key, Run Key, Request Identity and internal Turn identity stay distinct.

`configureSession(reference, configuration, { key })` and `sendMessage(reference, message, { key, ... })` describe durable requests. The first accepted complete configuration atomically saves the Session, baseline, Workspace, access scope and original core request answer. An incomplete first configuration or message to an unknown key records a definite rejection without partial Session state. Later configuration applies supplied mutable fields in admission order, with no special original-baseline comparison. Immutable Workspace/access constraints and ordinary validation still apply. Configuration creates no Turn or model work and resolves its workflow Promise on committed acceptance; a message's workflow Promise resolves to its original bound work's final result, after the separate admission acknowledgement.

Awaiting configuration before describing a message creates an ordinary JavaScript dependency on successful configuration. A fresh evaluator may be needed to observe that acknowledgement, but no generated-ID discovery, creation-reference resolver or native dependent-failure graph is involved. Configuration remains committed after a later message failure. Concurrent clients may interleave updates and messages; no cross-call lock, historical revision guard or rollback is promised.

The Session request-construction boundary and optional persistent output schema remain accepted. New requests use current committed settings; admitted model requests and replacement Attempts retain frozen inputs. Explicit instruction updates preserve every admitted update, including A → B → A and fresh A → A, in their eventual model-visible history; same-request replay creates no duplicate. Other supported settings and exact wire shapes remain with their owners. See [Session initialization](../design/session-initialization-proposal.md) and [instruction history](../design/instruction-update-history.md).

### Shared request identity and independent submission

Core configuration and message admissions use the same Request Identity contract for direct and workflow callers. Each key binds operation kind, complete canonical inputs and its first committed answer, including a definite rejection, atomically with accepted core changes or rejection. Check an existing binding before reevaluating current conditions: matching repeats recover the original answer, while changed inputs conflict. A message rejected before initialization stays rejected under that key afterward. Deliberate fresh submissions use fresh identities. Malformed envelopes without usable identity and storage failure preventing commit cannot promise a saved answer.

Workflow Runtime deterministically scopes each Run-local call key by Run identity to form its core Request Identity. A fresh Run therefore has different request keys even when targeting the same full Session key. Encoding must distinguish namespaces/components unambiguously. Before submission, save the exact request identity and inputs as a Workflow Submission Intent. Then call the core and save its acceptance/rejection separately. Recover unanswered intents by resubmitting the original identity and inputs. The core does not inspect Run state, own Run membership or enforce Run cancellation. Its saved answer and the workflow's answer record have independent transaction owners. This is recoverable admission, not exactly-once external execution.

Message admission binds to its original selected work; several message requests may share an internal Turn and final outcome. Observation by request identity never substitutes a later Session result. Workflow Runtime obtains original results through the core API and saves completed results and stable failures in its own records. Separate invocations of an equal keyed workflow call deserialize the original saved result independently; object-valued results are distinct across invocations, while repeated awaits of one Promise retain ordinary JavaScript identity. No bridge-owned decoded-answer cache survives handoff, and user-held values remain charged to the engine heap.

Each evaluation starts from source against the immutable Visibility Snapshot frozen from those saved results, returns all encountered calls and waiting/value/failure outcome, then exits. JavaScript alone determines branches, joins and the returned root. One newly available dependency can justify reevaluation while unrelated dependencies remain unresolved; the surrounding runtime does not interpret Promise dependencies or construct another workflow DAG. No live result enters an evaluation, and no JavaScript heap, continuation, bytecode or callback survives a durable wait. Native reads of prepared immutable input remain permitted. V1 supports deterministic joins and excludes `Promise.race` and `Promise.any`. See the [private evaluator boundary](../design/evaluator-coordinator-boundary.md).

### Completion

Workflow completion follows the value or Promise returned by the workflow entry function. A fulfilled returned Promise (or immediate returned value) supplies the Workflow Output, subject to strict-data validation and the existing admission/publication fences. An unresolved returned Promise suspends evaluation with its complete encountered unresolved call set; a rejected returned Promise is a workflow failure under the existing failure path. Do not require every encountered call to resolve before accepting a fulfilled root, and do not reject a workflow merely for an unawaited call. JavaScript constructs dependencies as it executes; the Host neither builds a separate DAG backwards from the return value nor reconstructs Promise reachability.

A successful evaluator result must include the keyed calls encountered during evaluation even when the returned Promise has fulfilled. Process those descriptors through the same complete prevalidation and independent admission path before publishing successful Workflow Output. Already admitted Session work keeps its ordinary lifecycle after workflow completion; completion is not an implicit stop or cancellation. A terminal Run is not reevaluated when that work finishes. Unawaited JavaScript continuations do not survive evaluator exit and are not promised later execution; await or join any continuation whose work or value is required. This adds no detached workflow worker or background Promise lifecycle. Complete unresolved-call capture is a conservative eligibility basis only while the returned Promise remains pending, not a requirement to wait after it fulfills.

### Eligibility and crash recovery

Workflow reevaluation uses one asynchronous pull loop within the existing Host. When evaluator capacity is free, Workflow Runtime selects the oldest eligible Run from its saved facts, ordered by creation time with a stable identity tie-breaker. For a suspended Run, a result now available for any dependency unresolved in its latest published evaluation permits reevaluation; a whole-join completion test is not required. Some evaluations may therefore only observe partial join progress and suspend again. New Runs and interrupted admitted generations are separate discovery cases. Revalidate cancellation, terminality and generation identity before admission. A fresh generation binds one immutable Visibility Snapshot. After a Host crash, abandon an interrupted evaluation and admit a fresh generation using currently available original keyed results; do not reconstruct the interrupted snapshot. Retain committed keyed operations and their original results, and discard unpublished calculations and incomplete dependency/output publication. Equal-key replay reuses committed work; changed kind or inputs conflict. A replacement generation fences publication and command admission from the abandoned generation. Recovery eligibility does not require a newly finished dependency: interruption itself requires a fresh evaluation, subject to cancellation and terminality. A committed generation outcome remains authoritative; a committed terminal Workflow Output is not reevaluated. Snapshot capture must remain fixed within one evaluation, but no durable per-call first-visible-generation marker or historical visibility reconstruction is required solely for crash recovery. This changes workflow evaluation recovery only; model retry and unified uncertain-tool recovery retain their own contracts.

After one evaluation's publication or failure handling and physical cleanup, give other ready Host work its ordinary bounded service turns, then look for another eligible Run without an intentional polling delay. Only a check finding no eligible work arms a one-second asynchronous idle timer. On expiry, perform a current check; do not accumulate missed ticks. Startup enters the same discovery path. This is not a one-evaluation-per-second rate limit or a hard discovery deadline under contention. Model/tool I/O, controls and settlements continue while the evaluator or idle timer is awaited. SQLite still occupies its owning connection while a statement executes; asynchronous driving does not make that work concurrent or preemptible.

### Visibility capture and decoding

Supply results on demand from fixed disposable input rather than requiring all visible answers to be decoded before source execution. Within Workflow Runtime persistence, capture the exact available Run-local keys, outcome tags and original immutable result references in one visibility read transaction; the read view, not an earlier generation-admission timestamp, defines inclusion. That transaction may write its private charged snapshot-metadata scratch and ends before result-body materialization or evaluator execution. Captured original results must remain immutable and retained through their existing Run/result ownership until materialization finishes. Do not add a separate lease owner merely for this input. Outside the visibility transaction, materialize only captured references through their owning bounded content interfaces, finishing SQLite access before each scratch write and giving other Host work service between windows. This capture never joins core tables or requires a simultaneous cross-Session observation. A result arriving after the captured view stays absent from that evaluation. Exact index/file layout is implementation work; keys use lossless exact comparison and lookup order cannot depend on invocation order.

Native result lookup decodes a requested original outcome and releases the bridge's reference after handoff. Missing, successful null and stable failure remain distinct; malformed ranges, unavailable captured content, short reads and decoding failures are evaluation failures, not missing results. Repeated lookup can repeat I/O and decoding. Lookup, key comparison, decoding and encoding remain within native allocation and CPU/lifetime protection. On-demand loading removes mandatory preload and bridge retention; it does not promise that simultaneous user-held values or an individual decoded result fit the engine heap. No custom promise-delivery scheduler or historical delivery order is introduced. Temporary input is non-authoritative and discarded after interruption.

### Validation and publication

Capture and completely validate evaluator output before admitting its requests. Capture each call's inputs at invocation time, with JavaScript-specific strict-data checks before serialization. Prevalidation checks all encountered existing bindings and consistency among repeated keys; a known mismatch fails before new requests from that output commit. Equal immutable bindings are reused through read-only comparison without reapplying an operation or opening a mutation transaction solely for replay. New calls retain encounter order. Workflow Runtime rechecks call identity, generation and Run cancellation before saving each new submission intent; the core independently rechecks request identity, access and current Session applicability in its admission transaction. A saved unanswered intent remains recoverable even if cancellation subsequently arrives. Retain committed prefixes after a later failure or crash; never claim whole-generation rollback or incomplete successful output.

Between admissions and bounded validation/materialization stages, give controls, cleanup and settlements service through the existing Host driving path. Release active SQLite statements and borrowed shared workspaces before returning; retain only owned scratch and bounded traversal state. Sequential streaming validation does not require a manually yielding parser or a separate worker. Individual library calls and atomic SQLite publication may block; integrated measurements must establish the control-service target. These turns do not start another workflow evaluation before the current lifecycle ends. No grouped commit policy or durable admission cursor is added. Final complete dependency/outcome publication remains one atomic transaction with final generation/cancellation checks.

For a suspended outcome, publication records the generation's complete unresolved dependencies as the next eligibility basis under its atomic generation-publication boundary. A terminal outcome is authoritative and creates no next reevaluation obligation from unawaited calls. A dependency unresolved in that snapshot remains represented even if its result committed meanwhile, so the next pull sees it. A result already considered by that evaluation does not alone keep it eligible. This same current-fact query handles results arriving before dependency publication, during evaluation, and before Host restart. Workflow discovery requires no Turn-completion hook, deferred completion-ID queue, subscription registry or maintained durable ready set. Waiting Runs retain no evaluator, callback or payload-bearing resident queue; one shared idle timer serves discovery.

Select through bounded resident query/workspace state without loading all waiting or eligible Runs. Use oldest-eligible selection without a rotating cursor, sweep state or ready queue, and give controls/settlements service between discovery/evaluation turns. Evaluate this policy against millisecond evaluation lifecycles and Turn completions taking seconds to minutes. This policy does not promise starvation freedom under sustained evaluator overload; aggregate completion demand and discovery cost still require qualification. Query plans, examined work, selection fairness, the concrete generation/publication mapping and qualification against the existing idle-CPU and control-response targets remain required evidence. A small result limit alone does not establish bounded lookup work. The [readiness comparison](../design/workflow-readiness-comparison.md) records the chosen pull loop and the limitations of its synthetic measurements.

Workflow Output has no independent total serialized-result byte cap. Serialize through bounded windows into charged scratch and stream parent capture instead of materializing a complete encoded output frame in both child and parent. The JavaScript result and native conversion/validation state remain subject to their actual memory owners, and evaluation/encoding remain subject to finite work/lifetime protection. Shared scratch exhaustion, memory exhaustion or time exhaustion produces explicit failure, never truncation or a partial successful Workflow Output. Complete validation and canonical content/outcome publication retain their existing atomic boundary. Protocol length representability and strict-data invariants still apply; they do not justify copying the historical 64 KiB result or 512 KiB frame capacities into product quotas. Separate the historical descriptor-scratch use of `workflow_output_bytes` and derive that workspace from its real consumer. This accepted contract requires bounded serialization/capture before removing current buffer-safety checks; the initial engine heap limit is specified under Disposable evaluator construction, while time policy and native workspace derivation remain separate. It does not promise that arbitrary JavaScript result graphs fit.

Cancelling a Workflow Run saves cancellation intent and fences new evaluation/call creation. Recover every saved unanswered submission using its original request identity and inputs, then record the core answers. Previously undelivered requests may now commit configuration or start work before a subsequent stop; that effect/cost window is accepted. Apply ordinary stops to current work in every distinct Session reached through accepted message calls. Reference declaration, accepted configuration and reads alone add no stop targets, and configuration is not rolled back. Core admission has no Run-aware fence.

Cancellation cannot complete while an unanswered submission or required stop remains unresolved. A crash before durable cancellation completion may repeat the complete stop pass, including previously successful or idle stops; callers coordinate sharing because newer work can be stopped. Once terminal Run outcome records cancellation completion, recovery does not propagate it again. Use existing Run intent/outcome and ordinary Session stop facts, without per-Session propagation receipts, idle-check rows, durable cursors or a cancellation queue. Tool uncertainty still prohibits replay. See [shared request identity](../design/shared-request-identity.md) and the [cancellation recovery trace](../design/workflow-cancellation-stop-mapping.md#accepted-simplification).

## Run interface

The local adapter exposes Workflow Runtime operations to create/attach, observe and cancel Runs, alongside ordinary Session core configuration, messages, observations, Permission Decisions, exact Model Interruption and Session stops. Workflow Runtime is the public workflow module and contains its private evaluator; there is no separately instantiated evaluator or Run Service required of callers. Ordinary Session operations keep Turn identity internal. Each verb owns its distinct authority, concurrency, idempotency, and transaction contract; there is no generic native command or result union.

`drive` is a separate Host scheduler operation. One bounded quantum may settle evidence, admit consequences, release committed external work, and compose several individually atomic transactions before stopping at quiescence, an observable block, terminality, interruption, or quantum exhaustion. It is not one atomic mutation and returns only a small drive report. The server repeats it while immediate runnable work remains. A pending external execution that cannot reserve Active Capacity is not immediate runnable work for this loop; it must not cause repeated driving without a resource or eligibility change. Client mutations admit intent; they do not own scheduling, and no public `advance` call is exposed or required.

Between individual ordinary result settlements, give ready stop/cancel requests and their due cancellation cleanup bounded service turns through the existing Host driving path. A prompt durable stop acknowledgement must not leave already-sealed cancellation evidence and releasable custody behind an entire ordinary-result backlog. Preserve each settlement transaction's atomicity and retain custody until effect-specific physical release is safe. These service turns do not preempt an in-progress import or transaction; ordinary settlement and inspection must also make progress under sustained ready controls. Use the existing owners and custody table. The [saturated-workload control-acknowledgement target](../verification/resources.md#accepted-host-qualification-targets) governs qualification; it does not make an individual capture, transaction or library call preemptible. SQLite import and non-inspection command-work policy remains with the SQLite resource decision; inspection query shape, read ownership and responsiveness belong to the separate inspection decision below.

The single I/O Reactor services ready cancellation between individual socket events and between completed-transfer notifications, rather than waiting for an entire ready-network batch. Perform transport removal outside library callbacks and preserve handle, completion-message and descriptor lifetime rules when cancellation changes the ready set. One socket or timeout action and its callbacks remain non-preemptible; this service structure alone does not establish a strict latency bound. The supported transport library/build remains a separate qualification decision.

### Inspection

Run inspection composes Workflow Runtime records with ordinary Session core observations. These may represent different committed moments and briefly lag. Do not promise a global revision or cross-owner read transaction, and do not let workflow inspection query core tables directly. Each owner keeps its own observation consistent; exact-target controls validate current authority when admitted. Evaluator visibility is a different contract: one fixed set of workflow-recorded results per live generation.

Inspection exposes each associated durable Session's exact full key and enough existing label/context for an agent to select the intended conversation. Derive association from recorded accepted configuration or message calls, including configured-only Sessions; a locally declared reference alone establishes no durable association. Repeated calls to one Session need not create duplicate Session entries. Recover a lost submission acknowledgement before relying on its association. The message-only cancellation stop set remains narrower than this inspection set.

An agent can inspect W1, identify a Session, and type its full key directly into W2's configuration or message call. W2's own request keys remain scoped to W2. No Workflow Output metadata, previous-Run result plumbing, new attachment call or clone is required. The key addresses the shared Session's current state and history, not a snapshot from W1 or exclusive ownership. Keep previously bound message results immutable when that Session later advances.

Capture the complete composed report through bounded private traversal and charged scratch, release each owner's database resources before client delivery, and clean up scratch after success, failure or abandonment. A slow client retains no database transaction. No public cursor, collection cap, caller page size or serialized continuation token is introduced. Core read costs, workflow traversal, encoding and aggregate scratch require measured whole-Host latency; small result batches do not prove bounded total work. [ADR-0024](../adr/0024-capture-run-inspection-before-delivery.md) retains capture-before-delivery, amended by independent workflow/core ownership.

Between queued reports give ready controls and settlement/advancement ordinary service opportunities, while inspection also progresses under sustained ready work. Individual observations, SQLite calls and publication remain non-preemptible; no manually yielding parser, second reader or new scheduler follows. Measure each class's queueing and service cost against [Host qualification targets](../verification/resources.md#accepted-host-qualification-targets). There is no new hard capture deadline or abort quota.

Encoding and escaping use fixed-size windows and block scratch writes without whole-field/report materialization. Larger permitted strings stream across windows; prototype buffer sizes select no production constants. Every actionable Permission Request and other logical collection member appears with its observed state. JSON belongs to the HTTP adapter and Markdown to the CLI, with compiled public types and exhaustive golden fixtures owning exact field names. Truncated capture or delivery fails explicitly. Client interruption detaches; server termination pauses execution until explicit restart.

### Observation and wire contract

Each accepted message call retains its original work binding and is summarized in one category reported from committed core facts: `runnable`, `waiting_for_permission`, `in_flight`, `completed`, `failed`, or `cancelled`. Derivation has an exact precedence: terminal Outcome wins; otherwise an unresolved Operation with current admitted-execution facts or current future retry eligibility is `in_flight`; otherwise an actionable Permission Request with no remaining progress is `waiting_for_permission`; otherwise the nonterminal Turn is `runnable`. A retry-delayed Turn therefore remains `in_flight` even when it owns no Active Credit and no physical effect is live. `permission_required` is reserved for Run state. The core Request Identity binds atomically to selected work, which may already exist; Workflow Runtime records that answer separately, and its result never retargets to later Session activity. These observations establish no core-side Run membership relation. Public wire variants are compiled from this contract, not inferred from historical membership names.

Direct Session observation reads fresh committed facts. Waiting selects current work once at observation start and does not follow subsequent work indefinitely. History reads support recent entries, kind filters, and after-position queries; unapplied message content and reasons remain separately reachable without replaying history in every poll. These reads grant no remembered caller view, Session ownership, or historical revision precondition on later messages. Exact remaining public boundary choices stay in the Session/client decision; compiled public types and exhaustive golden fixtures own field names, tags, omissions, and string encoding of `u64`-class values. No handwritten duplicate wire schema is accepted.

## Disposable evaluator construction

Workflow Runtime treats its private evaluator as one disposable computation: supply the immutable generation inputs, receive and validate a complete outcome, and finish child/pipe cleanup. The evaluator owns its JavaScript engine and native working storage internally; they are not separate workers or services. SQLite retains workflow authority between evaluations, with no resident evaluator state while the workflow waits for external work.

The evaluator receives an empty environment, three explicit stdio pipes and the explicitly selected read-only descriptors for completed disposable workflow input. The Host closes all writable input handles before handoff; descriptor construction and close-on-exec own inheritance. Native bridge code may perform positional reads on those input descriptors. Workflow JavaScript receives no paths, raw descriptors, filesystem, process, imports, FFI, network, clock, randomness, credential or storage API. This permits no child-side pathname open or SQLite access. Core dumps remain disabled. Do not scan every descriptor number up to `RLIMIT_NOFILE` at each invocation, retain a process pool, or overwrite/free complete input/output/bridge mappings immediately before this disposable process exits. Those mappings have process lifetime and no subsequent in-process owner. This is not a sandbox guarantee after arbitrary native-code execution. The containment limits below govern this lifecycle; descriptor and native workspace capacities remain implementation derivations.

V1 runs **one evaluation at a time per Host**. The Host services model/tool I/O and controls asynchronously while the evaluator runs. Finish outcome validation/publication or failure handling and safe child/pipe cleanup before starting the next evaluation, so exited children cannot leave a growing backlog of captures or native workspaces. This serializes workflow evaluation, not model/Bash/Edit execution. Waiting work remains derived from canonical SQLite facts without a retained evaluator or per-waiter resident queue; the asynchronous pull loop under Workflow Runs owns discovery. Bursts may wait for earlier evaluations; no sub-second completion guarantee for a burst of 1,000 workflows follows.

Each evaluation has a **1-second process CPU budget** and a **5-second parent-owned elapsed lifetime deadline**, measured from successful child spawn through complete protocol delivery and child exit. Apply CPU protection to native evaluator work as well as JavaScript, including decoding, compilation, job draining and encoding. Waiting before spawn and external model/tool execution consume neither evaluation deadline. Parent preparation and canonical publication retain their own bounded-work contracts. Derive cooperative checkpoints and the coarse kernel CPU backstop from this policy and OS granularity instead of exposing independent timing knobs. On confirmed exhaustion, fail explicitly without truncated or partial successful output; do not infer a specific resource cause from an unexplained signal. Deadline expiry initiates termination, but cleanup remains owned until actual pipe closure and child reap. These are enforceable deadlines subject to OS scheduling, not hard real-time termination guarantees.

The initial engine-managed JavaScript heap limit is **16 MiB per live evaluator**. This is an allocation ceiling, not memory reserved for every workflow or a whole-process physical-footprint bound. Full replay, report serialization and Store publication must qualify under this limit before release; generated assembly probes alone do not establish compatibility. Native memory and concurrent evaluator population remain separately accounted.

Evaluator native allocations outside the QuickJS heap have explicit bounded ownership. Reuse temporary storage when one phase has finished and no retained reference needs its contents; parsing-key validation and later request encoding may share storage when their lifetimes do not overlap. Retained source, request metadata and canonical request copies remain charged to their actual owner. Engine heap limits do not cover native frames, workspace, stack or parent capture. This requires no additional process, pool or custom combined allocator. Derive the native workspace capacity from the selected representation and workload evidence; the historical 2 MiB arena is not an accepted numeric V1 limit. Buffer capacities and allocation layout are internal implementation choices, derived and verified against the supported workloads and aggregate OnePage footprint. They do not require independent caller configuration or a separate product decision for each allocation. A change that restricts supported workflow behavior or misses the whole-Host target requires explicit review; calling a cap internal does not exempt it from that obligation.

Do not impose independent evaluator source, arguments, aggregate visible-result, total-entry, request-count or microtask quotas merely to preserve historical fixed buffers and tables. Replace those representations with bounded allocation, transfer and work checks at their actual owners. Source compilation may still require contiguous storage within its allocation budget; JS values and request/key metadata consume their respective bounded memory. Preserve existing bounds checks until replacement storage and traversal are safe. Replace the microtask quota with CPU/lifetime checks through job draining and native phases. Resource exhaustion remains explicit; no truncation, missing request, retargeted replay or partial successful publication is permitted.

Retain strict-data/type/prototype/accessor/cycle validation, duplicate-key and exact request-binding checks, checked arithmetic and wire representability, engine/native recursion protection and bounded diagnostics. These protect distinct correctness or resource boundaries. Their internal storage/stack capacities are derived and qualified, not copied into independent workflow-size policies.

The supported macOS V1 build has no fixed 64 MiB address-space policy. Retire the historical setter/constant rather than enabling a setter the supported machine rejects, or treating virtual address space as physical memory. Engine/native allocation ownership, single-evaluator population, CPU/lifetime enforcement and whole-Host physical-footprint qualification provide the selected resource model. This does not add an RSS polling killer or platform memory service. Linux uses the same selected allocation, CPU, stack and parent-lifetime ownership without an independent address-space or RSS-killer policy. The [platform evidence policy](../../VERIFICATION.md#platform-qualification) requires honest distinction between available-Mac runtime checks, portable API/dependency evidence, cross-compilation and unexecuted target behavior; it adds no mandatory Linux runtime fleet.
