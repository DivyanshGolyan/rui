# OnePage execution architecture

This is part of the normative [ARCHITECTURE.md](../../ARCHITECTURE.md) contract. [Corresponding verification](../verification/execution.md) supplies the required checks.

## Required execution and recovery guarantees

[ADR-0025](../adr/0025-enforce-execution-contracts-without-historical-replay.md) separates required behavior from the execution representation. Persist facts needed by a recovery consumer or a concrete product promise. Diagnostic usefulness alone does not require permanent failed-try history. Enforce local delivery and resource-lifetime rules in the owning adapter and execution machinery; durable history must not compensate for an ambiguous producer contract.

| Scenario and consumer | Required behavior and recoverable information |
| --- | --- |
| Crash around dispatch; recovery owner | Admission precedes launch. Preserve the exact admitted work, authorization where applicable, execution identity and consumed allowance needed for conservative recovery; restart cannot recreate launch authority for the old try. |
| Model request has no saved result; Host | Retry unresolved work under the existing policy using its frozen manifest and remaining allowance. Restart never resets consumed allowance or future retry eligibility. A replacement may incur duplicate provider work or billing. |
| Bash result is lost; Agent | Never automatically replay uncertain execution. Preserve enough admitted intent and uncertainty to return an indeterminate Tool Result so the Agent can inspect external state. |
| Edit result is lost; Agent | Preserve the exact authorized proposal and admitted uncertainty. Return an indeterminate Tool Result without automatic replay or required target inspection; the Agent can investigate through ordinary tools. |
| Result acceptance; Conversation and workflow consumers | Commit the accepted result and its semantic consequences atomically. Recovery observes committed meaning without accepting another result or executing the effect again. |
| Model continuation; provider adapter | Preserve accepted output, ordered semantic projections and exact required provider continuation with their request/provenance bindings. Diagnostic logs cannot replace this authority. |
| Stop or interruption; recovery owner | Preserve applicable intent, exact target and committed outcome. Transport cleanup does not manufacture a semantic stop, prove remote cancellation, or allow a stopped Operation to retry. Existing shared-Session Run cancellation semantics remain in force. |
| Duplicate public submission; Caller or evaluator | Preserve original keyed configuration/message admission answers for direct and workflow callers, including committed rejections, plus existing permission/control repeat rules. These are separate from internal evidence delivery. |
| Old execution notification; live execution owner | Terminal delivery is at most once per execution. After delivery or detachment, suppress further result delivery and reject stale identities before they can affect reused custody or newer work. No historical payload comparison or old-Completion replay service is required. |
| Failed-try inspection; operator | Complete permanent failed-try diagnostics are not a V1 promise. Retain any failure facts still needed for recovery, retry accounting, accepted results or other canonical references; other details may be diagnostic telemetry. |

The [accepted comparison](https://github.com/DivyanshGolyan/onepage/issues/105#issuecomment-5556881068) supports the Operation-owned execution and final-result model selected in [ADR-0026](../adr/0026-let-operations-own-current-execution-and-final-results.md). The guarantees above apply independently of diagnostic history; accepted output and public replay remain canonical.

## Host Runtime execution and settlement

### Execution facts

An **Operation** is one model request or admitted Action. It owns immutable request/descriptor and causal bindings, current execution/retry facts, conserved policy accounting, and an optional immutable **Operation Resolution** value. Its ID identifies both the work and its eventual result; no separate Resolution ID or Completion-owned result chain exists. Ordered Model Output Items and other required final content belong to that Operation and remain separate immutable content references, never inline resident payloads.

An **Attempt** remains one physical try, identified by its Operation and a fresh, non-reused ordinal. Admission records that current identity on the Operation; historical Attempt and Completion rows are not authority. **Execution Evidence** is a transient terminal delivery from the effect owner, not a durable entity or publication queue. The Host imports only facts required by current retry policy or final meaning; other details follow the diagnostic contract.

Current facts distinguish unambiguously: no Attempt admitted; an admitted Attempt without saved terminal evidence; and a retryably completed model Attempt with policy-relevant failure facts and future eligibility. These are the recovery facts, not an additional cached lifecycle phase beside another representation. A Resolution is absent in each unresolved case. Once a Resolution commits, it and its required evidence/provenance cannot be replaced, retry eligibility is inapplicable, and further admission or acceptance for that Operation rejects. Permission denial, validation, interruption and cancellation can resolve work without inventing an Attempt or effect evidence.

Attempt admission atomically validates applicability, absence of Resolution, selected retry policy and any due time; records the fresh identity; consumes allowance at its actual scope; and replaces prior waiting eligibility with admitted uncertainty. Rollback preserves the prior facts and emits no permit. Retryable terminal settlement atomically replaces admitted uncertainty with the required current retry classification/eligibility and preserved accounting, without a final Resolution. Every due-work selection revalidates in the admission transaction. Restart, a new try, final settlement or compaction cannot reset consumed allowance. Exact policy and numeric values remain with their existing decision owner.

### Admission and dispatch

The Session core owns its semantic transactions through SQLite-specific storage code. One meaningful durable operation uses one cohesive transactional function: validate bounded syntax and complete content before the transaction; reserve a custody record when execution admission requires it; start `BEGIN IMMEDIATE`; read bounded saved facts, check applicability and apply the mutation; verify affected rows; commit; then release any external consequence. A mandatory pure classifier, Decision Snapshot or mutation interpreter is not required. Helpers earn extraction through concrete reuse. State-dependent checks remain inside the transaction, and rollback releases unused reservations without granting dispatch authority.

Workflow Runtime owns its Run records and uses the core API. It records exact submission intent before calling core and saves the returned answer independently. Core admission and workflow bookkeeping do not share a transaction or read each other's tables. Each connection retains single-owner access; physical database placement does not change these semantic boundaries.

One I/O Reactor multiplexes long-lived provider streams and subprocess pipes and observes temporary Action executors, including Edit. Execution machinery owns only volatile OS and library handles plus fixed borrowed windows while work is active; it cannot access SQLite or decide semantic meaning. One startup-allocated, fixed-size content-free Physical Custody table implements Active Capacity: occupancy of one record is one Active Credit, not a second object or pool. Waiting Sessions retain no per-Turn driver, worker, Session graph, payload buffer, parser workspace or lifecycle object. No permanent Edit lane is introduced.

After Attempt admission commits, the Storage Owner asks the selected adapter to materialize an outbound request from the frozen manifest and canonical source items into an immediately unlinked scratch file through fixed windows. Neither the generated request body nor a second replay representation becomes authority. Execution consumes that descriptor and streams inbound bytes directly to another immediately unlinked scratch file. No SQLite transaction spans request construction, network or subprocess execution, filesystem mutation, or response streaming, except that the inspection read transaction may span its private report-scratch writes under [inspection capture](workflows.md#run-interface); Workflow Runtime may similarly write private metadata while capturing its own recorded result visibility under [Workflow Runs](workflows.md#workflow-runs). Scratch is dynamically charged, non-authoritative, and nonrecoverable; a process crash discards it and leaves the Operation's current admitted Attempt unresolved for effect-specific recovery. Tool output has the additional temporary spillover consumer described below; retaining that output after settlement does not make it durable execution authority.

### Evidence and settlement

Only after transport or execution reaches an effect-specific terminal boundary does its effect owner seal the scratch descriptor and hand it to the Storage Owner. The Storage Owner uses one shared serial validation/import workspace to parse complete model output or tool evidence, then normally commits immutable content, the Operation's Resolution value and required final provenance/evidence, Conversation or permission facts, and the next semantic consequence in one transaction. Retryable model evidence instead commits only current retry facts and eligibility on the unresolved Operation. SQLite current eligibility is the retry queue; one periodic bounded query while the Host is running is the only V1 retry-eligibility trigger.

Validation is sequential after complete capture, with bounded resident memory. It does not require manually yielding parser continuations or a validation worker without measured need; bounded memory does not establish a bound on transaction or validation elapsed time.

The post-seal model parser represents variable input as byte ranges into the sealed scratch source, with bounded resident token, nesting, and validation state. Use one sequential, immediately unlinked metadata file for the current shared serial validation/import workspace to record item ranges. Traverse it through fixed windows after complete validation rather than reparsing the entire response inside the import transaction. Its growing bytes count against the shared scratch allowance; release it after import or failure with safe I/O cleanup. This is one implementation file role, not a per-item file collection, resident index, separate quota or per-execution parser workspace. Additional metadata required by the complete provider validator remains bounded in memory and charged if scratch-backed; the prototype's 16-byte start/length pair is evidence for that representation, not a universal provider-metadata size. After complete provider validation, the Storage Owner imports the selected content incrementally within the existing atomic settlement transaction, preserving exact bytes wherever the provider continuation contract requires them. Decoding and projection use bounded windows rather than response-sized strings or an in-memory object tree. A late validation error or failed import cannot publish partial success. The ranges and index are private, non-authoritative preparation state: they grant no independent publication, recovery, or replay capability and are released with their scratch sources. Durable Model Output Items and explicit manifest references retain their existing authority. This refines the existing serial validation/import workspace; it does not require sharing that storage with inspection.

Variable caller content enters through a sealed source supplied to the semantic mutation that first references it. The public APIs expose no independent content-publication operation or caller-visible staged Content Reference. The Storage Owner verifies exact length, digest, media or schema type, and stable positional bytes while importing under its owning content and command-work contract; no semantic row may reference incomplete or unvalidated bytes.

The adapter and effect owner provide at most one terminal Execution Evidence delivery for each Attempt; after delivery or detachment, they suppress further delivery. The Host owns retry policy and semantic acceptance. Live identity checks prevent stale events from affecting newer execution, and a result cannot replace already committed meaning. No internal service promises to return or compare historical Completion payloads on resubmission. Cancellation records intent and may signal the live owner, but only the effect-specific terminal owner may propose Execution Evidence. This removes the generic Completion Inbox, consumption watermark, two-transaction admission protocol, online stream detector, and scratch replay path.

The explicit model-interruption operation targets one exact unresolved Model Operation in nonterminal work. It validates the Local Owner, exact target and its canonical parentage, and current applicability in one transaction. The Interrupted Resolution retains the exact command target and causal provenance; domain repeat/conflict rules recover the prior result or reject conflicting/inapplicable input without a generic command ledger or mandatory direct caller key. No whole-Run revision gates the operation, and ordinary Session controls do not require callers to name a Turn. Its semantic mutation is setting the previously absent Resolution value on that Operation. It neither stops the whole Session nor decides whether another Operation follows. Ordinary advancement derives continuation only when independently admitted User Messages are applicable; otherwise ordinary terminality derives the cancelled Turn Outcome. Remaining observable repeat/error details belong to the Session/client decision, not an implementation-ticket copy.

An intentional model interruption may commit an `Interrupted` Resolution without inventing terminal Execution Evidence. It prevents acceptance and retry of that work, without claiming remote processing or billing stopped. The local execution owner orders interruption against completion, fences further application-result publication, suppresses an unconsumed Dispatch Permit or detaches an active transport, and retains callback state and custody until cleanup is safe. This is one local owner's ordering responsibility, not a generic late-result arbiter. Partial, interrupted and late provider output never becomes durable continuation. Actions have no independent interruption command; ordinary Session stop follows their safe settlement rules.

The V1 cancellation command targets one exact Workflow Run. Workflow Runtime validates the Local Owner's command and request binding and durably records Cancellation Intent under its repeat/conflict rules. This fences new evaluations and new call creation. It then resolves every already-saved unanswered submission by sending its exact original identity and inputs through the core API and recording the answer. Some requests may be delivered for the first time during this sequence: resulting configuration changes are not rolled back, and admitted work may incur cost or effects before a subsequent stop. Those costs are accepted. Core has no Run cancellation fence or Run membership policy. Cancellation cannot complete while saved submissions remain unresolved.

An ordinary Session stop selects the current work once and fences its further advancement. Stop completion is the selected work's durable terminal outcome and atomic logical Session occupancy release; an idle stop completes immediately. Acknowledgement of the saved request is distinct from completion. Completion follows the selected work rather than future Session activity, and a stop does not rewrite an outcome committed before its admission. Existing tool Resolution and ordered Tool Result obligations must settle first. Model transport suppression/detachment may finish afterward under its existing Physical Custody owner, with Active Credit retained until release; logical completion does not free resources still in use or prove that a remote provider stopped processing or billing.

Workflow Runtime applies ordinary Session stops through bounded traversal of Sessions identified by its accepted message answers after recovering unanswered submission intents. Reference construction, configuration, or reads alone do not add Sessions. Each stop serializes with advancement and affects the selected current work regardless of which Run submitted it. A Session may be idle; stopping it is then a no-op. Other Runs observe the stopped outcome without themselves being cancelled. This control path remains permitted after the Run evaluator is fenced.

An unfinished cancellation pass may restart from the beginning after a crash. Use bounded disk queries and a disposable traversal position; do not persist per-Session propagation receipts, idle-check results, or a progress cursor. A stop that previously succeeded or found an idle Session may select newer work during the repeated pass. Callers coordinate Session reuse while cancellation is unfinished. Workflow cancellation completion composes ordinary Session-stop completion for every Session in the pass, regardless of which client submitted the work selected by a stop. There is no separate predicate that waits only for work submitted by the cancelling Run. Use the Session-level completion rule above; workflow cancellation adds no different effect-settlement policy. Request the required stops promptly through bounded traversal before awaiting completion, so one slow tool cannot delay stopping later Sessions. Every stop in a full pass must complete under that common contract before the existing terminal Run outcome can record cancellation completion; once that outcome commits, replay/recovery never runs the pass again. A crash after the final stop but before completion commit may repeat the pass. Failure to commit is not successful cancellation completion. Exact ordinary stop storage and Run settlement integration remain implementation work; no separate cancellation subsystem is introduced.

Ordinary Session stop authority governs admission and settlement of the selected work. If model-result settlement commits first, its Resolution remains valid and the stop governs remaining work. If the stop commits first, late provider bytes cannot bypass it; bounded driving records Interrupted Resolutions for unresolved Model Operations with causal stop provenance. A directly requested model interruption instead cites its Local Owner and exact command-target provenance. An unresolved Action with no Attempt resolves without execution. An Action with a committed Attempt settles from available evidence or an explicit indeterminate outcome when custody is lost. Active Bash receives best-effort process-group interruption. Edit may stop as not applied before mutation starts; after mutation starts it retains custody for safe bounded execution, observation and cleanup. A failure after mutation is not proof the target is unchanged. Every accepted Tool Call still receives one typed Tool Result in call-ordinal Conversation order.

Pending User Messages and Permission Requests in stopped work become inapplicable through that work's ordinary stop/terminal facts. Their immutable admissions remain; no per-item withdrawal state or resident queue is added. The Session runtime retains effect-specific recovery, cleanup, and safe Turn settlement independently of the propagation loop. Run cancellation completion is not proof that a remote provider stopped processing or billing. No permanent Session fence or protection against overlapping callers is promised.

Attempt admission commits before physical dispatch. Only the invocation that observes that commit receives a volatile one-shot Dispatch Permit; reconstruction never recreates it. The commit records the admitted Attempt on the Operation but does not oblige the owner to launch after a later committed interruption. The local owner orders permit consumption and post-commit suppression at the launch boundary. This determines whether the external effect may have started; it does not choose semantic meaning or require a separate distributed race protocol. Failure while preparing post-commit request scratch is evidence for that Attempt, not authority to erase it.

## Model retries and inactivity

The accepted provider-policy portion of [Choose provider retry and external-effect budgets](https://github.com/DivyanshGolyan/onepage/issues/91) permits three replacement Attempts after the initial model Attempt: at most four admitted tries of one model Operation. Default waits before those retries are 2, 4 and 8 seconds. A valid provider Retry-After is a minimum wait; use the later of the provider time and the default retry time. Persist consumed tries and next eligibility so restart does not reset either. Retry uses the same frozen manifest, including after an uncertain disconnect that may cause duplicate provider work or charges. Ordinary new model Operations have their own retry accounting; there is no aggregate Turn request limit. This does not authorize repeated compaction that cannot make a request fit, automatic redispatch after storage failure, or retries of deterministic incompatible continuation.

Retry temporary connection failures, response-body inactivity timeouts, rate limits and temporary provider-server failures within that same allowance. Invalid requests, unsupported provider responses and authentication failures that credential refresh cannot fix do not qualify for blind retry. Provider adapters map concrete protocol errors into these categories; a permanent error must not become retryable merely because it arrived over the network. Provider-confirmed context overflow takes the existing compaction path rather than an equal-manifest retry. Storage failure and deterministic continuation failure retain their explicit no-automatic-retry rules.

Use a five-minute response-body inactivity timeout while awaiting the first body data and between subsequent incoming body chunks. Any incoming response-body data, including provider heartbeat traffic, resets this timer. A progressing stream has no total-duration deadline. On timeout, stop the local wait through the transport owner and use the same remaining retry allowance; this does not prove remote work or billing stopped. Host admission waits and local request preparation are not provider-response inactivity. Exhausting the retries reports failure and follows the existing safe Turn-settlement obligations rather than bypassing outstanding effects or Tool Results.

The retry count, retry waits, provider-inactivity timeout, tool-output excerpt size and default Bash timeout are adjustable through one Host configuration loaded at startup. The accepted defaults are three retries with 2/4/8-second waits, five minutes of provider inactivity, a 10,000-byte tail excerpt and five minutes of Bash execution. Bash retains its per-call timeout override. No live configuration reload is required. Configuration must not reset consumed tries or already-saved retry eligibility, rewrite an admitted Action's timeout, or change saved Tool Results. Exact setting names and encoding remain implementation details.

Five minutes is an accepted policy default, not a measured maximum provider silence. The [initial timing experiment](../../research/stream-inactivity/OBSERVATIONS.md) observed only three synthetic Codex requests; it does not certify this timeout or Claude behavior. Provider-confirmed context overflow belongs to the compaction machinery and its existing context-change contract; this decision adds no separate one-compaction-attempt limit.

## Effect-specific recovery

Recovery is effect-specific:

| Operation | Uncertain Attempt |
| --- | --- |
| Model | A policy-authorized replacement Attempt may reuse the same Model Request Manifest while recording possible duplicate work or billing. |
| Bash | Never replay automatically. Resolve as indeterminate and show the evidence to the Agent. |
| Edit | Never replay automatically. Resolve as indeterminate without required target inspection; the Agent may inspect and propose a fresh authorized action. |

No tool is automatically re-executed when its admitted Attempt may have started, even if a crash preceded physical launch. Current external bytes cannot prove which actor produced them. Uncertainty alone neither requires User intervention nor terminates the Turn; a model may investigate with a fresh ordinary tool call.

SQLite owns transaction atomicity and recovery. OnePage owns semantic validation, external-effect uncertainty, and causal admission. It does not reimplement the pager or distrust the configured local machine without evidence.

## Tool output and spillover

Stream tool output to temporary files through bounded I/O windows. There is no per-call total output-capture size limit; Host-produced spillover bytes count against the existing shared temporary-storage allowance while OnePage retains their names. External changes and storage held after eviction by other processes follow the [retention scope](resources.md#shared-temporary-file-retention). The default excerpt is the last 10 KB (10,000 bytes) of rendered tool-output text, measured as UTF-8 before provider JSON framing. This is one aggregate allowance for the output shown by a Tool Result, not a separate allowance for each output stream. Preserve valid character boundaries when selecting the tail. Short output is included in full; longer output includes the bounded tail plus a small omission notice and spillover reference. Command status and this bounded metadata are separate from the output excerpt. Large output alone is not a failed Tool Call and does not instruct the model to rerun a completed command merely to obtain less output.

A Spillover Tool Result saves the command outcome, bounded excerpt, explicit omission notice and an ordinary absolute temporary-file path. The Agent uses the existing Bash tool with commands such as grep, tail or sed to inspect selected parts; no separate spillover-read tool or opaque retrieval protocol is added. Inspection is an ordinary new Bash call under existing permissions, timeout and output handling. This result is canonical Conversation content; the full Spillover Output is disposable and is not automatically imported into SQLite as durable content or treated as diagnostic capture. Loss on crash is accepted. Missing spillover must be reported as unavailable rather than silently retargeting its reference, altering the saved result, or automatically executing the old command. The Agent may issue a fresh Tool Call, including a deliberate rerun, under ordinary authorization and effect rules; such a call may repeat external changes.

This adds a temporary-output consumer after command completion, amending the earlier assumption that every tool capture is deleted once its result is saved. It does not require raw provider responses or other private execution scratch to remain accessible. Spillover follows the [shared FIFO temporary-file policy](resources.md#shared-temporary-file-retention), without a separate Turn-end deletion rule or expiry timer. The path-access decision is recorded in [Choose provider retry and external-effect budgets](https://github.com/DivyanshGolyan/onepage/issues/91). A spillover path is not a durable Content Reference. Named spillover is the scoped exception to immediately unlinked private scratch: other internal capture/metadata files keep their existing private access and cleanup. The Host must never reuse a published path for different output, including across Host restart; arbitrary external replacement has ordinary filesystem behavior, not a content-authenticity guarantee. If FIFO cleanup wins before a reader opens it, ordinary file-unavailable behavior is expected. Published spillovers follow that scoped retention accounting: OnePage does not discover or control arbitrary shell-reader lifetimes or external mutation. Private capture and Host-owned I/O retain strict ownership and growth accounting. Preserve bounded metadata/handle use without keeping a completed command's execution slot solely for spillover access.

When shared temporary storage is full, reclaim eligible files through the shared FIFO policy first. If that cannot provide space, or a real storage failure occurs, the accepted effect-owned stop and explicit storage-failure rules still apply. A bounded model excerpt is intentional and disclosed; incomplete full capture caused by failed storage must not masquerade as successful preservation. Required canonical effect evidence and exact authorized Edit intent retain their recovery guarantees independently of disposable spillover; scratch output is never a replay backup.

## Bash execution timeout

A Bash call has an optional `timeout` parameter. When omitted, use five minutes. The selected timeout bounds total command execution from process start, not inactivity: printing output does not reset it. Waiting for permission or execution capacity does not consume the command timeout. Bind the selected value to the admitted Action so execution does not reread an ambient default.

Expiry initiates effect-owned termination and cleanup and produces a typed timeout Tool Result; it does not undo external changes, prove every descendant has stopped, release custody before safe cleanup, or authorize automatic Bash replay. Existing uncertainty/recovery and Tool Result publication rules remain in force. There is no separate policy maximum for a caller-supplied timeout. Accept a positive finite duration that the selected representation and deadline arithmetic can express safely; reject invalid or unrepresentable values rather than clamp them. Exact units and wire encoding remain implementation details. The historical two-minute source ceiling is not retained.

## Native Edit module

The V1 Edit tool accepts one existing-file path and a nonempty list of exact whole-line replacements. Each replacement supplies one-based `startLine`, exclusive `endLine`, expected text and replacement text. Every range refers to the same original file state. Reject overlapping nonempty ranges; adjacent nonempty ranges are allowed. Combine insertions at the same position, or inside or at the boundary of another replacement, into one replacement. There is no search, relocation, fuzzy matching, normalization, replace-all, multi-file batch, creation, file deletion, rename or mode change. Empty replacement deletes the selected text, not the file. File eligibility is independent of Git. Relative paths resolve from the Session Workspace; absolute paths may lie elsewhere under ordinary filesystem access. Workspace is not a sandbox or OnePage path allowlist.

LF separates lines, and CR in CRLF remains an exact byte. An empty file has zero lines; a trailing LF adds no phantom line. For N lines, N+1 is the EOF insertion position. `[4,7)` selects lines 4–6; `[4,4)` inserts before line 4 with empty expected text. Insertion at EOF does not add a newline implicitly. A zero-length range checks its position but carries no text freshness evidence; callers can include an adjacent line in a replacement when they need that check. Preserve all unselected bytes. See [range rules](../design/fixed-location-edit-approval.md#range-rules) for examples.

The exact submitted proposal is sufficient to save and display a Permission Request after bounded shape validation. No target read, preimage snapshot, full-file diff, Git check or preparation executor is required before approval. Authorization binds the exact path, ranges and expected/replacement text. Bash supplies reads, line-number display and file/directory creation; no dedicated Read or Write tool is added. Display line numbers are not part of expected text.

After authorization and ordinary Attempt admission, the native Edit module opens the existing target without create or truncate. It validates target eligibility and every selected slice, using original coordinates, while streaming the complete edited output into one charged immediately unlinked scratch file. A late mismatch, missing target, read failure or scratch failure before this completes leaves the target untouched. It does not require whole-file equality with a preapproval snapshot. Caller-coordinated concurrent filesystem changes remain the caller's responsibility; no locking or isolation promise is added.

Only after all checks and complete output construction succeed does Edit copy that output back through the same opened target handle, set its final length and flush. Do not truncate before copying or rename-replace the inode. Empty output makes final truncation the first mutation. Write, truncate or flush failure may leave partial changes; preserve the actual failure or uncertainty rather than claiming rollback. Before mutation cancellation may stop without applying changes. After mutation starts retain resources for safe execution, observation and cleanup. Scratch is disposable preparation, never recovery authority or permission to replay after crash.

The Host owns admission, authorization, immutable proposal content, semantic outcomes and recovery. Edit owns file checks, streamed transformation and mutation mechanics and returns typed evidence; it cannot open SQLite, read credentials or choose retry policy. Supply scoped inputs and owned buffers/scratch/cancellation facilities, not the whole Host. This remains a trusted in-process module with bounded service turns, no dedicated worker, thread stack, service or independent crash isolation. No transaction spans file I/O.

Use a reusable 16 KiB copying window and bounded range/content traversal. Expected and replacement text can remain disk-backed; no 16,384-byte search-text quota, search overlap buffer, source snapshot, per-line object collection or whole-file resident string is required. Derive actual materialized input, output scratch, target descriptor and transient overlap costs from the implementation. Charge all scratch bytes and pending growth, releasing them only after the last safe use. There is no separately enforced file-count quota or new buffer pool.

Edit has no separate execution or reconciliation timeout. No timer grants unbounded synchronous work on the control path or a fixed wall-clock completion promise for filesystem I/O. Lost custody produces an indeterminate Tool Result without required target inspection or automatic replay, as for Bash. The Agent may inspect current state and propose new work under ordinary permissions.

Older Git/search matcher and three-scratch-role prototypes describe superseded designs and cannot certify this implementation. The shared 1,000 execution default and 256 MiB qualification target remain; integrated accounting and measurements must establish compliance. No four-Edit cap or independent Edit lane is selected.
