# Bound V1 configuration and trust established mechanisms

OnePage treats public configurability as an architectural cost. A setting earns a V1 public knob only when users repeatedly need to make that decision, the setting has one clear owner and scope, and OnePage can persist and display the resolved value. V1 has built-in defaults, one optional user file at `$XDG_CONFIG_HOME/onepage/config.toml` or `~/.config/onepage/config.toml`, explicit CLI overrides, and explicit Job arguments. More specific explicit input wins within the setting it owns. Environment-variable configuration, project configuration, profiles, arbitrary provider options, and equivalent configuration paths are excluded.

The user file contains only `active_capacity` and `model_retries`. The CLI may override those two values for one invocation. `model_retries` defaults to three, accepts zero to disable automatic retries, and is capped at ten. The default Active Capacity is the largest value up to 100 that the required release benchmark proves on the minimum supported Mac; a requested capacity that the Host cannot support fails explicitly rather than being silently reduced. Provider policy supplies the default model and reasoning effort, while a Job may explicitly bind `model` and `reasoning_effort`. Retry classification, delays and jitter, HTTP connection-pool sizing, SSE buffering, provider endpoints, response bounds, service tier, originator metadata, and transport choice remain internal policy until evidence establishes a recurring user decision.

OnePage does not add `config get`, `config set`, or `config edit` commands in V1. Unknown, misplaced, or invalid keys fail with an actionable diagnostic. Run and Job inspection report every resolved execution-affecting value and whether it came from a built-in default, user configuration, CLI override, or Job argument. A Run or Job snapshots those resolved values before execution; later configuration changes cannot alter existing durable work, and an idempotent key presented with different resolved bindings conflicts.

`active_capacity` bounds concurrent active agent work through the existing Active Credit invariant: a credit may belong to a live Harness, an admitted external Attempt, or a closure handoff. Dormant Sessions, workflow dependencies, retry timers, permission waits, conversational-input waits, and other work with no admitted Attempt retain no credit. Live model streams therefore cannot exceed Active Capacity. Provider transport, effect execution, and semantic admission may use fixed private resource-class permits when their costs differ, but V1 does not expose a scheduler or separate tuning surface for them. Tool requests remain asynchronous and release the Harness and Activation Slot while admitted execution owns the transferred credit; private process, file, and descriptor admission prevents unbounded Host resource use.

V1 trusts SQLite, the local filesystem, the operating system, QuickJS-ng, pinned dependencies, and OnePage's own committed internal data to satisfy their documented contracts. OnePage validates untyped or external data when it first crosses a boundary from the CLI, workflow evaluator, provider, or tool, converts it into a canonical typed representation, and trusts that representation internally. Size, count, depth, and concurrency limits preserve deterministic resource use; they do not imply that the user's machine or workflow is an adversarial security boundary.

Every durable semantic fact has one canonical representation. Indexes, inspection snapshots, and rendered views are derived structures rather than competing authorities. OnePage does not add duplicate fields, codecs, checksums, or defensive copies solely to anticipate hypothetical corruption or a future consumer. Digests and validation remain when they serve a current identity, exact-effect binding, reconciliation, or resource-safety requirement. A newly observed failure mode or concrete second consumer may justify expanding this surface through a replacement decision and corresponding verification evidence.
