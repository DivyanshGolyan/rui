# Use SQLite as the sole durable content store

OnePage stores every recoverable OnePage-owned durable byte in the Host Store's one SQLite database. Immutable content is Session-scoped by `(session_id, content_ref)` and stores exact length, a typed digest, and payload. V1 adds no cross-Session deduplication, semantic-kind column, compression layer, second connection, background writer, or custom VFS.

The Storage Owner imports content with `zeroblob` and fixed-window incremental blob writes inside the same short transaction that creates its first durable Session-ledger, Conversation, or Completion reference. A prepared semantic commit identifies whether each import is directly referenced by a fact or indirectly referenced by a typed Patch Intent that the same transaction directly imports. The Storage Owner rejects every import outside that closed relationship. File-backed sources are pointer-stable borrowed capabilities for the duration of the synchronous commit. The SQLite row-length limit equals the 1 MiB content limit plus 4 KiB of bounded schema and record overhead, so an exact-maximum payload remains representable without raising OnePage's content limit. The transaction either publishes both content and reference or neither. Ordinary reads use fixed windows and trust SQLite plus committed metadata; OnePage does not rehash a complete payload merely to distrust the local machine or database it already treats as authoritative.

External work never holds a SQLite transaction open. Each live Harness owns one opaque, pointer-stable scratch allocation and supplies only a borrowed capability to its Session; allocation succeeds before the Session can bind or claim an epoch, and close releases Session scratch before freeing the allocation. That borrowed Session may use one unlinked transient file and one open writer. Its fixed pending table is derived from V1's largest same-transaction first-import closure: three values for patch bytes, canonical Patch Intent, and Tool Call content. Existing durable references do not consume this bound. Aggregate disk-backed scratch is therefore capped at 3 MiB and the ordinary single-value path at the 1 MiB content bound. No complete payload is retained in resident metadata. After all pending values commit, the file is truncated and reused; append, rollback, or reset failure fails that live Session closed, and close or process exit releases the file. Scratch has no durable identity and cannot be discovered after restart. The Host-level lifetime lock and ownership epochs replace the former per-Session lock files. Removing the custom durable blob tree also removes pre-publication orphan discovery, durable-draft sweeping, cross-store publication ordering, and backup closure as V1 responsibilities.

The private integer content row ID exists only because SQLite's incremental blob API opens a row by rowid. The durable content identity exposed to OnePage remains the Session-scoped `(session_id, content_ref)` key; the surrogate is neither semantic identity nor a public reference.
