# Accepted runtime decisions — September 2026

This index records the accepted architecture direction and amendments published together after the architecture discussion. The normative owners define behavior; the linked design records explain decisions and examples. Research, protocol models and measurements establish only their stated evidence. This publication does not claim implementation or final readiness.

| Decision | Normative owners and rationale |
| --- | --- |
| OnePage's own consumers drive the interfaces; native embedding and Durable Objects are design probes. Linux/macOS support uses explicit capabilities, with runtime evidence on the available Mac and separately labelled source/API/cross-compilation evidence elsewhere. | [Platform and consumers](../../ARCHITECTURE.md#consumer-driven-interface-design), [platform rationale](platform-contract-review.md); #118, #126 |
| The Session core uses cohesive transactional operations and retains the published Operation-owned execution/final-result model. Content validation precedes the transaction; saved-state checks and semantic writes belong inside it; dispatch follows commit. Sequential validation is the baseline. | [Execution](../architecture/execution.md), [transactional operations](transactional-operations.md), [ADR-0026](../adr/0026-let-operations-own-current-execution-and-final-results.md); #106, #119, #120 |
| Execution tracking is allocated at startup; oldest eligible work fills available capacity. Neutral records do nothing, and the loop waits on OS events/deadlines when no work can progress. | [Resources](../architecture/resources.md), [tracking rationale](fixed-execution-tracking.md); #68, #89, #121 |
| Bash and Edit never automatically replay uncertain admitted effects. Edit accepts exact whole-line replacements in one existing file, saves the proposal without a mandatory target read, checks every range after approval, then copies checked scratch output through the opened target handle. | [Execution and Edit](../architecture/execution.md), [range contract](fixed-location-edit-approval.md), [writing mechanism](edit-file-writing-proposal.md), [uncertainty](unified-tool-recovery.md); #120–122 |
| Core configuration and message requests save their first committed acceptance or rejection under a caller key. Workflow Runtime saves its own intents and answers in independent transactions and recovers lost replies through the same core API. | [Shared request authority](../../ARCHITECTURE.md#shared-request-identity-and-independent-workflows), [protocol rationale](shared-request-identity.md); #101, #118, #123 |
| One public Workflow Runtime contains a private disposable evaluator with fixed recorded inputs. JavaScript owns branches and joins. The accepted pull/eligibility policy remains; progress observations may briefly lag. Cancellation resolves unanswered submissions before ordinary Session stops, with the accepted possibility of newly admitted work and repeated stops. | [Workflows](../architecture/workflows.md), [boundary](evaluator-coordinator-boundary.md), [two-Session trace](two-session-workflow-trace.md); #114, #123 |
| Caller-side references do no core work. First complete configuration establishes the Session; later configurations apply normally in admission order. Configuration acknowledges commit, while message completion returns the original bound outcome. Run inspection exposes exact Session keys for agent-authored reuse in later workflows against current state. | [Configuration](../../ARCHITECTURE.md#sparse-context-and-exact-model-requests), [initialization](session-initialization-proposal.md), [core API](session-core-api-contract.md); #101, #123 |
| Every explicit admitted instruction update is preserved, including intermediate values, reversals and equal-value fresh submissions. Retrying the same request creates no duplicate. | [Instruction history](instruction-update-history.md), [request construction](../../ARCHITECTURE.md#sparse-context-and-exact-model-requests); #101 |

[#124](https://github.com/DivyanshGolyan/onepage/issues/124) owns final integrated readiness.

The provider-validation, Edit-transformation and Session-calculation boundary reviews remain proposed implementation guidance. They are not additional accepted public interfaces. Earlier separate Session creation, keyless direct mutation, integrated core/Run admission, instruction coalescing and automatic Edit reconciliation are superseded where historical records still describe them.
