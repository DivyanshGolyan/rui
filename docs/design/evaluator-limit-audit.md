6 September 2026. Design input for [Choose Workflow Evaluator containment limits](https://github.com/DivyanshGolyan/onepage/issues/90), coordinated with [Host accounting](https://github.com/DivyanshGolyan/onepage/issues/68). None are permission to delete source safety checks without the required representation changes.

**Decision complete, 7 September 2026.** The user accepted the final package below. All earlier pending/recommendation language records the discussion before acceptance; current authority is ARCHITECTURE.md Disposable evaluator construction, PRODUCT.md, ADR-0014 and VERIFICATION.md. Internal capacities remain implementation-derived. Production and integrated qualification remain outstanding; this closes the design question only.

## Current plan after the architecture clarification

7 September 2026. The user agreed to retain the core design and derive individual buffer capacities during implementation, judging the result by complete behavior, recovery, measured memory and straightforward code. This supersedes treating each internal workspace number as a separate product-approval question. It does not retroactively approve every historical guard or prove the full implementation fits.

- **Accepted architecture:** one Host with SQLite authority; disposable evaluator computations; no retained JS continuation while waiting. The evaluator contains both QuickJS and native support code.
- **Accepted policy:** initial 16 MiB engine heap; bounded native allocations with phase-local reuse; streamed Workflow Output without an independent total-result-size cap, within actual memory/time/shared scratch resources.
- **Implementation choices:** frame/encoding windows, native arena layout/capacity, metadata representations, structural stack guards and derived OS backstops. The tested 2 MiB arena is a starting engineering candidate, not a separate worker, user knob or whole-native memory guarantee. Remove obsolete representations with their replacement, not guards in isolation. Caller-visible shape restrictions still require justification.
- **Accepted behavior policy:** start with one live evaluator; 1 second of process CPU for each evaluation; a 5-second parent-owned elapsed lifetime deadline from successful spawn through protocol completion/exit. The user subsequently accepted this package on 7 September 2026. Waiting in SQLite and model/tool execution consume neither deadline. Cooperative checks cover native processing and JS jobs; the kernel CPU backstop derives from the selected CPU policy and OS granularity. Cleanup follows actual pipe closure and child reap, not the instant a deadline fires; OS descheduling means timeout enforcement is not a hard real-time promise.
- **Tradeoff:** one evaluator keeps the population simple but the prototype's 1,000 tiny evaluations took 11.409 seconds, and a runaway delayed the next by about 1 second. Existing external operations still run concurrently. Ordinary synthetic evaluation medians were about 10–20 ms; that supports the CPU candidate but is not full replay or whole-Host latency qualification. The accepted 5-second outer deadline is a generous elapsed backstop, not a measured workload requirement or tested final parent implementation.
- **Integration evidence still required:** large-report replay/serialization/import under selected resources, supported standard JS API coverage (including the observed JSON gap), accurate failure classification, non-cooperative timeout/cleanup, responsive controls, and combined Host memory at the selected execution population. An address-space backstop needs platform-specific purpose evidence; RLIMIT_AS is not physical-memory enforcement. Eligibility and wake-ups stay in their deferred decision.

There is no new allocator framework, runtime service, persistent evaluation queue or buffer pool. The issue remains open for behavior policy and containment conclusions. This section summarizes the current plan; owning normative documents hold accepted requirements and the dated experiments below remain evidence.

## Recommended direction

Protect resources at their owners: QuickJS allocations, native evaluator allocations, stack/recursive traversal, elapsed/CPU work, and Host transfer/scratch. Avoid independent source/argument/result/fan-out counters when they merely stand in for those same allocations. No unified custom allocator, configurable limit per field or new accounting framework is recommended.

The evaluator's memory limit is not currently a whole-process limit: its native frame buffers, bridge arena and parent buffers live outside the QuickJS allocator. Removing byte/count guards without first changing those representations would remove real safety checks. The following consolidations describe the desired design, not a patch that deletes checks in isolation.

## Accepted first decision — Workflow Output size

Remove the independent **total workflow-result size cap** from the intended product contract, once the output path streams through bounded windows into the shared scratch allowance. Keep memory containment for the actual JS value and temporary conversions, and time bounds for walking/encoding it. If memory, time or scratch is exhausted, return explicit failure; never truncate or publish a partial successful result.

The user accepted this narrow first choice; the later native-workspace decision is recorded below and remaining recommendations stay pending. It requires replacing both full output-frame copies, preserving strict-data validation and late-failure atomicity, and separating descriptor preparation from `workflow_output_bytes`. It does not promise every arbitrarily large JS result can complete.

## Correction to prior experiment interpretation

Both `encodeData` returning ExcessiveBytes and the later `builder.index > workflow_output_bytes + 7` check map to `WorkflowOutputBytes`. The 700,000-byte string fixture exceeds the 512 KiB output builder during encoding, **before** reaching the later 64 KiB result check. Therefore its error proves rejection by the current output path, not isolation of the 64 KiB check. The existing 70,000-byte unit fixture fits the output builder and exercises the smaller result ceiling. The earlier report attribution to the 64 KiB cap alone was too specific; timing/memory/outcome measurements remain valid.

Evidence: `src/workflow_evaluator.zig` evaluateParsed, encodeData/encodeStringPayload, Evaluation.parse, decodeData/deepFreeze, pending-job loop; `src/workflow_protocol.zig` Limits/Builder/Cursor/EntryBudget; `src/workflow_evaluator_main.zig` mappings/process limits; `src/workflow_evaluator_parent.zig` capture/deadlines. All are historical source shapes, not completed new Host integration.

No production code or numeric contract changed in this audit. Existing source and tests were inspected; no new benchmark ran. Accepted changes should be published in owning architecture/language/verification documents after the user's decision.

## Native workspace evidence

[Measured arena usage](evaluator-memory-accounting.md#native-workspace-measurement) demonstrates a simple phase-local 64 KiB reuse opportunity. The 2 MiB capacity is not always consumed; tiny-case claimed arena space falls from about 148 to 84 KiB while larger retained request sets still approach the capacity. This qualifies a specific allocation cleanup, not removal of native-memory protection or selection of a new numeric budget. No production edits are made by the evidence note.

## Accepted second decision — bounded native temporary memory

The user accepted reusing temporary storage after its last use and retaining explicit bounds on native evaluator allocations outside QuickJS. Use the measured parsing-key/descriptor buffer reuse where the non-overlapping lifetimes are preserved. No extra worker, pool or custom combined allocator is introduced. The final native capacity remains undecided; 2 MiB is historical capacity, and the measured 64 KiB reduction is arena usage rather than certified physical-RAM savings. This is an accepted design direction, published in ARCHITECTURE.md, ADR-0014 and VERIFICATION.md, not a main-production implementation change.

## Retained request-copy audit and native capacity recommendation

Current source review: `agentCall` encodes each request into the reusable descriptor window, compares repeated keys against retained canonical bytes, and duplicates each new request into the native arena. `Request.key` points into that retained descriptor. The copy remains necessary even for a request with a visible result because a later call in the same evaluation can reuse its key with a conflicting binding. Pending descriptors additionally feed `writeBlocked` after JavaScript evaluation. Deleting the copy or freeing it on result visibility would remove a correctness consumer or leave invalid references. This is current historical protocol behavior, not the completed keyed Session implementation.

The representation can change, but simply retaining a reference to the caller's mutable JS object is not an immutable request binding. Moving bytes to scratch requires bounded access/comparison and publication ownership across the evaluator's current three-pipe boundary; that is not merely freeing unused memory. A hash-only substitute must not silently replace the current exact byte comparison. Coordinate any replacement with the already-selected streaming work rather than introduce a separate disk lookup or allocator mechanism solely for these copies. Preserve same-key conflict detection, immutable admitted request meaning and complete pending-request delivery.

Recommendation for user decision: **2 MiB as the initial native arena/workspace ceiling**, retaining the demonstrated buffer reuse. The existing measurement shows approximately 84 KiB for tiny work, 1.24 MiB for 200 requests with 6,000-character inputs, and just under 2 MiB for 245 requests with 8,000-character inputs. This is a measured starting candidate with explicit exhaustion, not a derivation of all V1 input shapes. The existing fixed tables, full-frame representations and historical protocol remain qualification gaps. Native input/output frames, stack, engine heap and parent allocations are outside this arena and require their existing bounded owners and whole-process accounting. Do not call it a 2 MiB total native/process bound or multiply it by all dormant workflows.

The final V1 streaming representation may reduce retained copies or change metadata demand; it must qualify or explicitly revisit this candidate before release, without preserving obsolete copies or adding product payload/fan-out quotas to make the number fit. No production edit or new benchmark ran for this source audit. The numeric recommendation is pending user acceptance; the earlier 16 MiB engine limit is already accepted.

## Final remaining recommendations and evidence — 7 September 2026

Local prototype `codex/evaluator-limit-cleanup-probe`, commit `a461cdd`, report `/tmp/onepage-evaluator-limit-cleanup/research/evaluator-limit-cleanup/README.md`, supplies the remaining targeted evidence. All 16 step-loop fixture/variant outcomes pass: the candidate replaces the 4,096-job cap with the existing CPU/wall check before each pending job. A finite 10,000-await workflow completes; an endless await loop fails with CpuTime. Ordinary results, replay keys, heap failure and CPU-loop outcomes remain correct. This does not prove all native phase checkpoints or final parent timeout integration.

The supported Mac build currently **does not apply** the 64 MiB address-space setting: Zig's Darwin AS is a declaration alias of the RSS enum field, so `@hasField(..., "AS")` is false. A direct C attempt to set 64 MiB returns EINVAL (22) on macOS 15.7.7. The probe exits before any optional large allocation. Apple's [kernel setter](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L1560) rejects requested limits below existing mapped-address use; that upstream revision is explanatory, not asserted to be the installed kernel. Do not repair the conditional alone or describe the existing constant as enforced physical-memory protection.

Final decision package, accepted by the user on 7 September 2026:

1. Remove independent source/argument/visible-result byte, total-entry and request-count policies where they merely mirror resident copies/fixed tables. Replace those representations with bounded actual engine/native allocation and streaming transfer, retaining checks until replacements are ready. Compilation still needs contiguous storage; work must fit actual memory/time/scratch, with exact replay and no partial publication. No promise of unlimited data follows.
2. Replace the independent microtask-count policy with CPU/lifetime checks in job draining, extending checks through native work. Preserve strict data, duplicate keys, request identity, wire representability, checked arithmetic, structural recursion/stack guards and bounded diagnostics.
3. Retire the fixed 64 MiB address-space policy on the supported Mac target. Explicit allocation ownership, one-evaluator population, CPU/elapsed protection and measured whole-Host footprint remain. Do not add a separate RSS monitor or platform memory service. Future target support requires its own purpose/evidence for an OS address-space guard.
