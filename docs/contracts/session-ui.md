## Accepted contract

### Human entry and authentication

On a terminal, bare `rui` (optionally `--store`, `--provider`, `--model`) opens the **Session overview** of unarchived Sessions in the Store; on wide launch a chat opens beside it with input focused. Each row shows its primary name, state mark and compact time in that state.
The overview is Rui's primary terminal surface: a client view over Session listing and host information, not a Host entity, registry or report.
Listing alone neither creates nor resumes a Session.
It captures canonical cwd before starting/attaching the selected Host (default Active Capacity 100), and resolves only a locally usable supported provider for prospective Sessions. An unavailable or ambiguous choice opens a centered app sign-in dialog without creating a Session or Message.
The same dialog opens from app settings Sign-in above the retained screen. Root consumes its keyboard, paste and mouse input; clicks outside it do not activate the covered screen. First run stays gated until a usable binding exists; Settings returns to Settings.
Keyboard activation and editing require the last drawn control to remain the live focused control on the same page and attempt. A focus move awaiting repaint cannot activate or edit the previous control. Mouse actions retain their exact drawn hit target.
The account explanation is a plain wrapped subtitle above the ChatGPT and API-key choices. Contextual Back, Close and primary actions occupy a separate Panel button area, with stacked actions when a row would clip. Tab keeps the existing semantic control order; keyboard and mouse use only visible drawn targets. A quiet wrapped footer explains navigation without becoming a selectable field. Panel measures the subtitle and exposes its actual visible field rows, so clipped read-only facts cannot authorize copy.
The tagged pages guide account choice (ChatGPT or API key), then explicit browser/device method choice. The ChatGPT method page also offers usable saved browser or device credentials without reinstalling them. Both authentication methods reuse the plain CLI login owners on one joined worker.
Browser sign-in shows the visible linked URL, an explicit reopen control, and a masked callback field. Paste alone does not confirm a callback. Change method and Back cancel through the publication gate, wait for worker settlement, then return to the chooser. Expiry and failure retain retry and method recovery. Publication that wins cancellation still settles truthfully.
The device page wraps its complete readable URL across bounded value rows, retaining the full browser destination on every segment. It shows a separate read-only code and explicit Copy code and Open browser buttons. Copy takes the exact code in the last drawn frame and only when fully visible, including clipped/tiny layouts. Drawing and pasted hotkeys never copy. Clipboard feedback says the request was sent, not that the terminal accepted it.
The API form has independently focusable editable base URL, masked key and model fields, each with one DraftEditor length/caret owner. Paste recipient custody cannot cross fields or become an action. Refused drafts block Connect until acknowledged in their field. Mapped key storage is wiped in full after worker join or abandonment; frozen form slices cannot change while borrowed by the worker.
Base URLs reuse endpoint_value's HTTPS Responses API admission. An existing endpoint without a reversible `/responses` suffix stays byte-for-byte unchanged unless edited. Custom services require an explicit syntactically valid model ID; catalog availability or remote key acceptance is not promised. API provider/model binding applies only to prospective Sessions in this terminal, not existing Sessions or global custom-model defaults.
API save reuses host_start and the private-document owner: validate the complete sparse document before the publication gate, create a fresh immutable owner-only selected-Host key file, then publish endpoint plus file source in one lock-held update. Preserve unrelated settings/providers; materialize automatic routes through their existing owner. Blank usable key input freezes the form's admitted endpoint, normalized key source and authenticated mode. Under the same saved-document lock, save must match those descriptions before it resolves any chosen key or publishes another immutable scoped pair. A changed endpoint, source or auth mode refuses the attempt, even when the new key would be locally usable. The existing startup source owner derives omitted/default endpoints, environment base URLs and default-file equivalence. This protects settings pairing, not external mutation of a user-owned key file's contents at an unchanged authorized source. After the worker joins, supersession releases the stale form and Retry reloads current settings. No global key is replaced. Old immutable files and their locks remain for lockless startup readers; each attempt retains at most one max-key-size file plus its lock, with no eager garbage collection.
The private owner distinguishes definite nonpublication from post-rename uncertainty. Prepublication cleanup keeps the original error and any cleanup error plus retained file identity. Uncertain publication retains the key and offers conditional durability recheck; recheck never overwrites a superseding pair. A matching pair's pre-rename failure or post-rename uncertainty retains its original cause and retry authority; only an actual source mismatch is supersession. Plain CLI auth and global credential behavior remain unchanged.
An already-chosen, locally usable binding reaches the existing starter without inspecting startup-only source documents, so ready attachment does not depend on their current readability and absent-Host refusals retain the starter's structured diagnostics. Browser/device bindings keep their selected or recommended models. An already-chosen API binding without an explicit invocation model returns to guided sign-in, even for a standard service: Host facts name routes, not endpoints, so Rui cannot safely guess a custom service's model. The existing API form setup retains any original source-inspection failure. Chooser and locally unavailable scoped-API readiness still resolve effective file/environment/default sources through the startup owner; a custom service requires an explicit invocation model.
Connected requires the existing starter's fresh-launch evidence: frozen endpoint/private-file/authenticated assignments, current-profile same-socket peer PID, matching native start generation and executable, and the chosen served route. The two startup channels and exact child launch identity stay with the shared launch owner; no wire field, Store schema or fingerprint is added. Adopted, racing or unverifiable Hosts remain Saved, not active. That page offers shell-quoted selected-Store pause/start command copies, warns that pause interrupts all Sessions, and permits recheck without implicitly restarting work.
Credential publication, independent OAuth default saving, and complete Host activation settle through one joined outcome on completion or departure.
The screen borrows only its semantic projection; departure after screen restoration retains startup output, refusal/OS context and warnings and reports once.
Before another attempt changes page or frozen authority, the current whole outcome must transfer through a non-consuming renderer into a private unlinked file from the existing scratch factory.
SignIn caps the entire deferred committed/dirty prefix at sixteen maximum receipts.
Each receipt permits the larger of the shared launch report plus a 512-byte sign-in margin or a fully shell-escaped native cleanup path plus 1024 bytes of recovery guidance.
This permits repeated retries without an unbounded history or resident transcript list.
A complete positional append alone advances its committed end; failed append leaves the whole current outcome and overwrites the same tail on retry.
Capacity/create/write refusal keeps the old attempt and asks the user to exit/reopen.
Close and Settings reset retain this reporting custody.
API form inspection/mapping and worker setup failures retain their original causes through this same outcome and reporting boundary. A form failure cannot overwrite an earlier receipt, and Retry retries the form setup rather than activating a guessed binding.
Final departure streams only the committed prefix, then renders the last outcome in bounded memory without requiring more disk space.
The existing required stderr owner exposes acknowledged output progress; output failure is explicit, never inferred as zero-byte delivery or blindly replayed.
The first retained operation error determines exit status even after later success; an I/O failure is distinct and takes precedence until reporting can complete.
A refused replacement is not a failed login operation. Its archival cause is reported, but does not fail an otherwise successful operation once final departure acknowledges every report byte. An unresolved read/output failure still refuses successful departure.
Native departure uses `sign_in_connection_changed` for source supersession, `sign_in_connection_pending` for a saved connection not proven active, and `sign_in_report_unavailable` for required receipt I/O failure. Each asks for operational repair and exits6. Low-level storage/output causes remain with SignIn's receipt custody and exact cursors. They never change an already serialized prefix on retry. Context-free OS errors and internal admission/format invariants keep their existing internal classification.
Teardown closes the single descriptor, without claiming crash durability for unlinked scratch.
The existing launch owner still suppresses the expected `store_locked` loser transcript when it adopts another ready Host.
SignIn preserves every diagnostic retained by that whole Result, rather than treating that expected race as a launch failure.
Scoped API receipts cannot authorize a later ChatGPT flow.
Successful warnings remain an overview notice independently of default-save failure.
A running Host that does not serve the chosen provider is reported, not restarted.
When all three selectors are explicit, unreadable future defaults cannot block the overview, even after login fails to save them; otherwise the post-login choice rereads future defaults.
A ready existing Host retains its actual capacity/capabilities; no model capability prevents opening the overview without restarting it.
When its Host goes away the overview stays open and says so on one Host line, `■ Host stopped · start`; a click on its start control starts it through the same launch owner. Printable `r` on the overview is ignored.
A Host that ended without being asked to stop (a crash or SIGKILL) is started once by itself, the line reading `Host starting` meanwhile; a Host stopped by `host-stop` (pause, stop or an Upgrade's swap), by its launcher closing stdin, or by SIGINT, SIGTERM or SIGHUP (Ctrl-C on a foreground `host serve`, closing its terminal, or `kill`) is not, nor while an Upgrade holds the Host.
The stopping Host leaves a stop record beside its Store lease, which every Host start removes; an unreadable record counts as a stop someone asked for.
At most one automatic start runs per overview: a failed start or a second crash leaves the line’s start control available, with no retry or backoff.

### Desktop notifications

Divyansh decided on 2026-11-10 that Rui tells the terminal about its Sessions only through Mitchell Hashimoto's program status protocol, OSC 7501 (https://www.superlogical.com/rex/docs/build/program-status): Rui writes no OSC 9, OSC 777 or bell, inside tmux or screen too, and the terminal chooses how to show each record and how often to tell the person.
Records go out whether or not the terminal answered vaxis's program status query; a terminal that does not take them ignores them.
Rui writes one record per Session, `id=rui/REFERENCE` with `app=rui` and the Session's row title in base64 as `msg`: `working` for pending, working, retrying, stopping and Bash work; `blocked` with `kind=permission` while an Action awaits a decision; `done` for a finish the person has not opened; `error` for a failure; `idle` after a stop, or once the person opens a Session whose outcome the record shows.
Each record changes when the Session's state does, whether or not the terminal has focus.
The records come from listings alone, which read in order, so a slower read never sets a record back; the overview's listing jobs keep running while a conversation is open.
`State.seen` keeps, per Session, the record Rui wants on the terminal (a status and a version that names it) and what the terminal holds of it (no record, the version of a report a frame wrote whole, or unknown after a clear that may have landed); each time the overview steps, `Overview.sendStatuses` reports exactly the Sessions where the two differ.
A record follows each change a listing reads, and a later finish, failure or wait in the same state is a change: a listing compares what it reads with what the listing before it read, ordered by Turn, then within a Turn by the earliest Action awaiting a decision (`first_action`), with the Turn's finish or failure after every wait in it.
An outcome the conversation's first read shows as the person opens the Session is one they have seen, even when no listing had read it yet: the conversation hands that read to the overview through its lender, `State.seen` keeps the latest such state, a listing that reads that outcome or an earlier one gives `idle`, and only a later Turn's finish or failure is `done` or `error` again.
The listing the overview opens on gives a record only to work under way or waiting, so an outcome from before Rui opened never gets one, and a Session at rest gets none until it does something; a Session a full listing no longer shows has its record cleared.
A new title, from a Label or a first line read later, is a new version, so the record is written again with that name.
`Attention.report` writes each record and flushes it, and only then does the overview count it as held.
Each step rereads the preference, so `/setup --notifications off` applies at once; unreadable preferences leave the default, on.
With notifications off Rui wants no record: while any record of Rui's may be on the terminal it writes one clear (`state=clear:id=rui`, which clears Rui's records and no other program's), and from the frame that carries it until one writes it whole, what the terminal holds of each record is unknown; on again, it writes every record again.
Leaving clears Rui's records too whenever one may be on the terminal, though the spec lets `done` and `error` outlive the program: a record of a Session no Rui watches would not change again.
