# Linux and macOS portability evidence for OnePage

Research date: 2026-09-08. Decision consumer: [Audit macOS assumptions and establish Linux portability options](https://github.com/DivyanshGolyan/onepage/issues/125). Human choices belong to [Choose Linux and macOS platform contracts and portability seams](https://github.com/DivyanshGolyan/onepage/issues/126).

**Both operating systems are required for redesigned V1.** This note identifies mechanisms and qualification gaps; it does not select distributions, minimum versions, CPUs, credential backends, deployment modes, or weaker guarantees. External embedding is a first-class use case to evaluate. Nothing here establishes implemented Linux support.

## Credential options require a lifecycle decision

The existing [authentication Store interface](https://github.com/DivyanshGolyan/onepage/blob/d76c7350a3661da48e9d107258e3dd699f9b0aa7/src/codex_auth.zig#L46-L63) already separates load/save/delete from protocol work. That is evidence of a useful boundary, not a requirement to retain its exact signatures or synchronous behavior.

[Secret Service](https://specifications.freedesktop.org/secret-service/latest-single/) runs in the user's login session over D-Bus. Collections can be locked; create/read/delete flows can require prompts. Lookup attributes are not secret storage. Consequently, choosing the API alone neither establishes an available unattended backend nor proves the encryption/unlock policy of the selected implementation. Keep token/account bundles in protected secret values rather than assuming lookup metadata is confidential.

For a provisioned headless environment, [systemd credentials](https://github.com/systemd/systemd/blob/a7fc55f8654bef6a01c72ae7a6efa3357d1f344b/docs/CREDENTIALS.md#L8-L91) offer authenticated encryption and service-scoped delivery, but credentials are immutable during a service activation. This is a possible bootstrap/input mechanism, **not a complete rotating OAuth store**: refresh persistence, revocation and restart loading still need an owner. It also makes systemd availability/provisioning a deployment condition, which the user has not selected.

An embedding application could supply secure load/save/delete capabilities and own unlock/provisioning. That is another candidate requiring an explicit contract for refresh durability, account binding, concurrent access, failure and lifetime. It must not quietly substitute token environment variables, plaintext files, or a desktop daemon assumption. The research has not selected a backend or weakened the no-credential-leakage promise.

## Two portability traps worth deciding explicitly

**Disabling core files is not the same as disabling core collection on Linux.** The current evaluator sets `RLIMIT_CORE=0`, but Linux [core documentation](https://man7.org/linux/man-pages/man5/core.5.html) says piped core handlers ignore that limit. [PR_SET_DUMPABLE](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html) is a candidate Linux mechanism; it also changes ptrace and `/proc` access behavior. Determine where to apply it after process construction and verify both ordinary and piped collection. This is an enforcement adaptation, not evidence for a new sandbox guarantee or permission to alter an embedder's whole process without a contract.

**Memory metrics must retain their names and scope.** Linux `ru_maxrss` is KiB, and `RUSAGE_CHILDREN` reports the largest child's peak rather than simultaneous tree peak. `/proc` RSS/PSS/private fields have distinct sharing/accounting semantics and availability. Mac physical-footprint counters, allocator-live bytes, process RSS, filesystem cache and temporary-file charges must remain distinguishable. Embedded execution also shares a process with unrelated application memory, so attribution and whole-application qualification need explicit treatment. No new RSS killer or guessed conversion factor follows.

## Decisions the evidence leaves open

The platform ticket can now choose a concrete OS/version/CPU/libc/deployment matrix; interactive and headless credential behavior; supported Store/temporary filesystems and native dependency delivery; equivalent process/resource enforcement; and platform-specific qualification definitions. Each Mac dependency above needs a common mechanism, an owned platform implementation, replacement, or explicitly accepted product tradeoff. Platform-specific implementation does not itself justify a general platform framework.

The existing product semantics remain baseline: one authority, exact authorization, effect-specific recovery, bounded owners, retained spillover's scoped lifetime and caller-coordinated optional Session sharing. Historical source limits and platform measurements must not silently narrow them. Supporting both OSes does not require reviving obsolete code or promising every distribution, CPU or filesystem.
