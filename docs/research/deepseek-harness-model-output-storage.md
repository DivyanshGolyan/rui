# DeepSeek Harness model-output storage

**Checked source:** [`deepseek-ai/deepseek-harness` at `76fda729799fe9b3848dbe2c211d4b231032b81e`](https://github.com/deepseek-ai/deepseek-harness/tree/76fda729799fe9b3848dbe2c211d4b231032b81e) (2026-09-03), from a fresh shallow clone.

## Answer

DeepSeek Harness does **not** durably retain a full raw provider response beside a normalized semantic response. Its continuation authority is one provider-neutral, immutable `Message`: the same object shape is used for delivery, durable history, and later model requests. Assistant messages may carry a small, adapter-private `source.replayState` containing only provider metadata that cannot be reconstructed from canonical content, such as response IDs and signatures ([message contract](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/message.ts#L9-L20), [single-representation statement](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/message.ts#L130-L150), [replay envelope](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/types.ts#L335-L354)).

There is one qualification: the append-only session log stores the normalized `StreamChunk`s as well as the assembled assistant message. This duplicates token deltas, reasoning deltas, and tool-argument fragments for timeline/token-level replay, but those chunks are already Harness protocol values, not raw SSE payloads or native provider response objects ([event schema](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/types.ts#L255-L302), [assembly loop](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/agent-loop/src/agent.ts#L361-L427)). On disk, runs of these canonical deltas may be losslessly packed; unknown fields in an already-normalized chunk stay verbatim rather than being compressed ([chunk-row codec](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/chunk-rows.ts#L1-L17), [storage record](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/chunk-rows.ts#L49-L73)).

So the closest characterization is: **one canonical semantic message with provider-only replay extensions, plus a normalized stream journal**. It is not dual storage of provider-native and normalized responses.

## What is retained

| Datum | Durable representation | Used to reconstruct later requests |
| --- | --- | --- |
| Assistant text | `text` blocks in `assistant/message`; also normalized text chunks | Canonical blocks are serialized for the target provider |
| Reasoning | `reasoning` blocks; also normalized reasoning chunks | Direct DeepSeek recreates `reasoning_content` from the canonical text |
| Tool calls | `tool-call` block with ID, name, and argument string; also `tool/call` execution event | Rebuilt from the canonical block; the execution event is not model history |
| Tool results | Canonical user-role `ToolResultMessage` in `tool/result`; optional tool-private JSON `meta` | The canonical result message is translated to the provider's tool-result shape |
| Signatures / native stop reason / successful response ID | Only when an adapter projects them into `replayState` | Recombined with canonical blocks by that adapter |
| Provider response bytes / arbitrary native fields | Not retained | Cannot be reproduced unless an adapter explicitly projects the necessary field |
| Failure request ID | Provider-neutral `LlmFailure.requestId` in the terminal chunk and retry event | Diagnostic/retry data, not successful continuation state |

The direct DeepSeek adapter makes the split concrete. It parses each SSE payload into a transient `WireChunk`, reads only `reasoning_content`, `content`, tool-call deltas, finish reason, and usage, and emits canonical chunks ([translation](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/translate.ts#L103-L205)). Its wire type contains only those recognized fields and no response ID or catch-all metadata ([wire schema](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/types.ts#L118-L160)). The success path streams the HTTP body directly through the SSE parser and translator; it never saves the body or parsed chunks as provider-native records ([adapter success path](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/adapter.ts#L699-L704)).

On later calls, the direct adapter recreates assistant text, reasoning, and tool calls from canonical blocks and reconstructs the entire wire request in memory ([assistant serialization](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/serialize.ts#L202-L235), [message and request reconstruction](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/serialize.ts#L238-L275), [request body](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/serialize.ts#L342-L391)). The serialized JSON request string exists only around `fetch` ([dispatch](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/adapter.ts#L630-L648)).

Tool calls have deliberate semantic duplication for execution traceability: the assistant message contains the canonical call block, while `tool/call` records the exact canonical argument string and `tool/result` stores its model-facing result plus optional opaque tool metadata ([tool event contracts](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/types.ts#L303-L326)). Neither is a copy of provider wire JSON.

## Provider-only replay state

The pi-ai adapter demonstrates the intended escape hatch. It explicitly says canonical Harness content remains authoritative and projects only provider-native metadata. Its current projection includes text/thinking/tool signatures, a reasoning `redacted` flag, native API/provider/model identity, optional `responseModel`, optional `responseId`, and native stop reason ([projection schema](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L1-L31), [projection code](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L64-L103)). It then recombines that metadata with canonical content to recreate the native assistant message ([reconstruction](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L178-L221)).

There is no dedicated encrypted/opaque-continuation field in the checked adapters. The core treats `replayState` as opaque lossless JSON, so an adapter can define a minimal opaque field, but the current pi-ai implementation whitelists only the fields above. Replay metadata is exposed only when the same registered adapter instance owns the historical and target provider; otherwise the runtime strips it ([adapter ownership gate](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/index.ts#L943-L956)). Malformed, foreign-version, or content-mismatched pi-ai replay state degrades that message to provider-neutral history instead of making the request fail ([validation](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L109-L141), [fallback](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L224-L248)).

## Unknown fields and item kinds

DeepSeek Harness does not solve future provider vocabulary by saving every native response field. In the direct adapter, unreferenced fields in the parsed provider object are ignored, and an unknown `finish_reason` becomes a normalized terminal error ([finish mapping](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/translate.ts#L27-L43)). The pi-ai event translator covers the dependency's current closed event union; a new event kind is intended to cause a compile-time exhaustiveness failure rather than be persisted generically ([pi-ai stream translation](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/stream.ts#L141-L231)). Plugin-added canonical content blocks that pi-ai cannot represent are skipped in provider-neutral conversion, except assistant images, which fail explicitly ([foreign conversion](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-pi-ai/src/replay.ts#L143-L175)).

That is separate from forward compatibility of the Harness's own durable log: an unknown session-event type is refused unless its writer marked it `ignorable: true`, because silently dropping a required event could reconstruct the wrong session ([storage validation](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/session/session-persistence/src/storage-contract.ts#L52-L77)).

## Errors, retries, and exact reconstruction

For a non-2xx DeepSeek response, raw response text is held only in the thrown error's in-memory `cause`. The adapter extracts status, retry delay, and request ID into provider-neutral failure facts ([HTTP error path](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-deepseek/src/adapter.ts#L658-L692)); the runtime normalization deliberately detaches only serializable facts and excludes the cause ([failure normalization](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/adapter-failure.ts#L10-L28), [retained failure fields](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm/src/types.ts#L39-L51)). Thus raw error bodies are not durable either.

Retry scheduling and start transitions are durable and contain the normalized failure, delay, and attempt number ([retry event schema](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-retry/src/types.ts#L6-L48), [retry writes](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/llm/llm-retry/src/index.ts#L149-L191)). A failed attempt does not append an assembled assistant message; after approval to retry, the loop derives the same live semantic surface and builds another request ([retry loop](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/agent-loop/src/agent.ts#L348-L407)). Any canonical chunks emitted before failure remain in the journal, but chunks are explicitly excluded from model history ([surface projection](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/surface.ts#L77-L120)). The retry therefore reproduces the semantic request, not stored wire bytes.

Normal request reconstruction folds the live surface into the already-frozen messages stored inside events, then combines those messages with the latest logged request header's provider/model/system/tools/settings ([history derivation](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/session/src/index.ts#L772-L810), [request construction](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/core/agent-loop/src/agent.ts#L498-L543)). A checkpoint policy flushes the complete logged request prefix before dispatch and flushes the preceding response/result batch at the next request boundary ([durability policy](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/session/session-checkpoint-policy/src/index.ts#L20-L37), [boundary semantics](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/session/session-checkpoint-policy/src/index.ts#L52-L81)). `append` itself is best-effort; `flush` is the physical durability barrier ([persistence contract](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/session/session-persistence/src/index.ts#L114-L129)).

## Compaction exception that is not provider dual-storage

Compaction deliberately persists both a safe text-only `summary` and `rawOutput: ContentBlock[]`, then immediately appends the framed summary as the replacement user message ([compaction event contract](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/compaction/compaction/src/types.ts#L24-L67), [commit](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/compaction/compaction-basic/src/region.ts#L436-L475)). Here `rawOutput` means the complete **canonical `ContentBlock[]`** assembled from the summarizer stream before its text-only projection, not a raw provider response ([summarizer](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/compaction/compaction-basic/src/summarizer.ts#L121-L181), [text projection](https://github.com/deepseek-ai/deepseek-harness/blob/76fda729799fe9b3848dbe2c211d4b231032b81e/packages/compaction/compaction-basic/src/summarizer.ts#L216-L224)). The one-shot compaction path keeps `assembler.blocks()` and usage, but does not attach that call's replay state to `rawOutput`; response IDs/signatures from the summarizer call are therefore not captured there.

## Implication

DeepSeek Harness's design supports faithful future requests without storing two whole representations. Canonical content owns all cross-provider semantics; provider-only data is a narrow, versioned extension owned and validated by the adapter. The cost is explicit: a provider-native field or future item kind that was neither normalized nor deliberately projected into replay state is lost and cannot later be reproduced. Its stream journal helps debugging and UI replay, but is not an escape hatch for unknown provider wire data.
