# Codex CLI edit/apply-patch research

Research target: OpenAI Codex source at revision `ac192cd7937b0d73edc6dffe009940ae53782dd4` (the pinned local source snapshot is recorded in `/tmp/onepage-edit-priors/codex-sha`). The local extracted files below are evidence copies; the immutable primary citations are the GitHub links.

## What one call can express

Codex's native edit surface is a single `apply_patch` call whose body contains one or more hunks. The grammar supports `Add File`, `Delete File`, and `Update File`; an update may include an optional `Move to` destination and multiple ordered change chunks. Each chunk has optional one-line context, old lines, new lines, and an end-of-file marker. This is a patch language rather than a JSON schema of `(path, ranges, expected, replacement)` records. [parser.rs, lines 1-22](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/parser.rs#L1-L22), [parser.rs, lines 64-131](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/parser.rs#L64-L131) (local: `/tmp/onepage-edit-priors/codex-codex-rs_apply-patch_src_parser.rs`).

Multiple files are supported in one call. Verification rejects duplicate operations targeting the same resolved path, including a source/destination collision, before producing the action. The action stores a map of resolved paths to changes, so callers receive one prepared change per path. [invocation.rs, lines 214-294](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/invocation.rs#L214-L294) (local source was fetched for this check at `/tmp/invocation.rs`). The map means patch input order should not be treated as a durable ordering contract across distinct files; within one update file, chunks are explicitly expected to be source ordered.

## Matching and sequential semantics

For each update file, verification reads the current text, finds each chunk at or after a moving `line_index`, and builds all replacements before returning a prepared action. Matching attempts exact lines first, then ignores trailing whitespace, then ignores leading and trailing whitespace; this pinned revision also has a final Unicode punctuation/space normalization pass. End-of-file chunks prefer the file tail. After matching, replacements are sorted by source index and applied in reverse order so earlier replacements are not shifted by later ones. [file_update.rs, lines 24-45](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/file_update.rs#L24-L45), [file_update.rs, lines 85-220](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/file_update.rs#L85-L220), [seek_sequence.rs, lines 1-105](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/seek_sequence.rs#L1-L105) (local: `/tmp/onepage-edit-priors/codex-codex-rs_apply-patch_src_file_update.rs`, `/tmp/onepage-edit-priors/codex-codex-rs_apply-patch_src_seek_sequence.rs`).

Tests demonstrate multiple non-adjacent chunks in one file, additions/deletions/replacements, and a single summary entry for that file. [lib.rs, lines 1162-1268](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L1162-L1268) (local: `/tmp/onepage-edit-priors/codex-codex-rs_apply-patch_src_lib.rs`). There is no explicit overlap check in the matching code: it advances the cursor for chunks, then sorts replacement spans and applies them in reverse. Therefore overlapping or otherwise contradictory ranges are not a separately specified safe case; OnePage should reject overlap explicitly if its fixed-range contract needs deterministic behavior. This is an inference from the implementation, not a tested Codex guarantee.

The matcher is deliberately fuzzy, so an `expected` text field copied into a OnePage request would not have Codex's exact-match meaning unless OnePage adds its own exact precondition. Codex's own tests cover trailing/leading whitespace tolerance and Unicode dash normalization. [seek_sequence.rs, lines 105-185](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/seek_sequence.rs#L105-L185), [lib.rs, lines 1306-1358](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L1306-L1358).

## Reads, preparation, permission, and preview

The tool handler parses the patch, resolves the environment, then calls `verify_apply_patch_args_with_mode`. Verification reads delete targets and reads every update target to compute the new contents and a unified diff. Only after this verification does `execute_verified_patch` calculate write permissions, call `prepare_apply_patch`, and hand the prepared action to the orchestrator. [handler, lines 380-420](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/handlers/apply_patch.rs#L380-L420), [handler, lines 547-615](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/handlers/apply_patch.rs#L547-L615), [invocation.rs, lines 200-294](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/invocation.rs#L200-L294). Thus the approval path is preceded by filesystem reads and diff preparation; it is not a no-read approval of an abstract request.

This is a two-read design. The prepared `new_content` and diff are attached to the approval action, but the runtime later passes the raw patch back to `apply_patch_with_options`; that function reads update files again while applying them. A target changed between verification/approval and execution can therefore produce a later match failure or a different result. The source does not compare the commit-time file against the exact bytes used to make the approval preview. [runtime, lines 168-198](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/runtimes/apply_patch.rs#L168-L198), [file_update.rs, lines 24-45](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/file_update.rs#L24-L45).

The prepared action carries the raw patch, resolved cwd, per-path changes, unified diff, and computed new content. The approval action includes the patch and changes, so the UI/event layer can show the proposed change. Streaming argument events also expose parsed changes while the model is still producing the patch, throttled to 500 ms. [lib.rs, lines 160-220](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L160-L220), [handler, lines 88-155](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/handlers/apply_patch.rs#L88-L155), [runtime, lines 75-85](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/runtimes/apply_patch.rs#L75-L85). The source exposes no explicit maximum patch/file size in these paths; strings, hunks, and the streaming line buffer are dynamically accumulated. That is an observed absence, not proof that a higher layer has no limit.

## Commit, partial failure, cancellation, and crash implications

The apply phase reparses the raw patch and iterates hunks. Each add/update writes immediately; deletes remove immediately; moves write the destination before removing the source. There is no transaction, temporary-file swap, rollback, or all-files atomic commit in this implementation. [lib.rs, lines 458-726](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L458-L726). The code explicitly records that a failed write may have truncated or otherwise modified a target before returning, marks the delta `exact = false`, and returns the mutations known to have committed before failure. [lib.rs, lines 489-501](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L489-L501), [lib.rs, lines 310-335](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L310-L335).

The move test intentionally makes source removal fail after destination write and asserts that the destination remains written while the source remains present. [lib.rs, lines 1107-1160](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L1107-L1160). The runtime accumulates committed deltas across attempts and returns them on errors. [runtime, lines 168-237](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/core/src/tools/runtimes/apply_patch.rs#L168-L237). The runtime receives a cancellation token in the handler, but the apply function itself has no cancellation parameter and the cited write loop has no cancellation checks. A cancellation or process crash during writes therefore has the same externally relevant uncertainty as an I/O failure: the filesystem may contain partial changes without a completed result. This last sentence is an inference from the call boundary and write loop.

The boundary between validation failure and runtime failure is useful for OnePage. Verification loops over every hunk and computes every update before returning an action, so a later-file missing path or unmatched context fails before the first write. After approval, however, execution loops over hunks and commits each successful write immediately; a failure in a later file leaves the earlier-file prefix committed. Codex reports that prefix through `AppliedPatchDelta`, with `exact` indicating whether the observed delta can be trusted completely. [invocation.rs, lines 232-294](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/invocation.rs#L232-L294), [lib.rs, lines 504-720](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/apply-patch/src/lib.rs#L504-L720).

## Consequence for the OnePage proposal

Codex supplies evidence that multiple changes can belong to one tool call, and that proposal preparation and physical application have different failure boundaries. Its pre-approval reads are an implementation choice, not evidence that OnePage must read before presenting the model's submitted proposal. For OnePage's proposed one-path fixed-range list, the relevant transferable rule is to validate every range and exact expected slice before the first mutation, with explicit overlap rejection. Approval ordering remains OnePage's decision; this research does not amend it or add a recovery phase. Codex does not establish all-or-nothing filesystem durability.
