# Libghostty interface evidence for the OnePage redesign

Research date: 2026-09-08. Decision consumer: [Establish which libghostty interface principles transfer to OnePage](https://github.com/DivyanshGolyan/onepage/issues/117).

This is research for a **full redesign**, including external embedding as a first-class use case alongside OnePage's CLI and workflows. It does not select an architecture, ABI, binding, distribution model, or product amendment. Existing product promises are the baseline; specific tradeoffs require the user's decision. Concurrent sharing of a Session remains an optional, caller-coordinated composition.

## What philosophy the evidence actually supports

Hashimoto's [September 2025 rationale](https://mitchellh.com/writing/libghostty-is-coming) describes extracting proven functionality for consumers that should not need to recreate terminal correctness, exposing smaller libraries as capabilities mature, and using real consumers to improve the API. It explicitly distinguishes mature core behavior from an immature public interface. That dated roadmap is motivation; current source below establishes what exists at the pinned revision.

For OnePage, the transferable question is: **which coherent capabilities can a CLI, workflow evaluator, and external application each use without reproducing the difficult execution, recovery, and resource rules?** This can justify replacing current module boundaries. It does not require exposing every private subsystem, making every module generic, or minimizing the number of changed files.

## Two different integration surfaces

| Surface | Actual contract and consumer | What this establishes |
| --- | --- | --- |
| Full application integration | [`include/ghostty.h`](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty.h#L1-L11) calls itself internal, tailored to macOS, and unsuitable for general external use. The [Swift app](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/macos/Sources/Ghostty/Ghostty.App.swift#L47-L88) supplies wake, action, and clipboard callbacks. A wake [schedules a main-thread app tick](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/macos/Sources/Ghostty/Ghostty.App.swift#L540-L548). | A real application boundary can be deliberately specialized. Its existence does not prove a generally usable public library interface. |
| Application-runtime composition | [`apprt.zig`](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/apprt.zig#L1-L55) shares core logic and selects the runtime at compile time; library builds select the embedded runtime. | Dependency direction and compile-time composition can separate application integration without a runtime plugin system. This is not a prescribed OnePage thread model. |
| Standalone native capability | [`lib_vt.zig`](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/lib_vt.zig#L1-L154) deliberately curates the exported module rather than exposing all terminal internals. It still exports substantial native types, including Terminal, Screen, PageList, parsers, and input encoders. | A reusable native API need not mimic an opaque C facade or consist of very few functions. Selection follows consumer usefulness. API stability is still explicitly unpromised. |
| Standalone C capability | The [stream example](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/example/c-vt-stream/src/main.c#L6-L68) constructs terminal state, processes bytes, formats output, and frees resources without creating a Ghostty app. [C wrapper ownership](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/terminal/c/terminal.zig#L44-L100) supplies retained I/O machinery and adapts native lifetime requirements. | External consumers can use a complete capability independently. A foreign-language boundary can adapt native mechanics rather than dictate their representation. |

The consumer comparison therefore needs at least two OnePage embedding scenarios: an application asking for complete durable agent execution, and an application asking for a narrower reusable capability. Whether the latter has enough value to deserve public exposure is unresolved. A native provider codec, exact-edit engine, or report reader is a candidate to evaluate, not a selected public module.

## Evidence matrix

The OnePage scenarios and decision implications below are research inferences. They are not claims that Ghostty implements durable agent execution or that OnePage already implements the proposed interfaces.

| Principle | Concrete evidence | OnePage scenario | Limitation | Decision informed |
| --- | --- | --- | --- | --- |
| Package a capability a consumer can complete independently | Standalone [C stream example](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/example/c-vt-stream/src/main.c#L6-L68); native [build/import example](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/example/zig-vt/build.zig#L16-L29). | An external application starts durable Session work, supplies permission decisions, observes results and reopens after a crash without constructing rows or driving private lifecycle phases. | The terminal example is a small synchronous use case. It does not prove the complete OnePage Host must be synchronous or caller-driven. | Which complete capabilities and lifecycle obligations must the embedding interface offer? |
| Separate consumer policy from shared mechanics | [Embedded clipboard interface](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/apprt/embedded.zig#L48-L87) distinguishes observed read facts, deferred completion/denial, and core interpretation. | Keep exact editing or provider grammar usable without granting it authority to admit effects, select retries, or publish canonical outcomes. | Module separation gives no process isolation; callbacks can still affect the host process. | Which decisions belong together in a deep module, and which belong to the embedding application? |
| Specify owned, borrowed, invalidated, and still-releasable values | [Public types](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/types.h#L128-L161) distinguish owned tracked references from borrowed graphics handles; [strings and buffers](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/types.h#L260-L288) document lifetime and required-capacity output. | A read window, execution handle, retained report, and spillover reference each expose their own lifetime and release rules. Optional retained files survive execution-resource release; external readers do not extend OnePage's retention charge. | One opaque handle type cannot hide differences between canonical content, private scratch, and externally mutable ordinary paths. | What values cross boundaries, and can each owner enforce its resource lifetime locally? |
| Make stale references harmless at their owner | [Tracked-reference implementation](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/terminal/c/grid_ref_tracked.zig#L16-L91) checks owner/screen generation and allocates a replacement pin before releasing the old one; [destruction test](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/terminal/c/grid_ref_tracked.zig#L195-L228) checks safe no-value behavior after terminal free. | An old callback after execution-capacity reuse cannot settle new work or refund its resources. | An in-memory generation proves no durable effect happened; recovery still needs admitted identity and effect-specific evidence. | How should identity, cancellation, completion and safe reuse be represented? |
| Define failure by the state it leaves behind | [Snapshot decoder](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/snapshot.h#L423-L481) distinguishes pre-consumption rejection from a poisoned decoder and preserves the caller-owned terminal after later history failure. | A command interface distinguishes rejected before admission, committed but acknowledgment lost, failed execution, and unusable Store connection. | Terminal partial restoration does not justify operating on incompletely reconciled effects. | Which errors leave inputs/owners reusable, which transfer ownership, and which require restart? |
| State effect timing and reentrancy explicitly | [Terminal effects](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/terminal.h#L55-L83) are opt-in synchronous callbacks, forbid recursive VT writes on the same terminal, and warn against expensive blocking work. | An embedder permission or completion callback needs a specified calling context, borrowing lifetime, legal reentry, and deferred-response path. | A synchronous callback is not a durable admission barrier and cannot justify waiting inside a SQLite transaction. | How do embedding applications interact safely with control and effect execution? |
| Expose progress without hiding scheduling | [Compression contract](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/terminal.h#L44-L51) creates no timer/thread; [incremental/full modes](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/terminal.h#L2244-L2267) distinguish bounded steps from a potentially stalling scan and require caller serialization. | Large Edit, report capture, import or recovery work must coexist with cancellation and controls; an external application's event loop may have its own requirements. | Incremental steps alone provide neither a wall-clock bound on filesystem calls nor fair service among populations. | Who owns driving and wakeups, and what progress/responsiveness contract crosses the API? |
| Make resource customization an intentional capability | [Allocator contract](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/allocator.h#L24-L67) supports explicit allocation and matching free with convenient defaults. | An external application's resource envelope may need to coexist with OnePage's budget; private temporary growth and FIFO retention must remain charged through ownership transfer. | An allocator parameter is not a whole-process memory bound, disk allowance, bounded handle population, or safe fallback policy. | Which controls are public, which are enforced inside owners, and what costs can an embedder rely on? |
| Prove dependency direction through build products | [Module build](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/build/GhosttyZig.zig#L105-L157) wires required and conditional dependencies; [native example](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/example/zig-vt/build.zig#L16-L29) documents disabling SIMD to avoid libc at a performance cost. | Compile an embedding consumer without importing CLI, HTTP or evaluator machinery it does not use. Compare optional capability costs on actual products. | Zero-dependency is configuration-dependent. SQLite, transport and credential services may be essential to a complete OnePage capability. | What is the module/import graph, and which dependencies are required by each consumer? |
| Validate the interface and real artifact, not only the core | [Library test and ABI steps](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/build.zig#L67-L79), [artifact schema verification wiring](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/build.zig#L127-L155), and the [stream fuzz target](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/test/fuzz-libghostty/src/fuzz_stream.zig#L8-L66). | Exercise the same selected API from CLI/workflow/embedding consumers; inject failures at admission, transfer, cancellation and recovery boundaries; verify actual imports and artifacts. | The fuzzer skips terminal initialization on allocation failure. That is robustness evidence, not proof of successful bounded OnePage workloads. ABI testing is relevant only if an ABI is selected. | What evidence must distinguish a convincing interface sketch from a production guarantee? |

## Policies that must not transfer by analogy

- **Best-effort parsing is not semantic acceptance.** [`ghostty_terminal_vt_write`](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/terminal.h#L2055-L2078) returns no error and logs malformed-input/processing errors to preserve terminal consistency. OnePage must not silently accept partial provider continuation or report incomplete canonical publication as success.
- **A bounded queue is not a durable queue.** The [application mailbox](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/termio/mailbox.zig#L57-L108) may wait indefinitely on a full queue and dispose a message when waking the writer fails. This supplies no permission to drop accepted OnePage work or introduce an unbounded control-path wait.
- **Streaming callbacks are not automatically nonblocking.** The [reader/writer contract](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/io.h#L28-L70) distinguishes EOF from short reads, has no would-block outcome, requires writers to finish partial writes internally, and explicitly says successful write is not durability. Copying its signatures into a multiplexed Host could conceal blocking or discard resumability requirements.
- **A safety-confirmation retry is not exact authorization.** [Paste retry](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/include/ghostty/vt/paste.h#L36-L53) intentionally rereads the source and may paste different bytes after confirmation. OnePage permission binds an exact immutable proposed Action.
- **Thread and failure isolation do not follow from library packaging.** Ghostty's [application runtime selection](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/apprt.zig#L38-L65) and standalone compression API have different scheduling responsibilities. Its [library panic path](https://github.com/ghostty-org/ghostty/blob/82232ecde55405559dec29c5466cb9e39938cb41/src/lib_vt.zig#L525-L557) traps. Choosing in-process embedding must explicitly assess the resulting shared failure domain; a C boundary does not isolate faults.

## Reuse and limits of the historical OnePage research

[Lessons from Ghostty](ghostty-lessons.md) and [Ghostty lessons for the architecture repair](ghostty-design-lessons-for-architecture-repair.md) remain historical research at upstream revision `6a508fd5e34c7e222c052a6d00bb3891ff3feace`. Their useful general lessons remain supported by the fresh ownership, progress, callback, failure, and test evidence above. The exact authorization and best-effort queue cautions also remain supported.

Their former recommendations must not choose the current design:

| Historical assumption or recommendation | Current limitation |
| --- | --- |
| One Wasm page, JavaScriptCore/native-Core wrapper, export fingerprints and image publication | These describe a previous executor and representation. Current docs place disposable workflow evaluation separately from native durable authority. They cannot require a Wasm-facing core or a compatibility layer in this redesign. |
| Harness `open / offer / drive`, authoritative Session Ledger, journal/checkpoint/projection publication | Current baseline puts canonical authority in SQLite with Operation-owned execution/results. Neither a ledger nor these method names are a present requirement. Preserve failure/commit reasoning, then choose the interface anew. |
| Per-slot images, completion inboxes, pooled pages and ownership epochs as a preferred representation | Current documents reject duplicate resident Session graphs and duplicate scheduling authority. Stale-event safety remains necessary, but Ghostty's implementation does not select OnePage's custody table, event topology, or durable identities. |
| Every temporary file tied to active execution or immediately unlinked | Current accepted spillover is a named ordinary file retained independently after saved result publication, subject to shared FIFO. Retained metadata/handles have their own population; active-capacity accounting alone cannot bound them. External file retention/mutation has an explicit scope exception. |
| Keep all public lifecycle boundaries and previous issue slices; keep embedding out of V1 | Earlier issue boundaries and terminal-display scope were conditional conclusions. External embedding is now a first-class subject of investigation. The research cannot preclude a new public capability or preserve current modules merely because they exist. |

Historical performance numbers, pool sizes, Wasm layouts and prototypes are not current OnePage production evidence. This note deliberately does not repeat their broad source audit or propose implementation slices.

## What the architecture comparison can now ask

Evaluate complete consumer traces against candidate designs: direct Session execution and permission wait; workflow composition with independent Sessions; external embedding with its own application lifetime; crash after effect admission; cancellation before physical cleanup; retained spillover after execution release; and large input/output under pressure. For each candidate, show which module owns durable facts, temporary resources, progression and failure handling, and what the consumer must coordinate.

The evidence favors testing those responsibilities concretely. It does not decide whether the best result is one embeddable Host, a smaller family of capabilities, or a different internal decomposition beneath the same consumer facade. API stability, foreign-language bindings, distribution and product amendments remain separate choices.
