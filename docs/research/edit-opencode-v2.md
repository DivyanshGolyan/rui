## What is implemented

OpenCode v2 exposes two relevant model-facing tools:

| Tool | Input shape | Scope | Matching/application |
| --- | --- | --- | --- |
| `edit` | One `path`, one `oldString`, one `newString`, optional `replaceAll` | Exactly one file per call | Exact substring first; then Unicode typography normalization; then line matching that trims trailing whitespace. Requires one match unless `replaceAll` is true. |
| `patch` | One `patchText` containing parsed add, update, delete, and move hunks | Multiple hunks and multiple files in one call; successive update hunks may target the same file | Parses and prepares every hunk, derives updated contents against the current prepared content for repeated updates, then applies prepared changes in order. |

The `edit` schema is single-file/single-replacement input; it has no array of files, ranges, or explicit coordinates ([local `edit.ts:24-39`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L24-L39)). Its replacement matcher records byte/string offsets, tries exact matching first, then normalizes curly quotes, dash variants, and Unicode spaces, and finally matches line sequences after trimming line-ending whitespace ([`edit.ts:42-101`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L42-L101)). The source and tests confirm that `replaceAll` applies all non-overlapping matches; default mode reports ambiguity and does not write ([`edit.ts:163-175`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L163-L175); [`tool-edit.test.ts:379-429`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-edit.test.ts#L379-L429); [`tool-edit.test.ts:537-566`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-edit.test.ts#L537-L566)).

`patch` accepts a textual patch whose parser can express add, update, delete, and move operations. Its preparation loop resolves every hunk, reads update/delete targets, derives each resulting content, and builds all diff metadata before the edit permission request ([`patch.ts:84-207`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L84-L207)). Multiple update hunks for one file are supported through the `updates` map: each later hunk is derived from the previous prepared content ([`patch.ts:151-180`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L151-L180)). The tests cover successive updates to one file and multiple files in one patch ([`tool-patch.test.ts:156-242`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L156-L242); [`tool-patch.test.ts:654-668`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L654-L668)).

## Permission, reads, previews, and writes

For an internal `edit`, OpenCode resolves the path and then reads the complete target file before calling `permission.assert`. It computes the prospective replacement and diff preview, asks for `edit`, and only then writes ([`edit.ts:146-207`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L146-L207)). The edit tests explicitly show one read before a denied edit and no write ([`tool-edit.test.ts:346-377`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-edit.test.ts#L346-L377)). Thus the implemented permission ordering is: external-directory approval first when needed, content read/match/preview, then edit approval, then write.

For `patch`, external-directory approval is requested while each target is resolved, before reading that external target. For internal targets, preparation reads happen first. All hunks are prepared and all diffs are assembled before one edit permission request containing resource names, a combined diff, and per-file diff metadata ([`patch.ts:114-207`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L114-L207)). The tests record two reads before the edit approval for an add/update/delete patch and record zero reads when external-directory permission is denied ([`tool-patch.test.ts:216-242`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L216-L242); [`tool-patch.test.ts:838-918`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L838-L918)).

The displayed permission preview is real computed diff data. `edit` puts one file diff in permission metadata; its returned output also carries the final diff ([`edit.ts:176-218`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L176-L218)). `patch` puts a combined textual diff and an array of file diffs in permission metadata, then returns file diffs after application and formatting ([`patch.ts:190-207`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L190-L207); [`patch.ts:254-285`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L254-L285)).

The ordinary local write path writes the complete resulting byte sequence with `fs.writeFile`; it creates parent directories, but does not write ranges or use a temporary file plus rename ([`environment/local.ts:51-55`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/environment/local.ts#L51-L55)). The edit path likewise computes a complete replacement string and passes the whole content to `FileMutation.write` ([`edit.ts:199-203`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/edit.ts#L199-L203)).

## Ordering, revalidation, and failure behavior

Both tools take process-local keyed locks around their read/prepare/write effect. The lock serializes cooperating OpenCode operations by resolved path, but the source explicitly says external writes can still race ([`file-mutation.ts:59-78`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/file-mutation.ts#L59-L78)). The `edit` test named “applies the edit when content changes after matching” changes the file after the read and expects the edit to overwrite the newer content ([`tool-edit.test.ts:622-643`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-edit.test.ts#L622-L643)). There is no expected-content/hash compare and no second content validation immediately before the write.

`patch` applies prepared operations sequentially after permission. Each ordinary add/update writes the complete target; deletes remove the target; moves write the destination and then remove the source ([`patch.ts:209-253`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/tool/plugin/patch.ts#L209-L253)). A runtime failure can leave a successful prefix on disk. The test forces the second add to fail and verifies the first file remains, with the error reporting “Completed before failure” ([`tool-patch.test.ts:793-813`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L793-L813)). A move can also leave both destination and source when destination write succeeds but source removal fails ([`tool-patch.test.ts:815-836`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/test/tool-patch.test.ts#L815-L836)).

This is runtime-failure behavior, not a crash guarantee. The implementation has no multi-file transaction or rollback, and says so directly: multi-file transactions/rollback are TODO, edits are sequential and report partial application, and crash recovery/idempotency for side effects are also TODO ([`file-mutation.ts:126-134`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/file-mutation.ts#L126-L134)). The source therefore supports neither all-or-nothing multi-file application nor a durable crash-resume guarantee. A process crash during a sequence of writes is outside the stated guarantee; the exact resulting prefix is not specified by these sources.

Cancellation is modeled by Effect interruption at the tool/runtime layer, and the tool contract says interruption must remain cancellation rather than become a model-visible tool failure ([`specs/v2/tools.md:29-47`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/specs/v2/tools.md#L29-L47)). The per-target file write itself is wrapped as uninterruptible inside its local keyed lock ([`file-mutation.ts:75-78`](https://github.com/anomalyco/opencode/blob/95503c177347a1a5e011bd0ed1c8fe830d7309b/packages/core/src/file-mutation.ts#L75-L78)), but there is no source-backed guarantee that cancellation or a crash rolls back an already-started complete-file write or a previous operation in a multi-file patch.

## Relevance to an explicit-range proposal

The closest implemented analogue is `patch`: one call can carry multiple explicit hunks/files, computes a complete preview before edit approval, and applies the prepared results sequentially. The important limits are that its hunk context is text-derived rather than durable range identity, it reads files before edit approval, it does not revalidate the approved source before writing, and partial application is an expected runtime failure outcome.

OpenCode’s single-file `edit` is a weaker analogue for a proposal model: it takes one old/new text pair, supports exact plus corrective matching, exposes a diff preview, and writes the entire resulting file. Its tests demonstrate overwrite-after-read drift and therefore do not establish stale-content protection.

These findings describe implemented behavior and explicit TODOs only. They do not select a OnePage policy for whether proposal creation may avoid reads, whether approval should bind to source bytes, or whether applying multiple ranges should be atomic.
