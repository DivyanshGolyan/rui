# OnePage architecture

This document is normative. Historical spikes and research explain how the project reached this design; where they conflict, this document and accepted ADRs win.

## System shape

```text
Caller: person, coding agent, or supervisor Agent
                    |
         local CLI adapter
                    |
        protocol-independent Run Service
                    v
              Host Runtime
       sole live owner of Host Store
          /                    \
 durable Workflow Run      durable Job Sessions
          |                    |
 spawn one disposable      Harness / Core
 Workflow Evaluator        Provider and tools
          |
 Completed / Blocked / Failed
```

OnePage is single-host. One native Zig **Host Runtime** owns one **Host Store** at a time and routes all durable access through its sole **Storage Owner**. It owns Workflow Runs, Jobs, agent Sessions, shared capacities, and every evaluator process; it is the only agent runtime. A **Caller** invokes the protocol-independent **Run Service** through the local CLI. A **User** is a Conversation role that may be fulfilled by a person or another Agent; it does not identify the Caller, security Principal, Run owner, or permission Authority. The Caller supplies a **Workflow Definition** that expresses demand for keyed Jobs, while the Host supplies and owns the Sessions that fulfil that demand. QuickJS is only the implementation of a transient, Host-managed **Workflow Evaluator** and never owns durable state, a Session, provider, tool, permission, or recovery decision. The Workspace is external mutable truth. Local durable storage is authoritative for Session and Workflow Run semantics but cannot reconstruct or overwrite arbitrary external Workspace changes.

## Simplicity boundary

Simplicity is a V1 correctness requirement. Each architectural role must own one necessary responsibility and hide enough mechanics to justify its existence. A new module, abstraction, durable representation, resident pool, background owner, or extension point is permitted only when it directly supports a current product guarantee, an external-effect boundary, or release evidence and cannot fit an existing owner without weakening that owner's contract.

OnePage prefers established dependencies for mechanisms and keeps policy in its existing domain seams. SQLite owns physical database transactions; Git owns patch parsing and application; HTTP, TLS, browser, and OS credential-store dependencies may supply narrow mechanisms for the provider-specific Codex authorization path. A transport dependency is accepted only when it cannot inspect the Workspace, select context, run tools, retry consequential work invisibly, or advance Session state.

V1 deliberately has no generalized scheduler, provider registry, OAuth framework, runtime tool registry, plugin loader, generic effect executor, terminal framework, custom SQLite VFS test system, Host Store maintenance subsystem, daemon, event stream, or industry wire-protocol adapter. The provider-neutral Conversation and model-tool data contract serves the deterministic Provider and Codex now; it is not an execution extension system. The Run Service is a native semantic boundary, not a network service requirement. The Workflow Evaluator is a disposable implementation detail behind the Host's workflow boundary, not a second runtime, durable coordinator, or generic extension host. Hypothetical reuse is not evidence. Adding a broader surface requires a concrete second consumer and an accepted ADR that explains why the existing deep modules are insufficient.

The resident-memory contract covers **OnePage-owned orchestration memory**: Activation Slots, live Harness state, Host Runtime metadata, SQLite, provider transport, bounded adapter capture, shared semantic-validation workspaces, and the one live Workflow Evaluator. It does not cap **workload memory** intentionally consumed by a model-requested Bash process or its descendants. Workload memory is observed and reported separately. A Dormant or closed Session and a Blocked Workflow Run retain no live Harness allocation, Active Credit, thread, socket, subprocess, JavaScript heap, Promise graph, or materialized Conversation. An In-flight Session retains no Harness, Activation Slot, or semantic-validation workspace but may retain the one bounded provider or tool resource owned by its admitted Attempt and Active Credit. A live evaluation may scale only with its current bounded Visibility Snapshot up to the fixed Workflow Resource Profile; it retains no cumulative state from older evaluations. No other resident allocation may grow with historical opens, closes, completed Jobs, or workflow replays.

## Durable authority

The Host Store is one host-wide SQLite database. Each Session owns one append-only **Session Ledger** within it. The complete ordered ledger is the sole order of semantic facts that create, advance, recover, cancel, or complete that Session. It includes task admission, accepted model and tool Operations, Attempts with typed recovery classes, Approval Required, Authorization, Results, Conversation advancement, reconciliation, cancellation, and Outcome. Recovery disposition is derived from the fact kind and typed evidence rather than stored as a redundant wire field.

One call to `Session.commitSemantic` prepares one typed transaction containing one to eight ordered facts and optional Core State. That transaction is the Storage Owner's only semantic commit input. The Storage Owner validates and canonically encodes it, derives its admission class and every normalized Conversation or Completion write, then occupies one Session sequence and one ledger row. One SQLite transaction atomically fences the ownership epoch and expected head, inserts the row, advances the head, and writes the derived indexes. No independently supplied projection sidecar exists, and no enclosed fact or side effect is visible unless the complete transaction commits.

Each live Session has one copyable `ResidentState`: the sole Session sequence and semantic index, the linear V1 Conversation head, and relevant pending Completion evidence. Live commit and recovery apply the same pure ledger reducer to produce the next complete value. Ledger advancement also prunes Completion evidence made terminal or irrelevant by that transaction. After durable commit, publication is one `ResidentState` assignment plus clearing explicitly volatile preparation; Conversation and Completion state have no separate publication or reconstruction protocols.

The Session retains its claimed ownership fence and validates it internally on every operation. Callers do not retrieve a token from a Session merely to pass it back; persisted facts carry ownership epochs only where the epoch is domain evidence, while the Host Store's conditional head update remains the authoritative stale-owner fence.

Inside the process, a semantic fact is a typed variant with a kind-specific payload. Cross-kind combinations are not representable; Result evidence additionally couples recovery class, Attempt identity, and evidence kind as one typed choice. Scalar identity and range validity is checked before canonical publication and after decode. The compact flat tagged form exists only inside the canonical codec, where hostile wire input is validated completely before constructing a typed fact.

Large or variable content is immutable and stored outside SQLite. A publisher writes and synchronizes content before committing a Session Ledger transition that references it. Failure before that commit may leave an unreferenced blob, which is garbage; a committed transition may never reference absent or unverified content.

The following are non-authoritative and cannot establish Session semantics:

- runnable and waiting indexes;
- lookup accelerators;
- generation-scoped Harness Projections and committed Run Snapshots;
- same-build activation caches, if later measurement justifies them;
- immutable Captured Model Output and the durable Completion Inbox used to reconcile adapter evidence that has not yet entered the Session Ledger.

Derived views may lag the Session Ledger. Captured Model Output and Completion Inbox evidence may precede their terminal transaction and remain after association for audit, but only unconsumed pending evidence belongs to the recovery scan or resident value. Neither advances semantic authority. Recovery replays complete ordered transactions through the same reducer used for live publication and reconstructs Core State from the newest committed payload that contains it. A sequence gap, duplicate, conflicting identity, invalid transaction payload, or missing referenced content fails the Session closed. SQLite owns physical transaction atomicity and journal recovery; OnePage owns semantic validation and does not claim protection from arbitrary faulty hardware, hostile same-user state mutation, or storage returning incorrect bytes.

Streaming deltas, terminal frames, diagnostics, scheduler polling, and raw provider payload bytes are not Session Ledger facts. They are volatile projections, debug evidence, or immutable content. Provider adapters stream one bounded candidate house result into **Captured Model Output** and publish its exact Attempt-bound Completion evidence. The existing Harness owner path later performs **Semantic Admission**: it borrows shared validation scratch, validates the captured bytes once, and atomically commits either their typed Result meaning or a typed terminal failure with Core State through the Session Ledger. Crash recovery repeats admission only when captured evidence exists without that terminal transaction. Matching already admitted content is not parsed and reserialized merely to re-prove its formatting.

## Workflow runs and jobs

A **Workflow Run** is Host-owned orchestration state, separate from every agent Session. It durably binds the Caller Run Key, exact Workflow Definition bytes, exact bounded arguments, canonical invocation Workspace identity, a workflow-semantics identity, a Workflow Resource Profile, and its terminal outcome. A completed outcome contains one canonical **Workflow Output**; failed, cancelled, deadlocked, resource-exhausted, and protocol-failed outcomes contain no Output. V1 runs one foreground driver at a time. Every Job Session inherits the stored Workspace. Exiting the foreground process leaves the non-terminal Run in its durable state; it does not cancel the Run or its Jobs. A **Blocked Workflow Run** is specifically waiting for its complete requested Job set and retains no evaluator. Explicit advancement reevaluates the stored Definition and arguments in the stored Workspace and never rereads a possibly changed source file or adopts the advancing process's current directory. Explicit Run cancellation durably prevents new Jobs and requests cancellation of member Sessions where their existing lifecycle still permits it. A late Job Outcome cannot revive a cancelled Run, and later inspection reports the stored cancellation.

Each `agent({ key, task, input, schema, agent_profile })` call names one durable **Job** within its Workflow Run. `key` is mandatory, unique within the Run, and contains 1–128 Unicode scalar values and at most 512 UTF-8 bytes; caller-defined Job Keys are not shell-safe system identifiers. `task` is non-empty bounded user-task text; `input` is a strict bounded data value included in the model-visible initial task; optional `schema` defines the successful Job Output; and optional `agent_profile` defaults to the built-in `default` Agent Profile. V1 exposes only that Profile; an unknown name fails before Job creation. It binds Codex instructions, exact Model Contract, and Tool Catalog but grants no permission or workflow resource. The Host canonically encodes the complete immutable Job specification. `(run_id, key)` with the same digest reattaches to the same Job and Session; the same key with different canonical bytes is a closed conflict. A Job owns one ordinary Session in the Run's Workspace. Without a schema, a successful Final Answer becomes text. With a schema, it must be exactly one UTF-8 JSON document after surrounding JSON whitespace and must validate locally against OnePage's closed JSON Schema 2020-12 subset: `type`, `properties`, `required`, `additionalProperties: false`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, and `enum`, without references or extension keywords. OnePage does no Markdown-fence extraction, substring search, repair, or coercion. Parse or validation failure rejects `agent()` as `JobOutputInvalid`; provider-native structured output is optional lowering, never authority. Every rejection is one frozen `JobError` with bounded `code`, `job_key`, and `message`; the closed V1 codes are `JobFailed`, `JobCancelled`, `JobIndeterminate`, `JobOutputInvalid`, `WorkflowDefinitionConflict`, and `ResourceExceeded`. `JobIndeterminate` is reserved for a terminal Job whose Session cannot safely produce a more reliable Outcome; an indeterminate tool Result alone is model-visible evidence and does not terminate the Job. The workflow layer does not add a second Conversation, provider loop, tool executor, permission system, agent tree, or workflow helper API.

The Storage Owner is the sole gateway for canonical Workflow Run and Job records in the Host Store. These records are distinct from Session Ledgers: they bind Workflow Run identity and Job membership but never duplicate Session Conversation or effect facts. Before launching an evaluator, the Host commits one **Evaluation Generation** and the digest of its exact immutable, run-local **Visibility Snapshot**. A retry of that generation uses identical Definition, arguments, semantics, Workflow Resource Profile, and snapshot even if more Jobs finish meanwhile.

The evaluator receives only terminal Job Outputs and stable terminal Job failure codes in that Visibility Snapshot and evaluates the exact source from the beginning. `agent()` either resolves or rejects from the snapshot or records the Job in the evaluation's blocked set. If the entry point cannot complete because Jobs are unresolved, the evaluator returns the complete canonical blocked set and exits. The Host commits that outcome, makes those Jobs runnable, waits until the whole set is terminal, then commits a later generation and snapshot before starting a fresh evaluator. It never retains a native Promise resolver or JavaScript continuation across this barrier.

Provider or tool completion timing is not semantic workflow input. Physical Job completion order is unobservable: results become visible together at a whole-blocked-set barrier, and the evaluator exposes `Promise.all` and `Promise.allSettled` but not `Promise.race` or `Promise.any`. Source that relies on wall-clock races, timers, randomness, or background work is outside the supported workflow contract. A completed root with unresolved or detached jobs is `Blocked`, not silently successful. Every evaluation ends as exactly one of `Completed`, `Blocked`, `Failed`, `Deadlocked`, `ResourceExceeded`, or `ProtocolFailed`.

Workflow Run state and Session state are independent. `Blocked` means only that a Workflow Run awaits its complete Job set. `Awaiting User` means a Session has one open permission or input Interaction Request. `In-flight` means a Session has one admitted external Attempt. The public Run state `input_required` is derived only when an Interaction Request is open and no other work can progress. Normative interfaces, Run Snapshots, and Projections do not use an unqualified `waiting` state because it would collapse these distinct ownership and wake-up rules.

The workflow data bridge accepts only bounded null, Boolean, string, array, string-keyed plain object, and finite IEEE-754 number values. Every string must be Unicode scalar text: a well-formed UTF-16 surrogate pair encodes as its standard UTF-8 scalar, while a lone surrogate is rejected without replacement or lossy encoding. An integral number must lie in JavaScript's safe-integer range, and negative zero canonicalizes to zero. The bridge rejects `undefined`, functions, symbols, bigint, cycles, accessors, proxies, host objects, lone surrogates, non-finite numbers, unsafe integers, unsupported prototypes, excessive depth, excessive entries, and excessive encoded bytes. Job Outputs may carry bounded data or a validated data-only durable content handle; the evaluator never receives a complete Conversation graph. The root function must explicitly fulfill with one bridge value. The Host canonically encodes and durably commits that Workflow Output before exposing it through a Run Snapshot or Content Reference; an invalid or implicit `undefined` return fails as `WorkflowOutputInvalid`, and interrupted presentation reuses the stored Output without evaluation.

`agent()` is the only supplied workflow capability. Ordinary JavaScript functions, loops, arrays, and deterministic Promise joins express fan-out, sequencing, branching, and joins without Host helpers, durable DAG nodes, or another scheduler. V1 has no model-visible Agent tool: composition is controlled by the Caller-supplied Workflow Definition while each model remains confined to its own Session and admitted model tools.

## Run interface

The **Run Service** is the highest protocol-independent semantic boundary. It is a native interface hosted with the foreground V1 process, not a daemon or public wire protocol. The CLI composes six operations and owns no Run, Job, Session, permission, or recovery policy:

| Operation | Semantics |
| --- | --- |
| `startOrAttach` | Idempotently create or find a Run by Caller-supplied Run Key and exact bound inputs; commit before acknowledgement. |
| `getSnapshot` | Return one pure committed `RunSnapshot`; never drive or mutate. |
| `submitResponses` | Validate and atomically commit a bounded batch of Interaction Responses; advancement is separate. |
| `requestCancel` | Durably record cancellation intent; repeated identical requests succeed. |
| `advance` | Acquire the owning Host Runtime's fenced driver guard and execute until a public caller boundary. |
| `readContent` | Read immutable Run-owned content by opaque reference and bounded range. |

The CLI commands are thin compositions: `run` is `startOrAttach` followed by `advance`; `respond` is `submitResponses` followed by `advance`; `cancel` is `requestCancel` followed by `advance`; and `inspect`, `advance`, and `read` map directly. Only one fenced driver may advance a Run. Inside one owning Run Service instance, committed reads do not require the driver lease. A second V1 CLI process still receives `busy` from the Host Store lifetime lock; cross-process observation during advancement would require the deliberately deferred daemon or IPC owner. V1 may reject concurrent `respond` or `cancel` while a driver is attached. Terminal Runs are immutable and later advancement returns the existing committed snapshot.

Run creation requires a stable Caller Run Key unique within one Host Store. The same key with equal workflow source, arguments, Workspace, semantics, and resource-profile bindings attaches to the existing Run; changed bindings conflict. Every Run operation derives the local Principal from the invocation and checks its Run access plus any delegated Authority required by that operation; knowing or reusing a key grants no access. This resolves a crash after durable creation but before stdout acknowledgement without creating a second Run. Response submission has the same retry discipline: identical replay of an accepted response succeeds; a different answer to an answered request, an answer to a withdrawn or unknown request, or an authority or binding mismatch rejects the complete batch. Cancellation is idempotent. A failed pipe or invocation after a commit does not prove that the mutation failed, so all mutating operations remain safely retryable.

A **Run Snapshot** is a committed revisioned read model over durable Run, Job, Session, interaction, output, failure, uncertainty, and Artifact facts. It is not semantic authority and never exposes `Harness.Projection` or its generation-bound content reference. [`docs/spec/run-snapshot-v1.schema.json`](docs/spec/run-snapshot-v1.schema.json) is the complete normative external JSON representation. Markdown is a deterministic bounded model-facing view generated only from the corresponding semantic value; it may omit non-actionable detail but may introduce no independent fact or transition. Opaque IDs, revisions, sequences, byte offsets, and other values that may exceed JavaScript's safe-integer range are JSON strings. A pagination cursor binds one snapshot revision or explicitly ranges over immutable monotonic records. Every currently open actionable request is present without pagination.

The normal foreground boundaries are `input_required`, terminal `completed`, `failed`, or `cancelled`, and `suspended` only if a concrete supported non-user wait cannot retain an in-process wake source. `input_required` requires both an open Interaction Request and proof that no other Run work can currently progress without a response. `running` is normally observed only through an in-process concurrent inspection; another V1 CLI process receives `busy`. SIGINT, terminal closure, caller timeout, and output failure detach the invocation without cancelling the Run; explicit `requestCancel` is the sole cancellation authority.

Run output uses complete inline text, complete inline JSON, or a Run-scoped **Content Reference**. Inline values never carry a truncation state. Content that does not fit inline is represented only by a reference; its optional bounded preview may be truncated while the complete immutable bytes remain readable. Final text, complete permission descriptors, large diagnostics, and immutable Artifacts are materialized before the originating Harness generation or evaluator is released. Each reference binds media type, byte length, digest, and optional bounded preview and remains valid for at least as long as its Run is inspectable. `readContent` enforces Run and Principal scope and bounded range reads. A mutable Workspace path is not itself an immutable Artifact; a workspace-change Artifact records validated relative paths and before/after bindings and references immutable content when needed.

V1 ships no MCP Tasks, ACP, A2A, event, subscription, webhook, or streaming adapter. These protocols validate parts of the semantic shape but do not define it. A later observation mechanism should prefer conditional long-poll snapshots; notification delivery remains non-authoritative and can never submit an Interaction Response.

## Conversation and Workspace

Conversation is the immutable parent-linked model-visible history. Its semantic entry kinds are `user_text`, `assistant_text`, `tool_call`, `tool_result`, and `context_checkpoint`; tool-specific execution bytes and provider wire objects are not Conversation kinds. V1 is linear: each committed entry is the child of the current `conversation_head_id`, and branching is not implied by the reserved Session `branch_id`. Every normalized Conversation row is committed-only, names its creating Session Ledger sequence, and is mechanically derivable from the typed `conversation_advanced` fact. Session creation atomically commits the Session identity, initial canonical transaction, and root Conversation row; it does not admit the task for execution. The later `task_admitted` fact acknowledges offered Task custody. Effect-recovery facts enter Model Context only through a committed `tool_result` Conversation Entry.

V1 permits at most one outstanding tool call. A `tool_result` is the immediate child of its `tool_call`: the call entry's `entry_id` is the stable call identity and the result's `parent_id` identifies it. Commit, decode, recovery, and context-window selection reject a missing, duplicated, non-adjacent, or split pair. A Tool Call stores its exact bounded strict JSON arguments, byte identity, Validation Profile, and the Tool Catalog identity fixed by its model Operation. V1 requires one unambiguous admitted meaning but no semantic-equivalence identity across independently encoded JSON. Conversation content is bounded immutable semantic content. Provider requests never expose Session Ledger sequences, SQLite row identifiers, blob paths, internal content handles, or provider-hosted conversation IDs.

A Context Checkpoint is an immutable Conversation Entry used by future compaction. V1 has no separate State Checkpoint: canonical Core State is already carried by the authoritative transaction that produced it.

An **Interaction Request** is immutable durable input demand. V1 supports two kinds: runtime-issued `permission` and Agent-issued `input`. The Agent issues input only through the provider-neutral, non-effecting `input_request` model disposition; it is not a Tool Call or executable Action. Committing that disposition atomically appends its bounded prompt as `assistant_text` and creates a request accepting either bounded text or one bounded single choice. Requests have never-reused identities, origin, routing scope, created Run revision, prompt content, response shape, and open, answered, or withdrawn state. Changing a request withdraws it and creates a new identity; ordinary response freshness is bound to that request identity rather than the whole Run revision.

One bounded atomic response batch carries both kinds under the normative [`InteractionResponseBatch`](docs/spec/interaction-response-batch-v1.schema.json) JSON contract, but their validators remain separate. Request identities are unique within the batch, and the responding Principal is invocation-derived rather than caller-asserted content. A permission response is a structured `allow_once` or `deny` decision and cannot be expressed as free text; it echoes the exact descriptor digest. It does not repeat operation identity or generation because the immutable open request already binds them. An input response carries bounded text or one allowed choice identifier. Permission validation checks the responding Principal, delegated Authority, operation identity and generation from the request, descriptor digest, allowed decision, and open request state. Input validation checks the User-role routing, content shape, request-specific byte or option bound, and open request state. Accepted conversational input becomes a canonical `user_text` Conversation Entry before the next model Operation. V1 accepts no unsolicited input when no matching request is open and no arbitrary forms, credentials, file uploads, notifications, or generic signals.

Every permission request states that a Job proposed an operation and OnePage validated its exact descriptor. It contains a complete structured summary plus the operation identity and generation, descriptor digest and byte length, allowed option identifiers, required Authority, and either complete bounded descriptor content or a Run-owned Content Reference. Truncation may affect only the preview, never the retrievable descriptor on which Authorization depends.

Conversation role and execution authority are independent. A parent Agent may provide a child's User-role content, but it may answer a permission request only when its Principal has an explicit delegated grant covering the exact operation. Otherwise the unresolved request propagates to an authorized Principal. Under the V1 default local trust profile, the invoking OS Principal may hold root Run authority; ask mode then provides durable orchestration and accountability rather than protection from that Caller.

The Workspace remains external truth because the User, Git, an editor, or another process may change it while a Session sleeps. One immutable **Patch Intent** binds the Workspace identity, canonical target path, permitted file properties, patch reference and digest, exact preimage digest, expected postimage digest, and Action generation before Authorization. Approval Required, Authorization, Attempt, and Result reference that same intent instead of reproducing its fields. Divergence produces a typed conflict or indeterminate Result; OnePage never reconstructs or overwrites a User worktree from Session history.

Git owns patch parsing and application semantics. The patch adapter prepares the expected postimage without mutating the bound Workspace, observes the target as preimage, postimage, divergent, or invalid, and applies only an authorized intent whose preimage still matches immediately before mutation. V1 assumes the target is quiescent from Authorization until Result commit; it does not claim atomic compare-and-swap protection against an uncooperative concurrent writer.

Host Runtime owns a fixed table of at most `active_capacity` **Workspace Effect Fences**. Before admitting any Bash or patch Attempt, Harness acquires the fence for the exact Workspace; contention releases the Active Credit and leaves the Session durably ready without admitting the effect. The fence transfers with the Active Credit and is retained until terminal evidence is applied or uncertainty is reconciled. Recovery rebuilds occupied fences from admitted non-terminal effect Attempts before new admission. OnePage never guesses that a Bash command is read-only. Model Attempts may run concurrently because they cannot access the Workspace or execute tools; Bash and patch Attempts may run concurrently only for different Workspaces.

## Core State and Activation Slot

**Core State** contains only compact semantic facts needed to continue one agent. It has an explicit schema version and canonical encoding with fixed widths, explicit enum values, defined byte order, length, and checksum. Unknown versions, states, enum values, identities, generations, or out-of-range fields fail closed. Native ABI fingerprints and struct layout are not durable compatibility rules.

**Activation Slot** is one Host-owned resident workspace whose actual size is derived at compile time from decoded Core State and the scratch used by production activation. It contains no page-size filler, speculative future reserve, or named buffer without a production reader and writer, and must remain at or below the 32 KiB V1 ceiling. A bounded content window is read directly into its final owner where practical; the activation path does not materialize a second full-size copy merely to transfer bytes between Host and Core. Core State never contains a native pointer or an offset into transient scratch. Large model responses, patches, command output, and Conversation content remain immutable blobs addressed by bounded handles and ranges.

At startup the Host Runtime resolves one explicit `active_capacity` and allocates that many Activation Slots plus fixed occupancy and generation metadata. Activation borrows a slot, decodes or reconstructs Core State into it, and performs no general-purpose allocation inside Core. Suspension encodes Core State, commits required semantic facts, scrubs the complete slot, and returns it to the pool. Slot identity and generation fence stale borrowed windows and late Completions. V1 adds no scheduler object around this pool.

Native Zig is the sole V1 Core executor. Native invariant traces cover accepted and rejected transition outcomes, rejection-state preservation, semantic observations, deterministic canonical encoding, and restoration through differently poisoned slots. Core State's fixed-width codec and the compile-time-bounded native Activation Slot are the portability and resident-memory contracts; V1 defines no secondary Core runtime or Core target ABI.

## Deep modules and interfaces

### Workflow boundary

The local CLI exposes `run`, `inspect`, `respond`, `advance`, `cancel`, and `read` as thin compositions over the Run Service. `run` reads the Definition and arguments once and submits them with the Caller Run Key and invocation working directory. Later commands identify the Run and never reread its immutable inputs. The Host Runtime creates or opens the Run, stores its canonical Workspace and inputs, owns every Evaluation Generation, launches and terminates evaluators, observes Jobs, and finalizes or cancels the Run. V1 exposes one built-in Workflow Resource Profile named `default`; omission selects it and an unknown name fails before Run creation.

The default export must be `export default async function workflow({ agent }, args)`. `agent` is the only supplied capability; ordinary JavaScript owns composition. For one Evaluation Generation, the Host gives the evaluator exactly the stored Definition, arguments, semantics identity, Workflow Resource Profile, and Visibility Snapshot over one bounded versioned protocol. The evaluator returns exactly one of `Completed`, `Blocked`, `Failed`, `Deadlocked`, `ResourceExceeded`, or `ProtocolFailed` and exits. It has no direct Host Store, Workspace, provider, tool, permission, network, filesystem, process, credential, environment, clock, random, timer, dynamic-code, or module capability. The evaluator contains a pinned QuickJS-ng dependency but is not an agent runtime.

The runner creates a raw QuickJS context and installs only the required ECMAScript intrinsics plus the frozen workflow capability object. It does not initialize QuickJS's standard library or OS helpers. Module loading and dynamic import are rejected; V1 evaluates stored source only and persists no bytecode. The QuickJS runtime enforces explicit heap and stack limits and an interrupt deadline. The bridge separately bounds native allocation, messages, Job count, result count, result bytes, diagnostic bytes, and microtask turns. The parent imposes a wall-clock deadline, closes unintended file descriptors, supplies an empty environment, disables core dumps where supported, and treats abnormal exit as a typed evaluation failure. These controls provide bounded local execution and defense in depth; they are not hostile multi-tenant isolation.

The workflow-semantics identity binds the QuickJS-ng version, runner protocol, allowed intrinsics, exact `{ agent }` capability-bootstrap bytes, bridge value encoding, Job-spec canonicalization, and named Workflow Resource Profile. An unsupported identity fails clearly. A release may reevaluate an existing Run only under the exact compatible semantics identity; source bytecode is never a compatibility artifact. QuickJS-ng is fetched unmodified through Zig's package dependency mechanism at an exact source URL and hash, and its license notices ship with OnePage.

### Core

Core is a deterministic reducer. It owns task phases, legal semantic transitions, Action interpretation, stable identities and generations, bounded context-selection policy, and terminal decisions. It consumes typed semantic input and produces a prepared semantic transition or a closed rejection. It does not perform I/O, allocate, publish durable records, format provider requests, execute tools, or render output.

### Harness

`Harness.open / offer / drive` is the complete Session lifecycle interface beneath workflow Jobs. No alternate direct Core advancement path exists.

The application first opens one opaque `HostRuntime` from a state path and host-level configuration, then gives a reference to each `Harness.open`. Exactly one SQLite-owning Host Runtime may exist in a process. The runtime owns the process-wide SQLite budget, state directory, singleton Storage Owner, connection, and Activation Slot pool. `Harness.open` acquires one private retained runtime lease, captures stable I/O, allocator, and execution capabilities once, and returns an opaque pointer-stable handle rather than a copyable resource-owning value. `Harness.close` consumes that handle: it closes Session resources, releases exactly one lease, destroys the complete Harness allocation, and makes every later use invalid. The runtime does not retain full closed Harness tombstones to make duplicate use appear safe. Harness configuration exposes no storage mechanics or create-time slices after open. Runtime close refuses while any lease remains. The application owner must serialize acquisition of an unretained runtime pointer against destruction.

- `open` acquires exclusive Session ownership through the Storage Owner and initializes fixed ledger and Inbox recovery cursors. A new Session returns ready immediately. A restored Session returns in `restoring`; it exposes no committed Projection or adapter work until `drive` has incrementally validated both snapshotted watermarks.
- `offer` nonblockingly transfers bounded Task, Completion, validated Interaction Response, cancellation, or shutdown input into fixed live-process ingress. It performs no I/O, allocation, wait, or Core call. `full` or `busy` preserves producer ownership; `accepted` transfers custody only to the live Harness instance.
- `drive` performs one bounded owner quantum. It borrows an Activation Slot only for that quantum, then encodes Core State, invalidates borrowed windows, scrubs the slot, and releases it before returning. It alone advances Core, publishes Session facts, admits immutable Attempts to adapters, applies durable Completions, and returns committed Projections and progress.

Projections are data-only values. They contain no Session pointer, generation pointer, file handle, or close authority. Content is reopened only through `Harness.openProjectionContent`, which checks the live Harness generation and Session identity before returning a bounded reader.

While restoration is incomplete, each `drive` consumes at most the configured recovery-record quantum and returns `restoring` with `more = true` and no Projection. The recovery cursor is a tagged protocol, so ledger, Inbox, pending, and ready fields cannot form invalid combinations. Completion offered during recovery remains in the single bounded Harness ingress slot and is not applied until the snapshotted pending-evidence watermark is safe. After the safe watermark is reached, Harness reconstructs the durable level state without dispatch, publishes Session identity first, and only a later `drive` may reconcile or admit external work. Recovery failure makes that live owner unavailable; a fresh `open` starts from durable bytes again.

Harness hides Session Ledger ordering, transaction replay, page activation and scrubbing, adapter admission, reconciliation, control settlement, and Projection regeneration. Cancellation and shutdown continue bounded Completion Inbox reconciliation while accepted Attempts settle; they publish a terminal Outcome only after no accepted Operation remains open. Host Runtime and lifecycle tests use the same interface; the public CLI never exposes it.

Issue #34 owns the asynchronous Active Credit transfer, closure handoff, wake, priority, and burst-drain behavior described below. Issue #32 supplies only the captured-output and shared semantic-admission prerequisite; it does not implement or verify that scheduler.

The Host Runtime multiplexes ready Jobs through this existing interface using exactly `active_capacity` fixed **Active Credits**. A credit is owned by one live Harness, one admitted external Attempt, or one closure handoff. Harness borrows an Activation Slot only during its bounded owner quantum. Committing Attempt admission transfers the same credit from Harness to the asynchronous adapter before the Harness is destroyed. Durable terminal evidence transfers it to a bounded keyed closure handoff; a fresh Harness applies it before the credit may be released or transferred to a later Attempt. An Awaiting User Session has no admitted Attempt and releases its credit; its immutable Interaction Request remains durable until a validated response is committed or it is withdrawn. The sum of these credit owners never exceeds `active_capacity`, so Harness and Attempt capacity cannot be counted separately. An Active Credit is a scheduling token, not a physical bundle of one Slot, parser workspace, transport connection, stack, and possible subprocess.

Adapters retain no Harness pointer or semantic-validation workspace. After Completion Inbox publication they may post only a bounded `(Session identity, generation)` wake hint to Host Runtime. The fixed wake table has at most one entry per Active Credit; a duplicate or full hint may be dropped because the Inbox remains durable authority. Bounded durable readiness reconciliation recovers a lost hint and opens a fresh Harness before using `offer / drive`. Semantic admission is closure work: it can use the shared validator without acquiring a new Active Credit and takes priority over new admission, so completed Attempts cannot exhaust every credit while waiting for validation. Workflow Job Outputs do not wake Sessions: the Host exposes terminal Jobs to a later Evaluation Generation only through its Visibility Snapshot. V1 uses a simple bounded ready order and fixed private resource-class permits inside Host Runtime rather than a public scheduler or fairness framework.

`offer` acceptance is not durable semantic acknowledgement. Only a committed Host Store transaction acknowledges durable acceptance. Until that commit, a process crash may discard volatile ingress: Completion is rediscovered from its durable Completion Inbox evidence, an uncommitted Interaction Response may be replayed against its still-open request, an uncommitted Task remains unadmitted, and uncommitted cancellation has not taken effect. The Run Service acknowledges semantic inputs only after commit and returns a committed Run Snapshot.

### Session storage

The Host Runtime acquires a lifetime operating-system lock before opening the Host Store. A second process targeting that store receives `busy`; SQLite transaction locks do not replace this singleton guarantee. Within the runtime, the Storage Owner is the only code allowed to open or access SQLite. Core, Harness instances, adapters, workers, and the CLI issue bounded requests and never open their own connections. The foreground CLI may host the runtime in V1; a future daemon may expose the same interface over bounded IPC.

The Storage Owner owns one pinned SQLite connection, schema installation and validation, Session sequences, ownership epochs, canonical transactions, normalized Conversation metadata, Completion Inbox evidence, and bounded reads. One request mutex serializes each complete public operation across every Harness, including its full `BEGIN` through `COMMIT` interval; SQLite calls from different requests cannot interleave on the connection. It executes only indexed and bounded statements and returns bounded results. Raw SQL, row identifiers, physical table shape, SQLite errors, and connection lifetime are not Session lifecycle interfaces.

V1 configures 4 KiB pages, rollback-journal `DELETE`, `synchronous=EXTRA`, foreign keys, `busy_timeout=0`, `mmap_size=0`, and `temp_store=FILE`. Tables are `STRICT`; defensive mode is enabled; trusted schema, double-quoted string literals, extension loading, `ATTACH`, and SQLite worker threads are disabled; conservative runtime limits constrain lengths, columns, SQL text, variables, expression depth, and database pages. The SQLite version and compile options are pinned. The 32, 64, and 128 KiB page-cache profiles are measured configuration points, not total-memory or production-performance promises. `sqlite3_hard_heap_limit64` covers every SQLite connection in the process, so Host Runtime—not an individual connection—owns and configures that allowance. Global heap is the authoritative enforced total. Page-cache, lookaside, and statement figures are non-additive diagnostics that may already be included in it.

The Host Store schema version and Session payload version are independent. Unsupported versions fail clearly. Pre-release V1 does not implement downgrade compatibility or a general migration framework. Opening reads schema identity from SQLite rather than inferring it from file existence. An empty database with zero application and schema versions may install or retry installation; an unowned non-empty schema fails closed. Schema objects and both identity fields commit in one transaction, with identity written last, so an interrupted installation remains safely retryable. Because V1 has no migration framework, open validates the exact stored DDL and object set. It does not duplicate that proof through weaker column probes, foreign-key counts, or eager preparation of every lifecycle statement.

### Adapters

Model, Bash, and `apply_patch` adapters receive only immutable admitted Attempts. They execute asynchronously after Harness has committed admission and released its Activation Slot. They may perform external work and publish typed evidence through the Completion seam; they cannot choose policy, advance Core, append Session facts, retry themselves, or render terminal output. A known provider dispatch failure is encoded as a durable terminal Result for its admitted Attempt; it is not recovered as missing evidence or retried. Each model Attempt commits a bounded count of earlier Attempts under that Operation that may already have reached the provider, making possible duplicate work or billing visible before redispatch. A model Operation may admit only its fixed recovery-history capacity: if every admitted dispatch loses evidence, exhaustion publishes a durable provider-failure Result for the last Attempt instead of stranding the Session or admitting an unrecordable retry. The deterministic external-model capability justifies the narrow Provider seam. The Codex adapter reuses that seam; V1 does not add a provider registry.

Adapter-owned buffers are part of orchestration memory. Variable output is streamed or spooled into immutable content through bounded windows; adapters do not retain one complete output and then allocate another complete encoded copy. Model adapters finish immutable Captured Model Output and release transport resources before the Host's semantic-admission stage uses parser scratch. The memory consumed by an admitted Bash process and its descendants is workload memory chosen by the model, not an Activation Slot or orchestration-memory guarantee. OnePage still owns bounded capture, durable publication, cancellation, process-group cleanup, and separate workload-memory reporting.

The Provider receives one versioned bounded semantic request assembled from the selected Model Context, instructions, exact model contract, exact **Tool Catalog**, and the built-in `input_request` disposition contract. A Tool Catalog is immutable model-visible data: each Tool Definition has a stable **Tool Key**, provider-facing name and description, bounded input JSON Schema, and bounded result-content contract. The input disposition is separate because it creates an Interaction Request rather than an Action or Tool Call. The catalog and other variable request content remain immutable blobs outside Core State and the Activation Slot; the model Operation binds their references and digests. The catalog's **Tool Catalog Digest**, semantic request digest, selected model profile, instructions, and Model Context are fixed when the model Operation is admitted. Every replacement Attempt under that Operation dispatches identical semantic request bytes. Changing any of them creates a new model Operation rather than a retry.

Provider adapters alone lower this house request into provider wire formats, bound provider framing and decompressed bytes, map provider-returned names deterministically back to Tool Keys, and map the declared input-request mechanism to the distinct house disposition. Conversion reads immutable request windows and spools response bytes incrementally; it does not require a second request-sized JSON value or an accumulated response. SSE or equivalent framing has an explicit transient-frame bound, and terminal events that repeat already-spooled output do not create a second retained copy. The adapter publishes one complete bounded candidate house response as Captured Model Output: non-empty assistant text, one Tool Key with exact JSON arguments, one bounded `input_request` disposition, or one typed provider failure. Streaming deltas, usage, provider request identifiers, raw wire payloads, and captured bytes are non-authoritative; partial output cannot authorize an effect or create an Interaction Request. Semantic Admission validates house framing, UTF-8, disposition, Tool Key and catalog membership, the versioned strict JSON profile, tool schema and bounds exactly once before committing a Result. Provider replay data is absent unless the Codex feasibility spike proves a bounded provider-specific sidecar necessary, and local Conversation remains the sole resume authority.

The Codex adapter implements the official Codex OAuth-compatible authorization and API semantics without embedding or invoking a Codex agent. One provider-specific flow may own browser authorization, PKCE/callback or device exchange, refresh, account selection, logout, and OS-backed credential storage. Established dependencies may own TLS, HTTP, browser opening, callback listening, and keychain mechanics, but not model selection, context, Workspace access, tools, retry, or Session state. OnePage owns the exact model name, bounded request and response, timeout, canonical decoding, dispatch uncertainty, and publication through the existing Provider contract. If the official subscription path cannot satisfy this boundary, the V1 product decision must be revisited explicitly; it does not silently fall back to an API-key aggregator or generalized authentication product.

Adapter evidence uses a non-authoritative durable **Completion Inbox**. A model adapter first finishes immutable Captured Model Output; other adapters finish their typed immutable result content. The adapter then asks the Storage Owner to commit one evidence row binding Session, ownership epoch, Agent generation, Operation and generation, Attempt, evidence kind, content reference, and digest. The envelope ownership epoch must equal the epoch committed with the matched Attempt, and its evidence kind must equal the kind selected by that Attempt's typed descriptor. SQLite assigns a host-wide positive Inbox identity; its uniqueness key excludes ownership epoch so a second epoch cannot disguise conflicting evidence for the same Session, Agent generation, Operation, Attempt, and evidence kind. Publication transactionally enforces at most 4,096 unconsumed rows per Session. Truly irrelevant evidence is not persisted. Valid evidence for an admitted Attempt that arrives after another Attempt completed the Operation is inserted already associated with the first terminal Result transaction sequence: it remains auditable but never enters the pending recovery bound or resident Inbox. The resident index handles the current Operation; evidence for an earlier completed Operation uses one purpose-specific Storage Owner cursor that reconstructs the exact Attempt and first terminal Result from indexed ranges of the Session's bounded 32,768-transition authoritative ledger. Point reads and cursor ranges share one verified transition-row decoder. During recovery, the Inbox read and every historical row consume the same owner quantum; live publication exhausts the same bounded cursor synchronously. The cursor requires the matched Attempt to precede the first terminal Result and requires their complete Operation contexts to match. No prior-Operation archive is retained in resident state. Exact duplicate evidence is idempotent and consumes no additional capacity. No Session-row counter or two-write publication protocol exists. Only after acknowledgement may the adapter offer the in-memory Completion notification. Lost notification is harmless: `open` and `drive` use the `(session_id, inbox_id)` index to scan only the bounded unconsumed range through the normal owner path.

Harness validates the complete identity and atomically associates the immutable evidence with the terminal Session transition through `consumed_by_sequence`; it does not delete the evidence on consumption. The unique Completion identity excludes ownership epoch, Result reference, and digest: the Attempt supplies the only valid epoch, the same identity and Result is idempotent, and a changed epoch or Result is a closed conflict. Missing, corrupt, or mismatched evidence never becomes authority and falls back to the Attempt's uncertainty rule. V1 retains evidence indefinitely. Post-V1 maintenance may collect it only after the Session is durably closed.

The Run Service presents committed Run Snapshots and immutable content reads without exposing Harness Projections, storage rows, or evaluator frames. The CLI parses commands, invokes only Run Service operations, and renders deterministic JSON or Markdown. The Host resolves its pools, adapters, Permission Mode, Principal, and delegated Authority and uses the same owner loop for creation and advancement. The CLI owns no Workflow Run or Session lifecycle policy.

## Transition protocol

Every authoritative state change follows:

```text
prepare -> commit -> publish
```

Preparation uses fixed scratch to validate identity, generation, descriptor, Authorization, capacity, referenced immutable content, legal Core transition, and the complete bounded typed payload. It may reject without changing authoritative state.

Every authoritative byte binding uses a domain-separated SHA-256 value with a semantic wrapper appropriate to its role. Descriptor, Patch Intent, preimage, postimage, Result, Completion, and ledger-record bindings share one cryptographic width but are not interchangeable identities. An all-zero digest is data, not an absence sentinel. These unkeyed digests provide collision-resistant byte binding and accidental-corruption detection; they do not make a locally rewritable database tamper-proof.

Commit asks the Storage Owner to publish one complete SQLite transaction. It may fail while leaving the previous Session sequence authoritative. An external adapter cannot observe an Attempt until that Attempt's identity, descriptor digest, ownership epoch, and recovery class are committed.

Publish assigns the already-prepared `ResidentState`, clears explicitly volatile preparation, and emits prepared Projections through infallible assignments. Semantic indexes, Conversation advancement, Completion pruning, capacity checks, and every other operation that can reject the transition are prepared before commit. If a platform operation after commit cannot complete, the live owner becomes unavailable and a fresh `open` reconstructs the committed transaction. Committed facts are never rolled back to match an older live image.

## Operations, Attempts, and recovery

An Action becomes one stable Operation. Operation acceptance and Attempt admission are separate Session Ledger facts. Each Attempt has exactly one current disposition:

- `definitely_unsent` — the adapter did not observe the Attempt;
- `possibly_executed` — the external effect may have occurred without a durable terminal Result;
- `terminal(Result)` — immutable typed evidence completed the Attempt.

Attempt admission is the conservative dispatch boundary. Once its Host Store transaction commits, recovery treats an unterminated Attempt as `possibly_executed` unless durable adapter evidence proves a terminal Result. `definitely_unsent` applies only when no Attempt admission committed or when a committed terminal adapter Result proves that external dispatch did not occur. OnePage does not infer non-execution merely because the Completion Inbox is empty.

The first durable terminal Result completes an Operation. Later evidence from a different admitted Attempt is associated with that terminal sequence for audit and cannot advance Core, Conversation, Projection, or Outcome again. Different evidence for the winning Attempt is a conflict.

Recovery is effect-specific:

| Effect | Recovery from uncertainty |
| --- | --- |
| Model inference | If the admitted Attempt lacks terminal evidence, admit a new Attempt under the same Operation whose durable duplicate count exposes how many prior dispatches may also bill or complete. A known provider failure is already a terminal Result and is not retried. |
| Bash | Never replay automatically; commit an indeterminate Result because arbitrary effects may have occurred, append the corresponding Tool Result to Conversation, and return the Session to the Agent for its next decision. |
| One-file patch | Observe the target through its durable Patch Intent. Accept the expected postimage without reapplying; apply a matching preimage only under the stated quiescence contract and current Authorization; stop on divergence or invalid target. |

Cancellation and shutdown stop new admission but settle or classify every accepted Attempt before publishing a terminal Outcome.

## Tools and Authorization

V1 exposes only the closed typed `bash` and `apply_patch` Actions. The model-visible Tool Definition and `tool_call` shape are generic so Provider conversion does not depend on those concrete Actions, but execution is not: Harness maps an allowed Tool Key through a closed switch to one admitted Action. Core accepts the admitted model disposition and selects the next semantic transition; Harness owns Action mapping, validation, Authorization, Attempt admission, durable ordering, and recovery, and a leaf adapter executes only an immutable admitted Attempt. Before Bash process spawn or patch mutation, Harness decodes the already admitted strict JSON exactly once into the existing durable typed effect descriptor bound to its Tool Call, implementation version, Workspace, and permission subject. Execution consumes that descriptor and never interprets generic JSON for the first time after Attempt admission. Tool visibility never grants authority; an unknown or unbound Tool Key cannot execute. Permissions remain a separate policy axis over the admitted Action. Bash covers inspection and verification through one bounded Result path. OnePage makes no repository-confinement or sandbox claim for Bash and never classifies an apparently read-only command as automatically safe.

A future out-of-tree tool requirement may justify a host-resolved definition table with stable input, output, and capability contracts. It must leave approval and durable recovery outside executors. V1 adds no dynamic registry, discovery format, unload lifecycle, dependency graph, event waterfall, or per-Session tool shadowing for two built-in Actions.

Validation creates an immutable descriptor before Approval Required or Authorization. The descriptor binds tool kind, exact bytes, Workspace and working directory, relevant environment and timeout, Action identity and generation, and preimage state where applicable.

`ask` is the default Permission Mode. It atomically commits Approval Required and an immutable permission Interaction Request for the exact descriptor before a Run Snapshot may expose it. The User Conversation role may be fulfilled by a person or another Agent, but that role grants no permission Authority. A matching allow or deny Interaction Response is accepted only from a Principal whose explicit Authority covers the exact operation identity, generation, descriptor digest, and option. Approval Required is an Awaiting User state, never an undecided Authorization. A valid response commits Authorization; explicit bypass commits Authorization for the same descriptor without creating a request. Both modes commit the exact Authorization before Attempt admission and follow identical validation and recovery paths. Shutdown and cancellation withdraw or deny outstanding requests before terminal control settlement. A prior exact Authorization remains evidence, but no Session retains blanket future authority.

## Capacity and density

V1 exposes one startup-fixed user-facing `active_capacity`. The Host Runtime allocates exactly that many Activation Slots and Active Credits. Each credit is owned by exactly one live Harness, admitted external Attempt, or closure handoff; Attempt admission transfers rather than duplicates the Harness credit. Private bounded resource-class permits reflect genuinely different costs for provider dispatch, effect execution, and semantic admission without becoming a public scheduler framework. V1 begins with `semantic_validation_capacity = 1` and one shared workspace; it increases only from measured throughput evidence. A future workload that requires parallel Attempts inside one Session must justify that change in a new issue.

Workflow evaluation is a separate Host-owned resource from agent Active Capacity. V1 fixes `workflow_evaluation_capacity` at one and launches at most one evaluator subprocess. A Workflow Run additionally binds named limits for source and argument bytes, Jobs per Run and per evaluation, simultaneously blocked Jobs, visible Job Output bytes, Workflow Output bytes, JavaScript heap and stack, native bridge arena, protocol and diagnostic bytes, microtasks, evaluation CPU and wall time, cumulative evaluations, and cumulative workflow CPU. These limits bound Host-managed workflow reconstruction; they do not change `active_capacity` or create per-effect Session pools.

Opening beyond `active_capacity` fails before Session ownership or external work is acquired. Temporary Active Credit, Slot, provider-permit, or effect-permit exhaustion returns bounded `busy`; it does not allocate, spin, create an unbounded queue, or disguise capacity exhaustion as a semantic Session state. Effect-capacity failure occurs before Attempt admission. Reconstructible semantic-validation scratch may be acquired after Captured Model Output is durable; temporary unavailability delays closure without changing committed semantics or redispatching the Attempt. Once an Attempt is admitted, its Active Credit remains reserved through terminal-evidence application, and closure handoff plus semantic admission takes priority over new admission without needing another credit.

The process-wide SQLite hard heap limit is the authoritative SQLite allowance. Page-cache, lookaside, and statement counters describe overlapping parts of that allocation and must not be summed as independent reservations. Request and result buffers remain separate OnePage reservations. Supported workloads must remain within a measured current and high-water envelope below the process allowance. `SQLITE_NOMEM` or violation of the validated envelope is a Host Store fault, not ordinary backpressure. Page-cache size is selected from the host budget and may grow on larger hosts without changing Session semantics.

SQLite's low-water page reserve protects only SQLite closure writes. Before admitting an external effect, OnePage durably prepares the immutable descriptor and any closure evidence that can be known in advance, then ensures the remaining bounded terminal representation can use the configured SQLite reserve and bounded blob policy. V1 does not claim that byte credits can guarantee writes on an arbitrarily failing or full filesystem. Failure to prepare evidence prevents dispatch; exhaustion after a possible effect fails closed and is reported as an unsupported storage failure rather than concealed by a scheduler.

The density proof has two required host axes. It measures 0, 100, 1,000, and 10,000 durable Dormant Sessions while holding `active_capacity` fixed, then measures `active_capacity` 1, 10, and 100 while holding durable population fixed. A 100,000-Session point is optional stress evidence rather than a V1 gate. A lifecycle run repeatedly opens and closes Harnesses under one long-lived Host Runtime and proves that orchestration memory returns to the same bounded envelope rather than following historical handle count. A workflow run measures empty, ordinary fan-out, maximum blocked-set, maximum Visibility Snapshot, and repeated-replay evaluations, then proves that Blocked and terminal Runs retain no evaluator process. The report publishes raw machine-readable measurements plus a concise table separating actual slot size and used components, reserved and occupied high-water slot bytes, semantic-validation workspace reservation, occupancy and queue high water, effective provider and effect permits, live Harness count, compact state, fixed host metadata, SQLite memory, provider transport, evaluator engine and native memory, virtual size, physical resident memory, blob and database bytes, and workload subprocess memory. Tests dirty and release each fixed workspace before measurement and include ordinary, maximally escaped, maximum-depth, many-member, malformed, and burst-completion model outputs. V1 claims that Activation Slot reservation is `@sizeOf(ActivationSlot) * active_capacity`; validation scratch scales with semantic-validation concurrency rather than Active Credits or provider waits; Dormant Session and completed Job population add durable bytes rather than resident objects; and a live evaluation uses at most its fixed Visibility Snapshot/resource-profile envelope without retaining memory from historical evaluations or closed Harnesses.

V1 has one SQLite writer and commits one whole Session request at a time. It has no fair queue, group commit, dynamic RSS feedback, pressure-triggered cancellation, topology experiment, or production scheduler. Additional writers, storage sharding, and scheduling policy require measured demand after V1.

## Failure and compatibility

Disk exhaustion, SQLite full, I/O, corrupt, and allocation failures, missing or corrupt referenced content, corrupt canonical payloads, unsupported versions, stale ownership, and capacity exhaustion are closed outcomes with explicit recovery rules. Physical Host Store corruption, failed SQLite recovery, and storage exhaustion may make every Session on the host unavailable; the host-wide failure domain is accepted and never reported as an isolated Session failure. OnePage tests its semantic use of SQLite and relies on the pinned engine and supported platform for pager atomicity and journal recovery.

Crash evidence uses a private closed catalogue of named semantic points rather than a production fault framework. A fixture subprocess terminates immediately at the selected point without returning through ordinary error handling or deferred cleanup; a fresh process then verifies recovery through the public Run Service or the owning lifecycle interface. Returned injected errors remain ordinary fault tests and cannot stand in for termination. The catalogue covers only boundaries with distinct documented consequences and does not attempt to re-test SQLite's pager internals.

The Host Store has an explicit maximum page count and protects a configured low-water closure reserve from durable admission. Free pages count toward available capacity. Admission performs its writes inside the transaction, then checks the actual remaining page budget before commit; an admission that would enter the reserve rolls back. Closure-class work may consume that reserve. Foreground work never runs `VACUUM`.

V1 makes no backup or long-term retention promise. The state directory is experimental, may be copied only while OnePage is closed, and may be deleted as a whole to reset. Recoverable snapshots, export, Session removal, blob garbage collection, integrity tooling, shrinking, and migration are post-V1 responsibilities. A future backup must bind one SQLite snapshot to its exact immutable-blob closure before it may claim recoverability.

A same-build raw slot image may be added later only as a measured invalidatable cache; it can never be the only durable representation.

## Future deployment and recursive workloads

V1 ships one native Host Runtime. Its semantic boundaries deliberately avoid native layout, SQLite handles, file paths, and process mechanics outside their owners, but portability is not a second implementation requirement. A Cloudflare deployment is post-V1: a Workerd profile would need a Wasm Core, a Storage Owner over Durable Object transactions, and non-process tool capabilities, while a Durable Object-managed Container could retain the native executable but would still need an explicit Workspace and storage topology. Neither path justifies restoring Wasm conformance or a platform framework to V1.

The architecture may later host Recursive Language Model workloads without retaining recursive call stacks. V1's User-directed Jobs already prove durable fan-out and result aggregation, but a model-visible Agent tool, external-context range API, REPL, recursive budgets, persistent environment, and model-directed scheduling remain post-V1 capabilities and must not enter Session authority implicitly.
